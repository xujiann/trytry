## 0. 最大的一处：**有两个机构评分接口，用的是两套引擎**

| | `GET /api/performance/orgs` | `GET /api/analytics/performance-report` |
|---|---|---|
| 权重来源 | `performance_indicators` 表 | `performance_formulas` 表（**另一张表**） |
| 算法 | 五个维度**硬编码**在代码里（转诊/远程/慢病/处方/家医） | 每个指标一条**用户可编辑的公式**，走 `formula.py` 白名单求值 |
| 归一化 | 权重按比例折算到 100 | `weighted / weight_sum` |
| 鉴权 | `require_roles("director")` | `require_roles("director")` |

**这不是"同一个指标算法不同"，是两个平行的评分体系。** 两张表各配各的权重，
两个接口都叫"机构绩效"，前端两个页面各取一个。

**✅ 已裁定（2026-08-21）**：**两套都留，但分工写死**——

- `performance/orgs` = **考核基准**。口径固定、全县横向可比。考核基准的价值就在
  "大家用同一把尺子"，一个各县能自己改公式的引擎天然做不了这件事。
  另外它开箱即用（`DEFAULT_INDICATORS` 启动时种子化）、前端三处在用、有契约与特征化网。
- `analytics/performance-report` = **自定义分析**。公式可编辑正是探索场景该有的样子；
  但 `performance_formulas` 是空表，不写公式则所有机构 0 分，本就不适合当基准。

**已落地（2026-08-22）**：两个页面互相点名对方，说明自己是哪套口径。

- 「绩效考核」页（`core.js` `renderPerformance`）：标明"本页是**考核口径**"、
  显示当前评分周期、点名「期末综合绩效报告」走自定义公式、两者不可比。
- 「决策分析」页（`pages-mgmt.js` `renderAnalytics`）：标明"加权得分"来自自定义公式、
  权重可随时改、与考核评分不可直接比较，对上考核用「绩效考核」页。
- 顺带修「运营月报CSV（累计）」按钮：CSV 里业务量列是累计、绩效分列是当年，
  只写"累计"会让人以为整张表一个口径，改成"业务量累计／绩效分当年"。

`tests/test_performance_caliber_labels.py` 盯住这几句文案。其中一条是**防呆用例**：
前几条都是纯文本查找，文案被挪进 `//` 注释里照样通过——那条要求它出现在
`<p class="desc">` 之后。变异验证：删掉提示、把提示改成注释，各自转红。

## 1. 转诊结案率

| 出处 | 分子 | 分母 | 机构维度 |
|---|---|---|---|
| `performance.py:196-201` | `status=='completed'` 且 `from_org_id==本机构` | `from_org_id==本机构` 的全部转诊 | **按转出机构** |
| `reports.py:75-79` | `status=='completed'` | **全部**转诊 | **无**（全县一个数） |
| `metrics.py:82-90` | 只给 up / down / completed 三个**计数**，不算率 | — | 按可见范围过滤 |

**分歧**：分母是"本机构转出的"还是"全部的"。按 `from_org_id` 算，意味着**接收方
把单子结案了，功劳记在转出方头上**；而接收方自己的分母里根本没有这张单。

**✅ 已裁定（2026-08-22）：维持按转出机构（`from_org_id`），分数不变。**

理由：① 双向转诊考核的落点是"转得出、接得住、转得回"，转出方是这张单存在的
发起方与责任方，一张转出去就没下文的单子应当扣在转出方头上；② 改成双方各算一次，
同一张单在全县口径里被计两次，指标含义变模糊；③ 改口径就是改分数，而分数经
`fund.distribute` 切分基金池——没有卫健口径文件支持的情况下不动真金白银。

**但裁定之前先修了一个更要紧的东西**：`PATCH /api/referrals/{id}/status` 当时
**只有角色守卫、没有机构归属校验**——任何机构的任何医师都能把别人的单子接诊掉、
结案掉（实测：无关第三方机构的医师 `accepted`/`completed` 均返回 200）。
`completed` 正是本指标的**分子**，分子谁都能改，讨论分母属于谁是空谈。
已补：只有接收方机构（`to_org_id`）可推进，全域角色放行（与 spd 侧
`_assert_holds_case` 同源）；归属校验**排在状态机之前**，免得 403/409 的先后
把单据当前状态泄露给没有归属的人。回归见 `tests/test_referral_status_authority.py`
（6 条，三处变异验证）。

口径本身用 `test_结案率按转出机构计_接收方分母里没有这张单` 特征化钉住。

## 2. 远程诊断服务量 / 检查结果互认

| 出处 | 口径 |
|---|---|
| `performance.py:204` | `status in ("reported","recognized")` —— **合并成一个数** |
| `reports.py:60-63` | `reported` 与 `recognized` **分开两个数** |
| `metrics.py:103-107` | 同样分开两个 query |

**分歧**：**互认（recognized）算不算"远程诊断服务量"**。

互认是"上级机构认可下级已有的检查结果、不再重做"——从"服务量"看它没产生诊断工作量，
从"资源下沉"看它恰恰是想要的结果。performance 把两者相加计入服务量，
等于**鼓励互认**；reports 分开列，可以分别观察。

**✅ 已裁定（2026-08-22）：互认照计，等同一次，分数不变。**

理由在于**这一项是按谁计的**——`ExamRequest.from_org_id` 是**申请方（基层）**，
`claimed_org_id` 才是真正出报告的共享诊断中心。所以这一维度衡量的是
"基层通过平台解决了多少次检查需求"，不是诊断工作量。互认（不重复做检查）
恰恰是政策想要的结果，不计入等于惩罚正确行为。

**✅ 补充裁定（2026-08-22）：中心侧也计分，指标随之改名。**

原先按申请方计的后果是——**真正干活的共享诊断中心一分不得**。"资源下沉"考的是
上级把资源投向基层，而提供服务的一方没有任何计分是说不通的。现改为两侧都计：

| 计给谁 | 依据列 | 数哪些状态 |
|---|---|---|
| 申请方（基层） | `from_org_id` | `reported` + `recognized`（互认照计，理由见上） |
| 共享诊断中心 | `claimed_org_id` | 只数 `reported` |

中心侧**只数 `reported`**：互认不产生中心工作量。这一点结构上也成立——
`recognized` 是**建单时**就定下的状态，而领取（`claim`）只能发生在 `pending` 上，
所以互认单永远没有 `claimed_org_id`。用例把这条结构性事实一并断言住了。

同一张单给申请方与中心**各记一笔**是有意的：本维度按机构算"参与了多少次协同"，
不是全县去重总量。

**这会改变分数**：作为共享诊断中心的机构分数上升，进而影响此后按分数分配的基金池。
已分配的池子是冻结快照（`fund` 模块存的是分配当次的得分），不受影响。

**历史数据的已知偏差**：`claimed_org_id` 是 2026-08 才加的列，回填靠 `claimed_by`
展示名反查用户，匹配不上的老单子仍是 NULL。**加列之前那些周期的中心侧数字偏低**，
跨该时点的同比不可比。

**改名**：`远程诊断服务量` → `共享诊断协同量`（原名听起来是诊断工作量，实际两侧都含）。
`DEFAULT_INDICATORS` 已改，**新库自动是新名**。

**存量库不自动改，只报告。** 起初写的是带 `AND name = 旧名` 守卫的 `UPDATE`，
被 `tests/test_migration_data_safety.py`（平台的迁移数据安全闸门）判为 A 档拦下。
拦得对，而且理由不止"规则如此"：`performance_indicators.name` 是**管理端可编辑**的
现场配置，会出现在各县自己的考核文件、报表标题、对上汇报材料里；迁移悄悄改掉它，
现场看到的是"报表列名自己变了"，库里却没有任何记录说明是谁改的。
那个 `AND name = 旧名` 只能挡住"已经改过名"的库，挡不住"没改过名但引用了这个名字"的库。

现改为平台通则的形状（与 `a1c3e5b7d9f2` / `e5b7c9d1f3a4` 同源）：升级时探到仍是旧名
就打一条 WARNING 指名该行，处置 SQL 与界面路径写在迁移 docstring 里，改不改由现场决定。
**不改不影响计分**——计分只认 `key`，`name` 纯展示。

⚠️ **不要和监测指标 #4 搞混**：`reports.py` 的"远程诊断服务量"是《紧密型县域医共体
监测指标体系（2024版）》的**法定名称**，口径是全县一个总数，不按机构分，**不改名**。
同名不同物。

## 3. 慢病随访覆盖率

| 出处 | 口径 |
|---|---|
| `performance.py:210-221` | 分子 = 有过**任意一次**随访记录的 distinct 患者；分母 = 本机构在管慢病患者 |
| `metrics.py:62-67` | `q_chronic_overdue`：`next_due` 已过期的在管患者（这是**逾期**，不是覆盖） |
| `analytics.py:351` | 按机构 count 在管慢病患者（只是**分布**，不算率） |

**分歧（最要紧的一条）**：performance 的"随访覆盖"**不带时间窗**——
一个管了三年的患者，只要三年前随访过一次，就永远计入"已覆盖"。
这个数字只会涨不会跌，随管理年限自然趋近 100%，**基本失去考核意义**。

**✅ 已裁定并落地（2026-08-21）**：`performance/orgs` 整体改为**周期口径**，
`period` 参数支持 `YYYY`（年度，缺省当年）与 `YYYY-MM`（月度）。

慢病这一项的时间语义是**不对称**的，这点值得单独记下：

- **分母 = 在管存量患者，不按期** —— 去年入组、今年仍在管的人今年照样要考核；
- **分子 = 本期内随访过的人**。

分母若也按期，指标就从"在管覆盖率"变成"本期新入组的有多少随访过"，是另一个东西。
分母**只设上界、不设下界**：不设下界 → 三年前入组、至今在管的人今年照样考核；
必须设上界 → 否则查 2025 年度会把 2026 才入组的人算进分母，历史分数随新入组
不断漂移、永远复核不出来。

两个坑都是事后被工具揪出来的，记在这里免得下次重犯：写回归用例时第一版没造出能
**区分**两种实现的场景（患者建于当下，把分母按期过滤掉也照样对），是变异测试发现的；
"分母缺上界导致历史分数不可复现"是 `/review` 发现的。

## 4. 处方合格率

| 出处 | 口径 |
|---|---|
| `performance.py:222-228` | 分子 = `status in (auto_passed, approved)`；**可用 `include_auto_passed=false` 收紧为只认药师人工审核通过** |
| `reports.py:81-87` | 只数 `auto_passed` 一项，且**不算率**；分母是全县全部处方 |
| `metrics.py:112-118` | 只给 `pending_review` / `rejected` 两个计数 |

**分歧**：**系统自动通过（`auto_passed`）算不算"合格"**。

自动通过意味着"没触发任何审方规则"，不等于药师看过。performance 默认算合格
（并留了开关），reports 把它单独列出来。

**✅ 已裁定（2026-08-22）：分子维持含 `auto_passed`，分数不变；但补上"规则可审张数"，
让这个数能被正确解读。**

先把事实摆清楚：`auto_passed` 的产生条件是 `status="pending_review" if violations
else "auto_passed"`——**没有任何规则被触发**就是自动通过。而 `drug_rules` 是
**全县共用的一张表**（`drug_code` 唯一，无 `org_id`），按药品编码维护。

于是：规则库越稀疏，越多处方是"无规则可审"地自动通过，`passed/total` 越接近
100%，越不反映用药合理性。极端情况——规则库为空——全县所有机构这一维度都是满分，
该维度对机构**毫无区分度**，却照样贡献 20% 的权重。

为什么**不**直接把 `auto_passed` 剔出分子：① 规则库是全县共用的，单个机构无法
通过"少配规则"抬高自己的分（不存在按机构的刷分路径）；② 剔出去会让全县分数
集体跳水并立即改变基金分配；③ 收紧口径的开关 `include_auto_passed=false` 本来就在。

改为**照既有先例把"没维护"显式说出来**——同一张 `drug_rules` 表里 `ddd` 未维护时
就是这么处理的（`models/pharmacy.py`：*"ddd 为 0 表示未维护，统计时跳过并计入
未覆盖数——按缺省值硬算…比'明说没维护'更糟"*）。

落地：`detail.rx_pass` 新增 `rule_covered` —— 本期处方里**至少有一味药对得上
生效规则**的张数（按处方去重；**停用**的规则与未维护同路处理，与
`prescriptions._active_rule` 一致）。`passed == total` 而 `rule_covered << total`
时，读数的人一眼看得出这个 100% 是没意义的。

响应体是**追加字段**（`passed`/`total` 原样不动），前端与 `fund.distribute` 都不受影响。
回归 4 条，两处变异验证（停用规则算进覆盖 / 不按处方去重）。

## 落地建议（技术视角，供参考）

1. **先裁定第 0 条**（两套评分引擎）——它决定后面几条要不要统一。
   若两套都保留，剩下几条的"统一"就只在各自体系内部做。
2. 第 3 条（随访覆盖无时间窗）**建议优先修**：它不是口径分歧，更像是个缺陷——
   一个只涨不跌的指标没有考核价值。但改动会让分数普遍下降，需提前打招呼。
3. 第 1、2、4 条本质都是"哪些算分子"，裁定后落地成本很低（改 filter 条件），
   真正的成本在**对历史数据的解释**——去年的分数用旧口径算的。
4. 建议每条裁定后，先加一条**特征化用例钉住新口径的具体数值**，再改实现
   （本仓库既有做法，见 `test_performance_orgs_contract.py` 里逐字钉住的 42.5/32.5/67.5）。

### 周期口径落地时连带修的（`/review` 提出）

改这一条时漏看了两个**内部 Python 调用方**——只查了前端，没 grep 代码：

- `fund.distribute()` 用绩效分**切分基金池**。基金池结算通常在次年年初，
  不显式传 `period=str(pool.year)` 就会拿"次年至今"近乎空白的分数去分上一年度的钱，
  轻则份额全错、重则所有权重为 0 直接 422。**这是真金白银按错数字分。**
- `reports.export_operations_csv` 其余各列都按 `period` 过滤，分数列不跟就会出现
  "本月就诊 30 人次、绩效分却是全年"这种一行两个口径的报表。

两处都已修，并各加一条守卫用例钉住（变异验证：去掉 `period=` 立刻转红）。

#### 已知的兼容性破坏（本次唯一一处）

运营月报 CSV 的表头列名由 `绩效评分` 改为 `绩效评分(<周期>)`（如 `绩效评分(2026)`、
