# 第十六轮：把三条工程判断变成平台一致的状态

上一轮的缺陷猎捕里，有三处判断做得好——好到我在报告里专门点了名。
点名是不够的：**一次做对是个人手艺，处处做对才是平台性质。**
这一轮把那三条判断从"某个包做对了"推到"全平台做不对就变红"。

三条判断各自对应一条反例——都不是别人写的，其中一条是我上一轮亲手写的。

---

## 判断一：同一个判定只许有一份实现

**出处**：F4 发现 `ws.py` 的 `_token_valid()` 是 HTTP 侧准入判定的第二份、更弱的
拷贝——验签名/过期/黑名单，却漏了账号停用、改密基线、令牌作用域。同一枚令牌
HTTP 侧 403、WebSocket 侧照常建连收危急值。修法是抽 `deps.check_token_admission`。

要害不是"代码写重了"，而是**同一个业务问题有了两个可以各自演化的答案**：
HTTP 侧补了三条判定，WS 侧不会跟着补，而且谁也不会发现——两侧的正常路径用例
全都是绿的。

**判据**（不是"代码相似"）：改了一处、另一处不会跟，且两处都还能跑。

**按这把尺全平台扫，找到两条同形的**：

| | 同一个问题 | 两个答案 |
|---|---|---|
| M1 | 登出黑名单用什么键 | "jti 优先、无 jti 退回原文"这条规则写在**四处、三种形状**，横跨业务端与居民端，且**写入端与判定端分属不同形状**。键规则一改（比如按 scope 加前缀，避免居民端登出误伤同 jti 的业务令牌），漏掉任一处就是"按一个键写进去、按另一个键查"——黑名单静默失效 |
| M2 | 这家机构的调阅授权此刻还算数吗 | 在**空 `expire_date`** 上两个答案正好相反：`visibility` 判"空 = 不设到期日 = 有效"，`patients.check_authorization` 在 SQL 里比 `expire_date >= 今天`、空串比不过判为无效。而 `expire_date` 是 `String(10) default=""` 的非空列，空串是可达状态。于是同一条长期授权，真正把门的那个判定说"能调阅"，给对接方看的校验接口说 `allowed=false` |

收敛为 `security.revocation_key()` 与 `visibility.active_authorization_grants()`。
M2 的口径**以把门的一侧为准**——它才是真正做事的那个判定，校验接口只是把同一件事
说给对接方听；让"说的"去追"做的"，不能反过来。`scope` 刻意不并进去：可见性判定
不分范围（拿到任一有效授权即构成依据），校验接口回答的是"我要的这个范围在不在
授权里"——这是两个不同的问题，不是同一个问题的两份答案。

**闸门**：`tests/test_single_source_judgements.py`，七类判定、164 个文件、
1754 个函数，豁免 2 条各带理由且只减不增。

**闸门自己被自己的自证抓过一次**：第一版的 PII 那条扫描盯"裸等值比较"，
而收敛后的代码里那种写法一处都没有——它 0 违规、100% 覆盖率，**其实永远不会响**。
是"每类判定的落脚点数为 0 即断言失败"这条自证把它抓出来的。这正是第十五轮
"闸门要自证覆盖面"的续集：报覆盖率不够，得报**分子**。

**顺带**：`printing.REFERRAL_STATUS_NAMES` 是转诊状态文案的第三份、与业务端逐字
相同，本轮合掉（改为 import）。居民端那套措辞不同（待接收/已接收/已完成）是刻意的
对外分叉，不是拷贝，登记为 P1-38。

## 判断二：迁移不得静默改动存量业务数据

**出处**：F3 给住院结算单加唯一索引时遇到存量重复，选了不阻塞路径——跳过建索引、
打一条**指名 admission_id** 的 ERROR 日志、把补建 SQL 写进 docstring。
理由是"财务凭证不能由程序替人决定删哪张"。

**反例是我上一轮自己写的**。`d3e4f5a6b7c8` 为了给 `resident_accounts.patient_id`
的部分唯一索引腾地方，先跑了一段 `SET patient_id = NULL`，把"一档多户"里除 id
最小以外的账户静默解绑。这是最坏的一种：

- `patient_id` 是绑定关系的**唯一载体**，置空即信息丢失；
- 裸 SQL 不经应用层，`audit_logs` 里一条都没有——事后连"谁被解绑过"都查不回来；
- **"留 id 最小的"本身就是错的判据**：一档多户最常见的成因是家人替老人注册，
  本人的账户往往是后建的那个，被清掉的恰恰是正主。

另一条 `d5e6f7a8b9c0` 把重复的全域基金池改成 `closed`——留了痕也没删行，
但仍是程序替财务决定哪本账作数，而池子下面挂着预付与结算单。

两条都改成 F3 的路径，一行存量数据都不动。改法**重放安全**（先探索引是否已存在
再动手，跑过旧版的库重放是 no-op）；两边的 `downgrade` 补上"索引不存在就跳过"，
否则跳过建索引的库一回退就炸。新增补偿迁移 `a1c3e5b7d9f2` 收尾：跳过的索引在链尾
重探一次、无冲突就补建，并统计"未绑定却存在同手机号档案"的账户打 WARNING——
那多半就是被静默解绑的那批。

**已经发生的解绑恢复不了。** 这一点写进迁移 docstring 与 `docs/运维手册.md`，
连同人工排查的三条嫌疑面查询，不假装能自动修。

**闸门**：`tests/test_migration_data_safety.py`。全量审计 85 个迁移（A 破坏性 2 /
B 补值性 5 / C 结构性 79），判定**fail-closed**——f-string 拼列名这种看不懂的写法
一律判红，宁可误报也不漏报，漏报的代价是下一次静默解绑。

## 判断三：清单不能靠人记得更新

**出处**：F6 把"零漂移"守卫从只比表名改成 `compare_metadata` 全量比对——
一比就从 0 处差异变成 77 处。旧守卫的分母只有表名，看不见列、索引、唯一性、外键。

**判据**（好清单 vs 坏清单）：**忘记更新它，会静默出错，还是当场变红？**

- **好清单**：只减不增的欠账登记（基线快照、豁免表）。忘了更新 → 变红。
- **坏清单**：写新代码时必须记得同步的枚举（"所有加密列"、"所有角色名"、
  "所有前端页面"）。忘了更新 → **静默出错**，而所有用例照样绿。

七处坏清单改成从代码结构推导：加密列清单改从模型元数据（`EncryptedPII` 列类型）
推导，可见性服务关系表改从"同时带 `patient_id` 与机构外键"推导，前端页面清单改从
页面注册表推导，等等。以后新加一列加密 PII、新开一个页面，**自动进入守卫的分母**，
不需要有人记得来改清单。

## 三条之间的一次撞车

J1 与 J3 各自做出了一份 PII 检索守卫——**两份守卫守着同一条判定**，
恰恰是本轮判断一要消灭的形状；而且 J1 那份的加密列清单是**手写**的，
又是判断三刚拆掉的形状。合掉手写那份，留元数据推导那份。

但那条判定仍留在 J1 的覆盖面报表里，落脚点数直接引对方的扫描结果：
**"由别人守"和"没人守"在报表上必须长得不一样**，对方哪天被删或被改到空转，
这边跟着红。

## 一条报上来但不成立的

J1 报"`integration.fhir_observation` 无任何鉴权依赖，只认 `X-Source-System` 头"。
实测：无令牌访问返回 **401**。鉴权挂在 `APIRouter(dependencies=...)` 的**路由器层**，
只读函数签名看不见它。

按仓库的规矩，**怀疑不值钱、触发才算数**——这次的补充是：跑一次探针比读一遍
签名可靠，**"某处没写"不等于"某处没有"**。如实记在 `docs/TECH_DEBT.md`。

## 顺带装上的：测试超时看门狗

F2 那条 WS 缺陷的用例在旧代码上**永久挂起**——不是失败，是挂住。挂住的测试
比失败的测试更糟：CI 上看起来是"还在跑"。

排查：app/ 侧出网 HTTP 全部已带 timeout；风险全在 tests/（`ws.receive_*` 23 处、
`Barrier.wait` 5 处、`Thread.join` 8 处，均无 timeout）。

仓库无 `pytest-timeout`，按第 12 条不引。四选一：

- ❌ 线程看门狗（`PyThreadState_SetAsyncExc`）：字节码边界才生效，**打不断**卡在
  `queue.get()` / `lock.acquire()` 的主线程——而 F2 那条恰恰卡在这里；
- ❌ `faulthandler.dump_traceback_later(exit=True)`：整个进程被杀，不是"某条用例失败"；
- ✅ **SIGALRM**：唯一能打断阻塞系统调用与锁等待的做法，二十行；
- 装在 `pytest_runtest_protocol` 的 hookwrapper 上而非 autouse fixture 上——
  fixture 按作用域排序，module/session 级（`TestClient(app)` 那种）在函数级 autouse
  **之前**建立，卡在那里就落窗口外了。

非空洞验证：摘掉 ws 心跳复核（模拟 F2 旧代码），旧行为是永久挂起，
现在是 `TimeoutError: 用例超时`，栈顶正是 `ws.receive_text()`。

## 验证

- 三包各自非空洞验证（每处改回旧写法确认变红），合计 6 + 4 + 7 条红/绿记录。
- 空库 `alembic upgrade heads` 通过，六个部分唯一索引全部建出，259 张表。
- `make build` / `make lint` / `make typecheck` 全绿。
- 合入过程中自己发现并修掉一处：`_patient_basis_uncached` 里 `org_id` 可能为
  `None`（调用方已挡，但函数自己没挡）——少了这道守，下面每一处 `列 == org_id`
  在 SQL 里都会退化成 `IS NULL`，也就是"和其它同样没机构的脏数据算作有关系"，
  **静默放行、不报错**。是 mypy 在合并后报出来的。
