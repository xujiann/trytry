# 通用平台能力补全开发计划

> 编制日期：2026-08-12。现状基线：158 张表 / 500+ 接口 / 583 项测试通过。
> 参考来源：国家《紧密型县域医共体信息化功能指引》（国卫办规划函〔2025〕63 号，
> 36 项已全部实现）、《浙江省县域医共体信息化建设指南》（82 项，现 A 64 / B 16 / C 2）、
> 《紧密型县域医共体建设参考手册（第一版）》（国卫基层运行便函〔2025〕4 号）典型案例。

## 〇、编制原则

本平台是**通用产品**，不是某一个县的实施项目。地方案例只用来回答一个问题：
"某地能做成的事，我们的模型支不支持得住？" 支不住的，补的是**能力**，不是那一地的
**流程**。

由此有三条硬约束：

1. **地方差异走配置，不走代码分支。** 任何一个县的具体办法都不得出现在 `if` 里。
   平台已有三个承载差异的支点——AST 白名单公式引擎（`app/formula.py`）、条件规则引擎
   （`app/rules.py`）、流程引擎（`workflow_definitions`）。新能力挂上去，不另起炉灶。
2. **新增维度一律可空、可不启用。** 不做总额付费的县、不分片区的县、不建专病中心的
   县，都应当感觉不到这些功能存在，而不是被迫先建一个空壳。
3. **不内置任何一地的组织架构。** 案例里的"运营发展中心三科"这类设置属于地方组织
   形式，通用平台不该内置——等自定义角色做完，用角色 + 页面权限配出来即可。

## 一、待补能力（按建议顺序）

### 阶段六 机构协作分组 ✅ 已交付

**问题**：`organizations` 只有 `parent_id` 单树，表达得了"隶属"，表达不了"协作分组"。
各地叫法不一——片区、健共体、医共体分片、网格、专科联盟——但结构是同一个：
机构的横向分组，且**可能多重**（一家卫生院既属某片区，又属某专科联盟）。

**做法**：新增 `org_groups`（分组名、分组类型、牵头机构、启停）与
`org_group_members` 多对多关联。不叫"片区"，因为那是其中一种类型而已。

**关键约束**：分组是横向的，`parent_id` 是纵向的，两者正交。**不要做成第二棵树**——
做成树，跨组调拨与跨组转诊立刻会遇到归属冲突。

**改造面**：约 30 处按 `org_id` 聚合的统计增加可选分组维度。建议在 `deps.py` 里做成
一个公共依赖统一解析，不在 30 个接口里各写一遍。

**风险**：这是唯一会改动既有统计口径的一步。动手前先补一组"分组聚合之和等于总数"
的用例，否则加了维度之后没人能保证各处口径还一致。**越晚做代价越大**，故排第一。

**交付结果**：`/api/org-groups`（分组增删改、成员进出、按机构反查、覆盖情况），
`deps.resolve_org_scope()` 公共依赖，运行效率 / 床位统计 / 用药结构 / 临床质量指标 /
绩效计分五处接入 `group_id`。管理端新增「机构协作分组」页。

实现过程中定下的几条口径：

- **分组不存在返回 404，不静默退化为全域**。把不存在的分组当成"没筛选"，
  会让人看着全县数据以为是某片区的。
- **分组与机构同时给出取交集**，不在组内即返回空集——这是唯一不会让人意外的语义。
- **就医流向刻意不支持分组筛选**：县外就诊记录没有县内机构归属，只筛县内一侧会得到
  分子分母不同域的比率，比不提供筛选更容易误导人。理由写在该接口的 docstring 里。
- **覆盖情况接口把未入组机构点名列出**。分组统计的天然陷阱是未入组机构的数据从分组
  视图里凭空消失，事后追问"为什么各片区加起来对不上全县"极难倒查。

顺带修了改签名时踩的一个坑：`efficiency()` 有一处内部位置调用，参数位置变化后
`db` 被塞进了新增的 `org_id`；相应的打桩用例也改为 `*args/**kwargs` 转发，
避免以后再随签名变动而失效。

### 阶段七 基金池与结余分配 ✅ 已交付

**问题**：绩效考核（`/api/performance`）算得很细，但**算完之后没有钱跟着走**——
考核结果只是一张排名表。而"总额付费、结余留用"正是紧密型与松散型的分界线，
也是绩效结果唯一的落地出口。平台缺的是把结算单、基金监测、预算表串成一本账。

**做法**：四张表 + `/api/fund` 模块

| 表 | 职责 |
|---|---|
| `fund_pools` | 基金池：年度、参保类型、筹资总额、预付比例 |
| `fund_prepayments` | 预付：按比例预付，记批次与到账 |
| `fund_periods` | 周期结算：按周期归集实际发生额，与预付对冲，出结余/超支 |
| `fund_distributions` | 清算与分配：清算总账 → 按公式分配结余 |

**四个必须先定死的口径**（写进接口返回，不只写文档）：

1. **分配依据须冻结绩效得分快照**。指标权重可调，若分钱时"当下重算"，等于分完钱
   还能改分。与知情告知书冻结正文同理。
2. **超支不自动扣减**。平台不替政策做决定：算出来、标红、把处置方式做成可配置
   （分摊/挂账/不处理），默认只记不扣。
3. **周期结算不产生资金流**，只有清算产生。两者混在一张表里，年终对不上账时无从倒查。
4. **分配办法用公式引擎表达**。各县办法不同且逐年调整，绝不写死进代码。

**可不启用**：不做总额付费的县不建池子即可，其余功能不受影响。

**交付结果**：`/api/fund`（池子 / 预付 / 预结 / 清算 / 分配 / 公式变量表）。
四条口径全部落到实现与用例上，并随接口返回一起给出。

实现中补充的几个决定：

- **公式返回份额权重而非金额**，由平台归一化。这样任何办法都能表达（均分 `1`、
  按绩效 `score`、拉开差距 `score ** 2`），也保证分完的钱正好等于结余。
- **可用变量刻意只有三个**（score / rank / org_count）。变量越多，各县越容易写出
  没人能复核的表达式。
- **预付超计划只警告不拦截**：现实中确有追加预拨，不该因为一个比例参数挡住真实
  发生的资金流。
- **重复预结同期为覆盖**：月中反复核对是常态，累加会算出虚高的发生额。

修了两个自己埋的坑：`UniqueConstraint` 含可空列在 SQL 里形同虚设（NULL != NULL），
全域池的重复创建没被拦住，改为应用层显式查一次；`validate()` 抛出的 FormulaError
没接住，非法公式返回 500 而非 422。

### 阶段八 人员调度与专病管理 ✅ 已交付

两块独立能力，规模相当，可并行。

**人员调度**：现有 `duty_rosters` 只有 4 个字段，够排共享中心值班，不够做人员下沉
调度。需与 `secondments`（派驻）打通成"谁、去哪、多久、在岗否"的统一台账。
直接收益：国家监测指标里的**"中级及以上医师派驻 6 个月以上人数"目前算不出来**，
打通后可直接出数。

**专病管理**：与慢病管理（`chronic`）**不是一回事**，不要复用那套表。慢病是长期
随访分级，专病是单病种诊疗路径（入组—路径节点—疗效评价—出组）。硬套会得到一个
两头不像的模型。病种目录与路径节点应当可配置，不预置任何具体病种的路径。

**交付结果**：`/api/staffing`（派驻台账、职称等级维护、下沉指标统计）与
`/api/disease-programs`（目录、入组、节点、疗效、出组、统计）。管理端新增
「人员下沉调度」「专病管理」两页。

监测指标的取数口径三条，都写进了接口返回：只计长期派驻（巡诊与短期支援不是下沉）、
跨年派驻只计落在统计年度内的天数、职称等级未填的不默认算入"中级及以上"而是单独
报出 `unknown_title_level`。职称等级**不从 `title` 文本推断**——各院写法不一，
靠关键词猜，一个"助理全科医生"就能把统计带偏。

专病侧两条：必需节点未做完**也允许出组**（转院、拒治是现实，硬拦只会逼人补假记录），
未完成节点留在完成度里如实呈现；疗效留空表示未评价，统计里单列不并进任何一档。

### 阶段九 代码健康度收口 ← 新增，插在最前

2026-08-12 第五轮代码审阅（`docs/第五轮代码审阅与下一步开发计划.md`）发现三条
必须先处理的问题，其中第 3 条是阶段十一的入场券：

1. `program_stats` 的 N+1（实测 50 条入组 → 103 次 SQL）与 `dispatch_stats`
   全表进内存；
2. 时间函数四套并存（aware/naive 混用），阶段二已经真炸过一次；
3. **越权用例只覆盖 64%**，259 个写接口路径中 91 个没有 403 用例——
   权限重构触及全部 550 个端点，没有这张网收不了口。

### 阶段十 统一资源与申请单中心

（原浙江计划阶段四）通用资源注册-发布-撤回模型，把号源/检查/手术间/血制品/工勤
收敛到一套资源表；`/api/service-requests` 从聚合视图升级为排程撮合中心；
流程图形化编排（前端画布产出既有 JSON 定义，**后端不动**）；DRGs 事前提示与事中预警。

### 阶段十一 权限模型重构与安全加固

（原浙江计划阶段五）角色表 + 权限点表 + 关联，`require_roles` 改为查权限点；
六个内置角色作为预置数据保留，保证现有部署零感知升级；审计防篡改哈希链与归档；
错误信息脱敏统一出口；CSP 响应头。

**排最后的理由不变**：它触及全部接口的鉴权路径。现有 643 项测试是唯一的安全网，
而越权用例目前只覆盖 64% 的写接口——**阶段九第 3 项完成前不要动这一步**。

### 阶段十二 前端拆分与金额精度（低优先）

`app.js` 5032 行按业务域拆分（用现有 PAGES 注册表做入口，**不引入构建工具**）；
40 列金额 `Float` 改 `Numeric`，建议与接入真实医保结算同批做。

## 三、明确不做的事

- **不把分组做成第二棵机构树**（理由见阶段六）。
- **不在平台内写死医保分配办法**——只提供池子、账、快照与可配置公式。
- **不内置地方组织架构**（如"运营发展中心三科"工作台），等阶段十自定义角色配出来。
- **不重做流程引擎**：图形化编排只应是前端画布产出同一份 JSON 定义。
- **不建主题数据仓**：单县百万级人口用不上数仓分层，真要做也应等接入省平台后按省侧
  口径建，而非自造一套。
