## 一、最高杠杆：三条被各自卡住的主通道

这三项高度相连，构成一条主线——**schema 能演进 → 隔离能根治 → 系统能横向扩展**。建议按此序推进。

### 1〔近期·必做〕修复 alembic 迁移链——它现在是坏的，被 `create_all` 掩盖 `[已核验]`

**证据**：`python -m alembic upgrade head` **直接失败**：`Multiple head revisions are present`。
`alembic/versions/` 51 个 revision 里有多个 head（实测 `alembic heads` 至少 2 个已命名 head，
另有大量从未接入主链的孤立单节点迁移）；运行时 schema 实际来自 `main.py:114
Base.metadata.create_all()`——**迁移根本没参与建库**，所以至今不显形。

**为什么现在做**：空库能起、有数据的库改不动。一旦生产库有真实数据、需要第一次 `ALTER`
（正是下面第 3 项补 `org_id` 要做的），会发现没有可用迁移路径——在最坏的时机暴露。

**做法**：把孤立迁移按真实依赖 rebase 成单链或生成 merge revision 收口；在空 PG 上 `upgrade head` 跑通；
用 `alembic revision --autogenerate` 对比确认"迁移终态 == 模型终态（`create_all` 现状）"；把
`alembic heads` 数==1 与 `upgrade head` 加进 CI。**工作量中、风险低（纯离线整理 + 一次对齐）。**

### 2〔近期·必做〕横向隔离从"靠人记得"升级为强制门禁，并补上扫描盲区

**证据（盲区是本轮最重要的发现）**：`test_stage15_horizontal.py` 的两个 AST 扫描各有一个结构性盲区，
本轮新发现的越权点几乎全部正好落在盲区里：

1. **按 id 写扫描**只匹配函数体里字面出现的 `db.get(<带org_id模型>,`。凡把取对象包进 helper 的
   端点——`_load_task` / `_enrollment` / `_admission_or_404` / `_pending` / `_get` / `_specimen`——
   `db.get` 被藏进 helper，扫描看不见，**即便缺守卫也不进 `UNGUARDED`、测试照绿**。
2. **患者维度 GET 扫描**只收 `patient_id`/`ehc_no` 入参的函数。所有按 `admission_id`/`encounter_id`/
   `request_id`/`enrollment_id`/`record_id` 直取的详情读接口**一律不在矩阵内**。

且门禁 (a) 埋在测试套里、不是独立 required check；(b) 用子串匹配、有假阴性；(c) 只覆盖 GET 患者维度 +
by-id 写，**GET 机构维度清单读没有等价门禁**。`visibility.py` 自己的血泪注释（D-5～D-8 反复复发）
已证明"需要人记得的事会被忘掉"。

**做法**：把三个扫描用例升级为独立 required CI job；扫描识别经 helper 的 `db.get`（按调用图而非子串）；
`_patient_scoped_endpoints` 纳入 `admission_id`/`encounter_id`/`enrollment_id` 等间接患者维度键；
补一条 GET 机构清单读的扫描维度。**做完这条，下面 §二的收口才不会"修完又复发"。工作量中、风险低。**

### 3〔中期·根治〕给服务记录表补 `org_id`（迁移 + 回填）——`visibility.py` 点名的根治项

**证据**：`visibility.py:344` 的 `visible_patient_ids` 注释直接点名："这几张表连'哪家机构做的'
都答不出来，于是机构工作量统计也做不了。补 org_id 是根治，但要迁移与回填，不在本批。" 约 20 张带
`patient_id` 却无 `org_id` 的表，高价值子集：`maternal_records / child_records / exam_requests /
chronic_patients / consultations / appointments / emergency_cases / bill_details / outbound_visits /
satisfaction_surveys`。不补，`scope_patient_list` 只能用跨全部关系表的 `UNION ALL` 子查询兜底
（县医院服务人数≈全县人口，明确的性能与正确性代价），且 maternal 这类模块的兜底**当前根本没接上**
（见 §二·1）。

**为什么排在第 1 项之后**：它正是"可用迁移链"的第一个真实客户。**工作量大、风险中（回填口径逐表定，
回填错=隔离错）。**

## 三、业务逻辑正确性（非安全，按会不会算错数排序）

**中等（会算错数 / 少收钱）**
- `medication.py:183 medication_profile` 把**全部历史处方**当"在用"，无时间窗/失效回收，
  `polypharmacy_warning`（≥5 种）虚高误报。"在用"类统计须加有效状态或时间窗。
- `quality.py:611 record_qc_summary` 月度病历质控**先 `limit(5000)` 后 Python 过滤月份**，
  病历超 5000 条时较早月份被静默漏算。应改 SQL `created_at` 区间过滤。

**低-中（口径 / 边界 / 精度）**
- `drgs.py:222 vs 236`：同一响应内机构级 CMI 用存量快照 `drg_weight`、MDC 级用目录当前 `base_weight`，
  改权后两者对同批病例给出不同 Σ权重。应统一用病例存量快照。
- `infectious.py:131` 迟报判定用**整天差×24**丢小时：甲类当日 5h 上报判为不迟、乙丙类次日 25–48h 判为不迟，
  系统性低估迟报率。应用完整 `datetime` 差。
- `pharmacy.py:196` 采购建议 `int(gap+0.999)` 对尾数∈(0,0.001) 取整错误，应 `math.ceil`。
- `cost.py:221` 占用床日 `max(days,1)` 对当日入出院（0 床日）也计 1，轻微高估床日、低估床日成本。

**量级 / 扩展性（正确但不可扩展，县域规模会显形）**
- `followups.followup_stats`、`spd/collectors.collect_publichealth`（全表载入做幂等去重）、
  `spd/service.award_points`（全表载入算日限、且 check-then-act 非原子可击穿日限）、
  `billing._orders_of_day`——统一下推到 SQL（`WHERE 时间区间 + GROUP BY + 聚合`）。

## 四、工程与运维债

- **审计链多 worker 根治**〔近期〕：`main.py:426 _audit_lock = threading.Lock()` 进程内锁，多 worker 下
  两进程读到同一 `prev_hash`→`verify_chain` 误报断链。`state_store` 黑名单/锁定、`scheduler` 都已 Redis 化，
  这是**唯一未解决的横向扩展硬阻塞**。方案：Redis 分布式锁，或更彻底地把链改成 DB 侧 `SELECT…FOR UPDATE`/
  Postgres advisory lock；必须补一条多 worker 并发写的链完整性测试。**另注**：`entry_hash` 现绑定
  `created_at` 序列化字符串，若换 `DATETIME(0)` 等截断亚秒精度的后端会误报——链完整性不应耦合时间戳保真度。
- **覆盖率门禁转正 + 修测试串扰**〔近期〕：`ci.yml` 覆盖率是 warning 模式（`|| true`）；`conftest.py` 全套
  共享 `sqlite:///./test_run.db`、模块级重建，`-k`/并行会互相踩（本轮多次遇到"隔离artifact"即此因）。
  去掉 `|| true`；DB 隔离下沉到 per-xdist-worker 临时库以启用 `-n auto`；CI 顺带跑 `test_postgres_real.py`
  （当前 CI 只跑 sqlite，方言差异无人守）。
- **by-id 归属校验做成依赖注入**〔中期〕：`assert_obj_org_*` 现 80+ 处手工调，模式一致（取对象→判归属）。
  一个 `Depends(load_and_authorize(Model))` 把"404 + 机构归属 + 取对象"收成一次，端点拿到的即已授权对象——
  是"抽出来才算数"在写侧的自然延伸，配合 §一·2 门禁把疏漏从"红"变"默认不会发生"。
- **拆分 `models.py`**〔中期〕：3938 行、~150 模型于一文件，是改模型的合并冲突热点。按领域拆包、
  `models/__init__.py` 重导出保持 `from app.models import X` 不变 + import 冒烟测试。风险低。
- **前端**〔远期〕：`static/` 5 个大文件共 149 处 innerHTML，但 `esc()` 用得很密、**XSS 大面已受控**；
  残留约 6 处裸插值（clinical）+ `m/doctor.js`/`m/m.js` 各复制一份 `esc()`。先做低成本增量（审计裸插值 +
  统一 esc + 拆大文件），把"上构建/框架"作为单独决策——`build-free` 是仓库既定约束，需团队 buy-in。
- **可观测性 / 国密纵深**〔远期〕：`monitor.py` 是进程内计数（多实例各查各的），多 worker 解锁后补
  config 开关的 `/metrics` 导出；`gmcrypto` 刻意不实现 SM2/SM4（"能跑但不安全的国密比没有更危险"），
  等保/密评落地时接密码机或认证库。

## 五、建议的推进顺序（一句话）

**先修迁移链（§一·1）→ 转正隔离门禁并补扫描盲区（§一·2）→ 借可用迁移链补 org_id（§一·3）**，
这条主线同时打通 schema 演进、隔离根治、横向扩展三个当前各自卡住的通道；其间**§二的隔离缺口**随门禁转正
逐条清（clinical_docs / maternal / disease_programs / surgery / spd 积分链优先），**§三的算数口径**
挑 medication 时间窗、quality 月度统计、drgs CMI 三条先做。审计链去进程锁（§四）与覆盖率门禁转正是解锁
多实例部署的前置，可与主线并行。
