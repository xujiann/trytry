## 一、P0：会造成 500 / OOM 的缺陷

### P0-1 规则求值器的类型错误逃逸成 500（上一轮我引入的）

`/api/rules/evaluate` 的 `variables` 是**客户端自由传入的 dict**，而
`app/rules.py` 只把 `RuleError` 当作预期失败捕获。变量类型与规则预期不符时，
底层 `float()` / `len()` 抛的 `TypeError` 直接穿透成 500。

已验证的三个复现（均返回 500）：

| 输入 | 抛出 |
|---|---|
| 规则 `len(chief_complaint) < 5`，传 `chief_complaint: 123` | `TypeError: object of type 'float' has no len()` |
| 规则 `daily_dose > 100`，传 `daily_dose: null` | `TypeError: float() argument must be...not 'NoneType'` |
| 规则 `daily_dose > 100`，传 `daily_dose: {"a":1}` | `TypeError: ...not 'dict'` |

讽刺的是，`evaluate_rules` 里那套 `errors[]` 机制本来就是为"一条写坏的规则不能
让整个审方停摆"设计的，测试也覆盖了"引用未知变量"的情形——但只覆盖了
`RuleError` 这一条路径，类型不匹配这条路径漏了。

**修法**：`_eval_operand` / `_eval_node` 对非数值、非字符串、非布尔的变量值统一
抛 `RuleError`；`len()` 的参数必须是字符串否则抛 `RuleError`；
`evaluate_rules` 兜底再捕一层 `TypeError/ValueError`。属于三处小改，附回归用例。

### P0-2 审计日志全量导出会打爆内存

`GET /api/audit/export`（`users.py:export_audit_logs`）把整张 `audit_logs` 表
一次读进内存并序列化成单个 JSON 响应：

```python
logs = db.query(AuditLog).order_by(AuditLog.id).all()   # 无 limit、无游标、无流式
```

审计中间件对**每一次写操作**留痕，一个县域平台跑一年就是百万级行。这个接口
在开发库上看不出问题，在生产上是一次 OOM。

**修法**：改为按时间区间 + 游标分页（`since_id`/`limit`），或走 `StreamingResponse`
按批 yield NDJSON。归档场景本来就该是流式的。

## 二、P1：性能与边界

### P1-1 综合绩效报告是 N+1，且每次都全表扫描

`/api/analytics/performance-report` 对每家机构调一次 `formula_variables()`，
而后者内部又调一次 `efficiency(period, db)` ——`efficiency` 每次都要扫描
**全部住院记录 + 全部就诊记录 + 全部在岗员工**。

实测（几乎空库、25 家机构、100 条就诊）：

| 调用 | 耗时 |
|---|---|
| 单次 `/api/analytics/efficiency` | 14 ms |
| `/api/analytics/performance-report` | 155 ms |

空库就已经是 11 倍关系，随机构数线性放大；一旦有真实数据量（十万级就诊、
万级住院），这张报表会退化到几十秒级。

**修法**：`performance_report` 里把 `efficiency(period)` 提到循环外算一次，
按 org_id 建索引复用；`formula_variables` 增加可选的预计算参数。改动很小，
收益是把 N 次全表扫描降到 1 次。

### P1-2 患者 360 视图无结果上限

`encounters.py:patient_360_view` 对就诊、报告、处方三类全部 `.all()`，没有
`limit`。一位管了十年的慢病患者可以攒出数百条就诊与上千条处方明细，单次响应
体积不可控。同域的居民端 `_build_archive` 是有 `.limit(50)` 的，两处口径不一致。

**修法**：与居民端对齐，各类取最近 N 条并返回 `has_more` 标记。

## 三、P2：最大的功能缺口——后端跑在了前端前面

阶段一~五交付了 56 个新接口、24 张新表，**管理端 SPA 一个页面都没加**。
按模块统计接入情况：

| 状态 | 模块 |
|---|---|
| SPA 已接入（46 个） | 机构、患者、转诊、共享诊断、审方、药房、慢病、住院、DRG…… |
| **SPA 未接入且应该接入（10 个）** | `jobs` 定时任务、`surgery` 手术麻醉、`clinical_docs` 住院文书、`followups` 随访中心、`accounting` 会计凭证、`cost` 成本核算、`materials` 物资与耗材、`analytics` 决策指标、`rules` 规则引擎、`workflows` 流程引擎与申请单中心 |
| 未接入但合理（6 个） | `portal`（居民端自有 H5）、`health`（探活）、`triage`/`surveys`/`encounters`/`integration`（被其他页面内联调用或对机器） |

这意味着最近五个阶段的能力，目前只能用 curl 或 `/docs` 操作。对一个要交付给
县域机构使用的平台，这是当前最大的短板——功能存在，但没人用得到。

## 四、P3：工程质量收尾

- **老模块异常分支覆盖**：`consultations` 76%、`contracts` 78%、`cssd` 78%、
  `referrals` 79%——状态机拒绝、越权、并发冲突这些分支缺测试。
- **演示数据未覆盖新模块**：`scripts/seed_demo.py` 停在第四阶段，跑完之后
  手术、成本、会计、随访、流程这些页面全是空的，演示时看不出东西。
- **`/api/jobs` 对所有登录用户可读**：任务名与执行摘要（含各类超期数量）
  对医师、药师同样可见。建议收敛到管理层。
- **`service-requests` 的 `total` 与截断口径不一致**：`total` 统计截断前数量，
  `items` 截断后返回，但响应里没说明这一点。

## 五、下一步开发计划

排序依据：**先修会崩的，再补没人用得到的，最后做锦上添花的**。

### 阶段六·A：缺陷修复（最优先，工作量最小）

- **T6.1** 规则求值器类型安全：非数值/字符串/布尔变量统一转 `RuleError`；
  `len()` 参数类型校验；`evaluate_rules` 兜底捕获。配三个复现用例的回归测试。
- **T6.2** 审计导出改流式/游标分页，加大表场景的用例。
- **T6.3** 综合绩效报告消除 N+1（`efficiency` 提到循环外）。
- **T6.4** 患者 360 视图加上限与 `has_more`，与居民端口径对齐。

### 阶段六·B：管理端 UI 补齐（工作量最大，价值最高）

按"临床 → 运营 → 平台"顺序补 10 个模块的 SPA 页面，复用现有
`formJson` / `postAction` / `table` 三件套与角色化导航：

1. **住院文书 + 手术麻醉**（医师日常使用频率最高）：病程记录时间线、体温单
   趋势图、手术排班表、术中记录表单；
2. **随访中心**：待随访/超期看板，按类别筛选与完成录入；
3. **成本核算 + 会计凭证**：科室成本表、分摊规则配置、凭证录入（借贷双列
   实时校验合计）、试算平衡表；
4. **物资采购 + 高值耗材**：采购流程四步条、条码追溯查询；
5. **决策指标**：就医流向与运行效率图表、公式管理、综合绩效报告；
6. **平台引擎**：规则目录与在线试算、流程定义可视化、我的待办、统一申请单中心。

### 阶段六·C：工程收尾

- **T6.5** `scripts/seed_demo.py` 补齐新模块演示数据，让每个页面打开就有内容；
- **T6.6** 把 P3 列的低覆盖模块拉到 85%（专测异常分支）；
- **T6.7** `/api/jobs` 收敛到管理层；`service-requests` 补 `truncated` 标记；
- **T6.8** E2E 用例扩到手术全流程与随访闭环。

### 建议的执行顺序

A（半天量级）→ B（主体工作）→ C（收尾）。A 里的 T6.1 是我上一轮引入的缺陷，
应当立刻修掉，不该带着一个已知会 500 的接口继续往前走。

## 六、维持不变的判断

- 外部依赖项仍不做（DICOM、省平台、医保联调、音视频、血站、药械采购平台），
  平台侧接口已预留；
- 支付真实通道与模型辅诊的适配层骨架可写但无法验证，等对接窗口；
- 统一规则引擎与流程引擎维持"兼容并行"，不强推既有状态机迁移。
