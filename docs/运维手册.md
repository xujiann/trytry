# 县域医共体信息化平台 运维手册（V1.0）

> 适用对象：平台运维/信息科人员。对应第四阶段试点准备（M6）。
> 平台构成：FastAPI 单体应用（`server/app/`）+ PostgreSQL（生产）/SQLite（开发）
> + 可选 Redis（多实例会话状态）+ 内置静态前端（管理端 `/`、居民端 `/m`）。

---

## 一、部署

### 1.1 docker-compose（推荐，含 PostgreSQL）

```bash
# 仓库根目录
export MEDPLAT_SECRET="$(openssl rand -hex 32)"     # 必改
export MEDPLAT_ADMIN_PASSWORD="强口令"               # 必改
docker compose up -d                                 # app(8000) + postgres16（命名卷持久化）
cd server && alembic upgrade heads                    # 结构迁移（连接串与应用一致）
# 注意是 heads（复数）：慢专病子系统自成一条迁移分支，与主平台并行推进，
# 单数 head 在两条分支都有新迁移时会报 "Multiple head revisions are present"
curl -s http://127.0.0.1:8000/api/health             # 验证 {"status":"ok","database":"ok"}
```

compose 内置：应用容器依赖 db 健康检查后启动、`restart: unless-stopped`、
数据卷 `medplat-pgdata`。

### 1.2 Render（演示环境）

`render.yaml` 已声明 Docker 运行时（`server/Dockerfile`），推送分支即自动部署；
`MEDPLAT_SEED_DEMO=1` 时启动脚本（`server/start.sh`）等健康检查通过后自动灌入演示数据。
**生产切勿开启 SEED_DEMO**，且必须在 Render 控制台配置 `MEDPLAT_SECRET`、
`MEDPLAT_ADMIN_PASSWORD` 与 `MEDPLAT_ENVIRONMENT=prod`。

### 1.3 裸机部署

```bash
cd server
pip install -r requirements.txt
export MEDPLAT_DATABASE_URL="postgresql+psycopg2://user:pass@host:5432/medplat"
export MEDPLAT_ENVIRONMENT=prod MEDPLAT_SECRET=... MEDPLAT_ADMIN_PASSWORD=...
alembic upgrade heads                                  # ① 先迁移
uvicorn app.main:app --host 0.0.0.0 --port 8000       # ② 后启动
```

systemd 单元示例：

```ini
[Service]
WorkingDirectory=/opt/medplat/server
EnvironmentFile=/opt/medplat/medplat.env
ExecStartPre=/usr/bin/env alembic upgrade heads
ExecStart=/usr/bin/env uvicorn app.main:app --host 0.0.0.0 --port 8000
Restart=always
```

对外发布须经反向代理（nginx/caddy）终结 TLS（≥1.2），并透传
`X-Request-ID`（应用会生成/回显该头用于问题追踪）。

### 1.4 部署顺序注意（create_all 与 Alembic 双轨）

应用启动时会执行 `Base.metadata.create_all`（开发便利）并种子化基础数据
（admin 账号、编码字典、绩效指标目录、法定传染病目录、DRG 分组目录）。
**生产环境必须固化"先 `alembic upgrade heads`、后启动应用"的顺序**：
若先启动应用（create_all 建了全部表）再执行迁移，`alembic upgrade` 会因
表已存在而失败——此时用 `alembic stamp head` 将版本标记对齐后再继续。

### 1.5 PostgreSQL / Redis 启用步骤（实操）

> compose 部署已内置 `db`(postgres:16) 与 `redis`(redis:7, AOF 持久化) 服务并注入对应
> 环境变量，`docker compose up -d` 即全套启用；以下为**存量 SQLite 部署切换**或
> **自管 PG/Redis** 的实操步骤。engine 参数与 Redis 后端选择均有自动化测试兜底
> （`tests/test_config_matrix.py`，不依赖真实 PG/Redis）。

**A. 启用 PostgreSQL（SQLite → PG 切换）**

```bash
# 1) 建库与账号（PG 侧）
sudo -u postgres psql -c "CREATE USER medplat WITH PASSWORD '强密码';"
sudo -u postgres psql -c "CREATE DATABASE medplat OWNER medplat ENCODING 'UTF8';"

# 2) 应用侧设置连接串（psycopg2-binary 已在 requirements，无需新增依赖）
export MEDPLAT_DATABASE_URL="postgresql+psycopg2://medplat:强密码@pg主机:5432/medplat"

# 3) 建表：先迁移后启动（1.4 的顺序纪律）
cd server && python -m alembic upgrade heads

# 4) 存量数据搬迁（可选）：用平台自带工具从旧库导出 CSV 后导入
python scripts/import_legacy.py patients 导出的患者.csv        # 患者/机构/慢病/员工
python scripts/import_dictionary.py diagnosis icd10全量.csv     # 标准字典全量

# 5) 启动应用并验证
uvicorn app.main:app --host 0.0.0.0 --port 8000
curl -s localhost:8000/api/health   # 状态 ok 即切换完成
```

验证点：启动日志无 `sqlite` 字样；`psql -c "\dt"` 可见全部业务表；
登录/建档/开单冒烟一遍。回退方案：连接串改回 SQLite 文件即回退（数据不同步）。

**B. 启用 Redis（多实例/多 worker 前置条件）**

```bash
# 1) 部署 Redis（生产建议开启 AOF 与密码）
docker run -d --name medplat-redis -p 6379:6379 \
  redis:7 redis-server --appendonly yes --requirepass '强密码'

# 2) 应用侧设置（redis 客户端已在 requirements）
export MEDPLAT_REDIS_URL="redis://:强密码@redis主机:6379/0"

# 3) 重启全部应用实例（半配状态最危险：部分实例内存态、部分 Redis 态）
```

验证点：任一实例登出后，另一实例携同一令牌访问应返回 401（黑名单跨实例）；
连续输错密码达阈值后，换实例登录同样被锁定。未配置 `MEDPLAT_REDIS_URL` 时
自动回落进程内存实现（仅单实例可用）。

## 二、环境变量全表（与 `server/app/config.py` 逐字段对齐）

### 2.1 核心

| 变量 | 默认值 | 说明 |
|---|---|---|
| `MEDPLAT_DATABASE_URL` | `sqlite:///./medplat.db` | 数据库连接串；生产用 `postgresql+psycopg2://...`。Alembic 与备份脚本共用 |
| `MEDPLAT_CRYPTO_SUITE` | `general` | 密码套件：`general`=通用算法（PBKDF2/HMAC-SHA256），`sm`=国密（SM3 迭代/HMAC-SM3）。做成配置项而非代码分支——不假定每个县都已上国密 |
| `MEDPLAT_SECRET` | `dev-secret-change-in-production` | JWT 签名密钥（同时用于审计哈希链与归档 MAC）。**prod 下弱值/占位符拒绝启动**（长度≥32 + 字符多样性 + 占位符词表三重校验）；轮换步骤见第九节 |
| `MEDPLAT_SECRET_PREVIOUS` | 空 | 密钥轮换宽限期的**旧密钥**：设置后仅用于**验证**既有令牌/审计链/动态码，新签发一律用当前 `MEDPLAT_SECRET`。轮换完成后清空（见第九节） |
| `MEDPLAT_ADMIN_PASSWORD` | `admin123` | 首次启动创建 admin 账号的初始口令。**prod 下弱值拒绝启动**（长度≥12 等强校验）；仅在 admin 用户不存在时生效 |
| `MEDPLAT_ENV` / `MEDPLAT_ENVIRONMENT` | `dev` | 环境标识，二者任一为 `prod` 即按生产处理（触发凭据强校验、停用 create_all） |
| `MEDPLAT_TOKEN_TTL_SECONDS` | `28800`（8h） | 业务端 JWT 有效期（秒） |
| `MEDPLAT_UPLOAD_DIR` | `uploads`（即 server/uploads/） | 附件本地存储目录；归档任务的输出也落在其下 `archives/` 子目录（见第十一节）。compose 已挂载命名卷至 `/data/uploads`，多实例需共享存储（NFS 等） |

## 三、Alembic 迁移操作

```bash
cd server                                  # alembic.ini 所在目录
alembic current                            # 查看当前版本
alembic history                            # 查看迁移链（基线 c1627502ad43 → head）
alembic upgrade heads                       # 升级到最新（发版标准动作，先于应用启动）
alembic downgrade -1                       # 回退一个版本（回滚发版时配合旧代码使用）
alembic revision --autogenerate -m "描述"  # 开发新增迁移（须人工复核生成脚本）
alembic stamp head                         # 仅对齐版本标记（处理 create_all 先行的存量库）
```

规程要求：
1. 每次发版流程 = 备份 → `alembic upgrade heads` → 部署新代码 → 健康检查；
2. 回滚流程 = 部署旧代码 → `alembic downgrade <目标版本>`（含数据迁移的版本回退前先评估数据损失）；
3. 迁移曾人工验证 upgrade→downgrade→re-upgrade 三段回路；重大变更前在同构环境演练。

## 四、备份与恢复

备份脚本位于 `server/scripts/`：`backup.sh`（全量备份）、`restore.sh`（恢复）、
`restore_drill.sh`（不碰生产数据的恢复演练）。平台状态分三处、**按同一时点一起备**：
数据库、附件目录（`MEDPLAT_UPLOAD_DIR`，含归档文件）、平台密钥指纹
（密钥本身**不打进备份包**，只记 SHA-256 指纹，恢复时比对告警）。

### 备份

```bash
cd server
sh scripts/backup.sh /data/backups
# 读 MEDPLAT_DATABASE_URL：PG 走 pg_dump -Fc，SQLite 走在线备份 API；
# 连同 uploads/ 与密钥指纹打成 medplat-backup-<UTC时间戳>.tar.gz + .sha256
# 建议 crontab（每日全量）：0 2 * * * cd /opt/medplat/server && sh scripts/backup.sh /data/backups
```

**当前形态如实说明**：`backup.sh` 提供的是**每日全量 pg_dump（RPO≈24 小时）**；
对 RPO 有更高要求的县走下面的 WAL/PITR 路线。备份目录无自动清理，超期文件由
运维按留存策略自行删除。

### WAL 归档与 PITR（RPO≤15min 路线）

生产 PG 用 pgBackRest 做物理备份 + WAL 连续归档，脚本与样例已备
（`server/scripts/`）：

```bash
# 1) 一次性接线：按样例写配置 + postgresql.conf 开归档（含 archive_timeout 兜 RPO）
cp server/scripts/pgbackrest.conf.example /etc/pgbackrest/pgbackrest.conf   # 按机器改路径/口令
# postgresql.conf: archive_mode=on / archive_command='pgbackrest --stanza=medplat archive-push %p'
#                  archive_timeout=60（低写入时段的 RPO 兜底）
sudo -u postgres pgbackrest --stanza=medplat stanza-create
sh server/scripts/backup_pg_pitr.sh check      # 归档链路必须先 check 通过

# 2) 日常备份（crontab）：周日全量 + 每日差异；RPO 由 WAL 归档保证，不靠备份频率
0 1 * * 0  sh server/scripts/backup_pg_pitr.sh full
0 1 * * 1-6 sh server/scripts/backup_pg_pitr.sh diff

# 3) 恢复演练：从最近备份恢复到临时实例，跑 alembic current + 核心表健康查询
sh server/scripts/restore_drill_pg.sh          # 无 PG 环境自动转 dry-run 打印步骤
```

**如实说明达标口径**：脚本与配置样例已备、CI 钉住语法与 dry-run，但
**须在真实 PG 上跑通 `check`/`backup`/`restore_drill_pg.sh` 全链并实测归档延迟
后，RPO≤15min 才算达标**——在此之前本节只是路线，不是能力。演练频率建议：
`restore_drill_pg.sh` 每季度至少一次（与上文恢复演练要求同频），其中每半年
至少一次做**定点恢复**（`--type=time`）验证 PITR 语义；演练结果记入台账。
定时任务（含归档类）失败会经 `MEDPLAT_ALERT_WEBHOOK_URL` 外发主动告警
（`app/alerting.py`，空=关闭；同类告警按 `MEDPLAT_ALERT_COOLDOWN_SECONDS` 冷却）；
本节的 pgBackRest 备份跑在 crontab 里，其失败告警由 cron 邮件/监控自行承接。

### 恢复与演练

```bash
cd server
sh scripts/restore.sh /data/backups/medplat-backup-20260811T020000Z.tar.gz
# 先校验包完整性(.sha256)与密钥指纹：指纹不一致会停下来问（--force 跳过）——
```

## 五、日志与审计归档

- **访问日志**：logger `medplat.access` 输出 JSON（ts/request_id/method/path/status/duration_ms）。
  容器部署走 stdout，由 docker/journald 收集；裸机/等保留存场景设 `MEDPLAT_LOG_FILE`
  同时落轮转文件（见第十节）。排查问题用响应头 `X-Request-ID` 关联。
  访问日志不含请求体，不会落身份证号/电话等敏感字段。
- **审计日志**：HTTP 中间件对全部 `/api/` 写操作（POST/PATCH/PUT/DELETE，登录除外）
  落库 `audit_logs`（用户/方法/路径/状态码，含失败与 500）。
  - 在线查询：`GET /api/audit?limit=&offset=&username=`（admin，X-Total-Count 分页）；
  - **自动归档**：`audit_archive` 定时任务可按保留期自动"导出+截断"（默认关，
    见第十一节，含哈希链断点锚点说明）；下面的手工导出接口适合**不删库内数据**的
    增量外拷；
  - **按月归档**：`GET /api/audit/export`（admin）**流式输出 NDJSON**（每行一条），
    按主键游标分批读取，不会把全表读进内存：
    - `since_id=<上次归档的 last_id>` 增量导出，`until=YYYY-MM-DD` 限定日期上界；
    - 响应末行是 meta 行（`total` / `since_id` / `last_id`），据此校验连续性并
      记录下次的游标；
    - 落归档存储后可清理历史分区；归档文件建议附哈希做防篡改校验。

    ```bash
    # 归档 2026-08 之前的审计日志，并记录游标供下次增量使用
    curl -sH "Authorization: Bearer $TOKEN" \
      "http://127.0.0.1:8000/api/audit/export?since_id=0&until=2026-08-01" \
      -o audit_202607.ndjson
    tail -1 audit_202607.ndjson          # {"_meta":true,"total":...,"last_id":...}
    sha256sum audit_202607.ndjson > audit_202607.sha256
    ```
- **登录安全事件**：登录失败/锁定不落审计表，由访问日志（`/api/auth/login` 的 401/423）承担。

## 六、监控要点

| 监控项 | 接口/口径 | 告警建议 |
|---|---|---|
| 定时任务失败 | `GET /api/jobs/runs?status=failed`（限管理层） | 出现即告警；`/api/jobs` 的 `last_status` 也可轮询 |
| 定时任务停摆 | `GET /api/jobs` 的 `next_run_at` 长期不推进 | 超过间隔 3 倍未执行即告警（调度循环异常或锁未释放） |
| 存活与数据库连通 | `GET /api/health`（无需鉴权）返回 `status`/`database` | 非 `ok` 或超时 >5s 告警；建议 30s 间隔探测 |
| 集成交换失败率 | `GET /api/integration/exchange-logs`（含总/分通道 `failure_rate_pct`） | 失败率 >5% 或单通道连续失败告警 |
| 业务预警面板 | `GET /api/metrics/alerts`（危急值/慢病超期/医废滞留/缺药） | 危急值未确认数 >0 持续 30 分钟升级 |
| 危急值催办 | `GET /api/exams/critical/unacknowledged` | 有超时未确认项即通知质控 |
| 传染病迟报 | `GET /api/infectious/late-reports` | 出现甲类迟报立即上报 |
| WS 推送通道 | `/ws/alerts` 连接数（应用日志） | 长期为 0 说明前端推送不可用 |
| 资源层 | 容器 CPU/内存、PostgreSQL 连接数、磁盘（含备份盘） | 常规阈值 |
| 运行环境概览 | `GET /api/monitor/overview`（限管理员）：库/Redis 连通与延迟、调度器到点未跑清单 | `database.connected` 为假、`overdue_jobs` 非空即告警 |
| 接口性能与错误 | `GET /api/monitor/api-stats`：分模块调用量与平均耗时、慢请求（≥1s）与错误样本 | 某模块平均耗时突破 1s，或 5xx 样本连续出现 |
| 集群节点存活 | `GET /api/monitor/nodes`：Redis 心跳，90 秒内有心跳视为存活 | 实例数少于预期副本数即告警 |
| 写操作异常率 | `GET /api/audit/stats?days=7` 的 `failed_ratio_pct` 与 `top_failed_paths` | 失败率突增，或某路径失败集中（多为权限配错或前端传参变更） |

### 监控数据的两个口径（重要）

`/api/monitor/api-stats` 是**进程内计数**：随进程启停清零，多实例部署下每个
实例只看得见自己。响应里的 `scope` 字段会写明这一点。用它看性能与错误，
**不要用它统计业务量**——扩容后每台的数字都会掉，看起来像流量腰斩。

`/api/audit/stats` 是**落库的写操作留痕**：跨实例、可追溯、按保留期归档。
业务量与合规追查以它为准。

`/api/monitor/nodes` 在未配置 Redis 时返回 `scope: "unknown"` 而不是"1 个节点"。
这是刻意的：单机部署与"多实例但漏配 Redis"看起来会一模一样，而后者意味着
登出黑名单、防爆破锁定、限流、任务抢锁全部只在单机生效——必须能被区分出来。

压测基线采样：`server/scripts/loadtest.py`（见 README"压测基线"章节），
每次扩容/迁移后重跑并留档对比。

## 七、故障排查 FAQ

| 现象 | 原因与处置 |
|---|---|
| 启动即退出，日志"生产环境配置不安全，拒绝启动" | `prod` 下 `MEDPLAT_SECRET`/`MEDPLAT_ADMIN_PASSWORD` 仍为默认值（H4 强校验）。设置强随机值后重启 |
| `alembic upgrade` 报"表已存在" | 应用先于迁移启动过（create_all 建表）。`alembic stamp head` 对齐版本后继续（见 1.4） |
| 登录返回 423 | 防爆破锁定（连续失败 5 次锁 10 分钟）。等待解锁或管理员核实是否撞库（结合访问日志 IP） |
| 用户批量 401"密码已修改，令牌失效" | 该用户改过密（M-4 改密吊销既有令牌）或运维轮换了 `MEDPLAT_SECRET`。重新登录即可 |
| 多实例下登出后令牌仍可用/锁定不生效 | 未配置 `MEDPLAT_REDIS_URL`，会话状态仅在单进程内存。配置 Redis 后重启全部实例 |
| 前端收不到危急值/缺药推送 | ① WS 连接未建立（代理未放行 `/ws/alerts` 的 Upgrade）；② 多实例未做会话粘滞，广播发生在另一实例（见第八节）；③ 定向推送仅达申请机构与 admin/director，属预期 |
| 居民端 429"核验尝试过于频繁" | portal 双因子核验限速（M-3）触发。确认是否为撞库；正常居民等 10 分钟后重试 |
| `/api/health` 返回 `degraded` | 数据库不可达。检查 db 容器/网络/连接数上限 |
| 演示数据混入生产 | `MEDPLAT_SEED_DEMO` 未置 0。立即置 0 重启，并从备份评估清理 |
| 时间类预警口径异常 | 预警接口以服务端日期为准（L-2）；核对应用服务器时区/NTP。`today` 参数仅限测试排查 |

## 八、多实例部署注意事项

1. **数据库**：多实例必须 PostgreSQL（SQLite 文件锁不支持多写入方）。
2. **会话状态（state_store）**：令牌黑名单、登录防爆破、**滑动窗口限速**（居民端
   验证码下发配额）默认为进程内存实现——多实例/多 worker（含 `uvicorn --workers N`）
   下**必须**配置 `MEDPLAT_REDIS_URL`，否则登出与锁定只在单实例生效，
   且验证码配额被放大 N 倍（N 个实例各自计数，短信轰炸成本降到 1/N）。
   Redis 建议开启持久化（AOF）与密码认证。
2.1 **定时任务执行锁**：调度器用 Redis `SET NX EX` 保证同一任务在多实例下只跑
   一次。未配置 Redis 时退化为单实例语义——多实例部署会**每个实例各跑一遍**，
   扫描类任务只是重复推送预警，但清理类任务（过期验证码）会并发删同一批数据。
   因此多实例必须配 Redis。
3. **WebSocket 广播**：配置 `MEDPLAT_REDIS_URL` 后，`ws.py` 的广播自动经
   Redis Pub/Sub 跨进程/跨实例分发（发布端 publish，各 worker 的订阅线程转发
   给本进程在线连接），多 worker/多实例可直接水平扩展。**未配置 Redis 时保持
   进程内语义**：危急值/缺药推送只送达与写请求同一进程的在线连接——单实例
   单 worker 不受影响，多 worker 上线必须配 Redis（与本节第 2 条同一个开关）。
4. **迁移执行**：多实例发版时由**单一节点**执行 `alembic upgrade heads`，其余节点仅部署代码。
   所有实例置 `MEDPLAT_MIGRATE_ON_START=0`，避免多实例并发跑迁移。
5. **反向代理**：需放行 WebSocket Upgrade 头；健康检查探 `/api/health`；
   建议按实例透传/记录 `X-Request-ID` 以便跨实例追踪。

## 九、密钥轮换

`MEDPLAT_SECRET` 同时用于 JWT 签名、审计哈希链与归档 MAC，直接换值会让全部在线
令牌即刻失效、且旧审计段验不过。`MEDPLAT_SECRET_PREVIOUS` 提供**宽限期**语义：
旧密钥仅用于**验证**既有令牌/审计链/动态码，新签发一律用当前密钥。

轮换步骤：

1. 设 `MEDPLAT_SECRET_PREVIOUS=<旧密钥值>`；
2. 换 `MEDPLAT_SECRET=<新密钥>`（生成：`python -c 'import secrets;print(secrets.token_hex(32))'`）；
3. 重启全部实例（多实例要一起换，半配状态下各实例签发/验证不一致）；
4. 宽限期（建议 ≥ 令牌最长 TTL，即业务端 8h 与居民端 7 天取大者）过后，
   **清空** `MEDPLAT_SECRET_PREVIOUS` 并再次重启。

宽限期内：旧令牌仍有效（用户无感）、审计链**跨新旧两段可验**。清空 PREVIOUS 后，
旧密钥签的令牌全部失效（等效强制重登）；旧密钥时期写入的审计链段仍在库里，
校验它需要临时再设 PREVIOUS。**旧密钥值轮换后按泄露处理**：不要留在 shell
历史/编排文件明文里。

## 十、日志留存（等保 6 个月）

等保要求日志留存 ≥ 6 个月。落地方式按部署形态二选一：

- **容器部署**：stdout 交给 docker/journald/集中日志系统收集，由收集端负责留存时长；
- **裸机/无集中日志**：设 `MEDPLAT_LOG_FILE=/var/log/medplat/access.log`，
  请求日志在 stdout 之外**同时**写轮转文件（目录不存在自动创建）：
  单文件超过 `MEDPLAT_LOG_ROTATE_MAX_MB`（默认 64MB）即轮转，
  保留 `MEDPLAT_LOG_ROTATE_BACKUPS`（默认 14）份历史。

**磁盘估算**：默认配置封顶 ≈ 64MB × (14+1) ≈ 1GB。单条 JSON 日志约 200 字节，
64MB ≈ 33 万条请求；日均 10 万请求的县约 3 天写满一个文件，14 份历史 ≈ 45 天——
**默认参数达不到 6 个月**。要靠本机文件满足等保，按请求量放大参数（如
`MEDPLAT_LOG_ROTATE_MAX_MB=128`、`MEDPLAT_LOG_ROTATE_BACKUPS=60`，
封顶约 7.6GB、约 7 个月），或用 logrotate/定时任务把轮转出的历史文件
压缩转储到归档存储再计 6 个月。

审计（audit_logs）与调阅留痕（access_logs）落库而非落文件，其留存见第十一节。

## 十一、运行数据保留与归档

三个内置定时任务（`server/app/jobs.py`，每日一跑，可在 `/api/jobs` 调整/手动触发）
控制三张无界增长的运行数据表。归档文件落 `MEDPLAT_UPLOAD_DIR` 下的 `archives/`
子目录：每次归档产出一个 `<表名>_<时间戳>_<起始id>_<随机后缀>.ndjson.gz`
（随机后缀 + 独占创建：任务锁失效双跑时撞名即失败，绝不覆盖已有归档），并向同目录
`manifest.jsonl` 追加一行账目（文件名、行数、时间范围、HMAC-SHA256 校验值，
密钥为 `MEDPLAT_SECRET`；`gunzip` 后对 NDJSON 字节流复算即可核验）。
归档分批执行（每批 1000 行）防大事务。**archives/ 目录随附件目录一起进备份**（第四节）。

| 任务 | 表 | 开关 | 语义 |
|---|---|---|---|
| `jobrun_cleanup` | job_runs | `MEDPLAT_JOBRUN_RETENTION_DAYS`（默认 90） | 超期**直接删除**（运行留痕无合规义务，不归档）；0 或负值=跳过 |
| `access_log_archive` | access_logs | `MEDPLAT_ACCESS_LOG_ARCHIVE_DAYS`（默认 0=关） | 超期行**先导出归档、后删除**；留痕是《个保法》义务，留多久是运维决策 |
| `audit_archive` | audit_logs | `MEDPLAT_AUDIT_LOG_ARCHIVE_DAYS`（默认 0=关） | 同上，但涉及**哈希链截断**（见下） |

**审计归档的断点锚点**：audit_logs 带防篡改哈希链，归档删除最旧段后，库内剩余
首条的 `prev_hash` 指向已删除的记录——`GET /api/audit/verify` 会在**截断点报一处
已知断点**（`partial_segment=true`，只能证明剩余段内部自洽）。这不是篡改，以归档
manifest 的锚点续接：manifest 里额外记录了归档段的 `first_prev_hash` /
`first_entry_hash` / `last_entry_hash`——核验时比对**库内剩余首条的 `prev_hash` ==
manifest 的 `last_entry_hash`** 即证明链在截断点续接无误；归档文件内部的链
可独立复算。

**开启建议**：
- `jobrun_cleanup` 默认即启用（90 天），一般无需动；
- `access_log_archive` 建议在留痕表过百万行、查询变慢后开启，天数 ≥ 留痕留存
  义务期（建议 ≥ 180）；
- `audit_archive` **默认关闭，开启是运维决策**：等保对审计留存有最低时限要求
  （6 个月），截断前先确认归档存储（archives/ 所在盘 + 备份）已就位，且天数
  **不得小于 180**。开启前建议先跑一次 `/api/audit/verify` 留基线。

## 十二、PII 列加密启用流程（阶段十四 E3）

身份证号/手机号三列默认仍为明文（开关关=行为零变化）。启用步骤：

1. 备份数据库（第四节）；
2. `python scripts/pii_encrypt_backfill.py --dry-run` 预览，再去掉 dry-run 正式回填
   （分批提交、`pii1$` 前缀幂等跳过、解密回读一致才落盘）；
3. 置 `MEDPLAT_PII_ENCRYPTION_ENABLED=true` 重启；
4. 验证：患者检索按证件号**全值**可命中（密文态不支持模糊匹配，属既定降级）。

密钥轮换注意：解密路径有 `MEDPLAT_SECRET_PREVIOUS` 宽限回退，但**检索索引列
没有多口径**——换密钥后须立即 `pii_encrypt_backfill.py --old-secret 旧值` 重加密，
否则索引检索落空。防线边界：防拖库/备份泄露，不防持有应用密钥的攻击者。

## 十四、静默解绑的人工排查（旧版 `d3e4f5a6b7c8` 遗留）

**背景。** 迁移 `d3e4f5a6b7c8`（居民账户绑定档案唯一索引）的第一版为了给
`resident_accounts.patient_id` 建部分唯一索引，在建索引前执行过

```sql
UPDATE resident_accounts SET patient_id = NULL
 WHERE patient_id IS NOT NULL
   AND id NOT IN (SELECT MIN(id) FROM resident_accounts
                   WHERE patient_id IS NOT NULL GROUP BY patient_id);
```

即"一份档案挂了多个账户时，只留 id 最小的那个，其余静默解绑"。该迁移已按
CLAUDE.md §4 整改为不阻塞路径（探到冲突只跳过建索引 + ERROR 日志，不改数据），
但**在整改之前跑过它的库，解绑已经发生**。

### 这件事恢复不了，先认下来

`patient_id` 是这条绑定关系的唯一载体，置空即信息丢失。平台没有为绑定关系留影子表；
解绑走的是迁移里的裸 SQL，不经过应用层，`audit_logs` / `access_logs` 里一条记录都没有。
**所以"谁在什么时候被解绑、原来绑的是哪份档案"无法从库里还原**，只能靠下面的方法
缩小嫌疑面，再请居民重新实名绑定。别向业务方承诺能自动恢复。

而且被留下的那个未必是本人：一档多户最常见的成因是**家人替老人注册**，本人的账户
往往是后建的、id 更大的那个——恰恰是被解绑掉的那个。排查时不要默认"留下的就是对的"。

### 一、嫌疑记录怎么找

升级到平台链 `a1c3e5b7d9f2` 时，迁移会把嫌疑条数打进日志（WARNING，不打手机号）。
明细自己查：

```sql
-- 嫌疑面 A（最强信号）：账户未绑定，却存在一份手机号与它相同的档案。
-- 正常流程下这种账户早该被 _autobind_by_phone 自动绑上，现在没绑，多半就是被解绑的。
-- 明文态比 phone；PII 加密开启后明文列是密文，改比 phone_idx（两条都写上，
-- 回填分批推进时同一个库里两态的行会并存，只比一边会漏）。
SELECT ra.id AS account_id, ra.nickname, ra.status,
       ra.created_at, ra.last_login_at, p.id AS patient_id, p.name
  FROM resident_accounts ra
  JOIN patients p
    ON (ra.phone     IS NOT NULL AND ra.phone     <> '' AND p.phone     = ra.phone)
    OR (ra.phone_idx IS NOT NULL AND ra.phone_idx <> '' AND p.phone_idx = ra.phone_idx)
 WHERE ra.patient_id IS NULL
 ORDER BY ra.created_at;

-- 嫌疑面 B：账户未绑定本人档案，却在代管家人——真·新账户很少先代管后绑本人。
SELECT ra.id AS account_id, ra.nickname, COUNT(fm.id) AS 代管人数
  FROM resident_accounts ra
  JOIN resident_family_members fm ON fm.account_id = ra.id
 WHERE ra.patient_id IS NULL
 GROUP BY ra.id, ra.nickname
 ORDER BY 代管人数 DESC;

-- 嫌疑面 C：账户未绑定，但在解绑发生之前就已经登录过——说明它当时是个"能看档案"的
-- 活跃账户。把 <迁移执行时间> 换成本库跑 d3e4f5a6b7c8 的时刻（见发布记录/迁移日志）。
SELECT id AS account_id, nickname, created_at, last_login_at
  FROM resident_accounts
 WHERE patient_id IS NULL AND last_login_at IS NOT NULL
   AND last_login_at < '<迁移执行时间>'
 ORDER BY last_login_at DESC;
```

三张单子取并集就是要人工核实的名单。A 的信噪比最高，B、C 用来兜住"换过手机号"
和"用微信登录、账户上没手机号"的那部分。

### 二、核实与恢复绑定

1. 逐条比对账户手机号 / 昵称与档案的 `name`、`phone`，判断是否同一人；拿不准的
   **不要**替居民决定，走客服回访确认。
2. 确认后请居民在居民端重新实名绑定（走正常的 `bind_realname`，会过一遍实名校验
   并留下应用层痕迹）。**不要用 SQL 直接回写 `patient_id`**——绕过应用层就等于
   再犯一次同样的错，且新的唯一索引会在冲突时直接报错，比 SQL 更早拦住。
3. 家人代管的情形不要绑成本人：走 `resident_family_members` 建代管关系。

### 三、顺带说明：`f7a8b9c0d1e2` 的 downgrade 有损

`f7a8b9c0d1e2` 把 `appointment_blacklist` 泛化成了 `service_blacklists`（upgrade 侧
整表搬迁，行一条不少）。但它的 **downgrade 只搬 `domain = 'appointment'` 的行**，
其余 domain 的黑名单会随 `service_blacklists` 一起消失。若要回退过这条迁移，先导出：

```sql
SELECT * FROM service_blacklists WHERE domain <> 'appointment';
```

## 十五、慢专病唯一键冲突的处置（迁移 `e1a2b3c4d5e9` 跳过的表）

**背景。** 慢专病 18 张表的唯一键此前只写在模型注解里，数据库上是普通索引——
同一个村医能有两个积分账户（实测余额 10 / 99），入账记一个、兑换扣另一个。
迁移 `e1a2b3c4d5e9` 把唯一性下沉到数据库，但按平台通则（CLAUDE.md §4）
**不替人删存量重复**：探到重复就跳过那张表的唯一索引，把冲突逐行记进
`spd_dedup_reports` 并打一条点名到表 / 键值 / 行 id 的 ERROR 日志。

**升级后必查。** 升级日志里出现"未建成唯一索引"就说明有存量冲突待处置：

```sql
SELECT table_name, key_column, key_value, kept_id, removed_id, note
  FROM spd_dedup_reports WHERE strategy = 'pending';
```

**处置。** 仓库自带脚本，先看再做：

```bash
cd server
python scripts/spd_dedup.py                 # 只报告：哪些表有冲突、打算怎么并（不改数据）
python scripts/spd_dedup.py --json          # 同上，JSON 输出，可挂巡检；有冲突时退出码 1
python scripts/spd_dedup.py --apply         # 归并 + 补建迁移跳过的唯一索引
python scripts/spd_dedup.py --apply --table spd_point_accounts   # 只处置一张表
```

归并口径：**积分账户**按 `balance`/`earned`/`used` 相加并成一条（两个账户都是这个人的，
相加是唯一不丢积分的并法）；**其余 17 张**保留 id 最小的那条，其余整行 JSON 存进台账后
移除，指向它们的外键改指到保留行。处置完 `strategy` 从 `pending` 变成
`merge` / `keep_earliest`，`removed_row` 里是被并掉那行的完整字段——
事后要核对"两份配置差在哪"就查它。

**不用脚本、手工处置的**：按台账逐条改完之后 DBA 自己补建即可，例如

```sql
CREATE UNIQUE INDEX ix_spd_point_accounts_user_id ON spd_point_accounts (user_id);
```

索引名与目标列见迁移 `e1a2b3c4d5e9` 的 `TARGETS`。**注意**：alembic 不会重跑已记录的
revision，所以处置完再跑多少次 `alembic upgrade heads` 也不会回头补建——补建这一步
要么交给脚本，要么手工执行。
