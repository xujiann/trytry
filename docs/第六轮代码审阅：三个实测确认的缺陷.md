## 〇、这一轮与上一轮的区别

`docs/第五轮代码审阅与下一步开发计划.md` 那一轮**偏架构**——靠 grep 扫模式，

## 一、缺陷（全部实测确认）

### D-1 手术排班两段事务，中断即进入不可恢复的卡死状态

**位置**：`app/routers/surgery.py:236-252`

排班记录先 `db.commit()` 落库，之后才设 `request.status = "scheduled"` 并发站内
消息，再第二次 `db.commit()`。两次提交之间任何异常（消息投递失败、进程被杀、
数据库瞬断）都会留下不一致。

**实测**：让第二段抛异常后查库——

```
排班记录已落库: True | 申请状态: approved      ← 该是 scheduled
重试排班: 409 {'detail': '该手术已排班或时段被并发占用'}
```

后果是**死结**：申请状态停在 `approved`，重排被唯一约束挡回 409，而填术中记录
要求状态为 `scheduled`。这台手术既排不了班也做不了记录，**唯一出路是改数据库**。

**修法**：排班记录、状态变更、消息投递合到一个事务里，只在末尾 commit 一次。
`notify_*` 本来就设计成"只 add 不 commit"正是为了这个，这里没用对。

### D-2 并发建全域基金池会建出两个，结余可能被分两次

**位置**：`app/routers/fund.py:115-137`

`fund_pools` 的唯一约束是 `(year, insurance_type, org_group_id)`。全域池的
`org_group_id` 为 NULL，而 SQL 里 `NULL != NULL`——**唯一约束对全域池根本不生效**。
阶段七我意识到了这点，加了应用层查重，但那是 check-then-act，中间有竞态窗口。

**实测**：6 个线程并发建同一个全域池——

```
响应码: [201, 201, 409, 409, 409, 409]
实际建出的池子数: 2 （应为 1）
```

后果直接管钱：两个池各自预付、各自清算、各自分配结余，同一笔钱会被分两次。

**修法**：加**部分唯一索引**（SQLite 3.8+ 与 PostgreSQL 都支持）：

```sql
CREATE UNIQUE INDEX uq_fund_pool_global ON fund_pools(year, insurance_type)
WHERE org_group_id IS NULL;
```

Alembic 用 `op.create_index(..., sqlite_where=..., postgresql_where=...)`。
应用层查重保留（给出友好提示），但**兜底必须在数据库**。

### D-3 假日期能入库，该记录随后从统计里静默消失

**位置**：全平台 22 处用 `pattern=r"^\d{4}-\d{2}-\d{2}$"` 校验日期的字段。

正则只管格式不管日历，`2026-02-31` 能过。入库之后，各处统计用 `strptime` 解析
失败就 `continue` 或返回 0。

**实测**：用 `2026-02-31` 建一条派驻——

```
建派驻: 201
台账里显示天数: 0
该机构是否出现在统计里: False      ← 整条记录从下沉指标里消失了
```

这直接违反了平台自己反复坚持的原则：**未采集/异常的数据要单独报出来，不能悄悄
丢掉**（DDD 未维护单列、职称等级未填单列、疗效未评价单列，都是这个原则）。
偏偏日期这里，一条记录无声无息地不见了。

**修法**：Pydantic 用 `datetime.date` 类型而不是带正则的 `str`，一次改掉 22 处。
它自带日历校验，`2026-02-31` 会在入口就被 422 挡下。落库仍存字符串的表
可在模型层转换，不必改表结构。

## 三、查过但确认没问题（免得下轮重复劳动）

- **前端 XSS**：扫了 `app.js`(5032 行) 与两个 H5 的全部 `innerHTML` 模板插值。
  初筛 288 处可疑，逐个核实后**全部安全**——`confirm()`/`prompt()`/URL 拼接不是
  HTML 汇聚点；`barChart()` 内部对 label 与 value 都调了 `esc()`；
  `PAGES` 注册表与定时任务名来自代码而非用户输入。**`esc()` 纪律在 5000 行里没破过。**
- **check-then-act 竞态**：除 D-2 的基金池外，其余"先查重再插入"的地方
  （患者建档、预约占号、专病入组、分组成员）都有数据库唯一约束兜底，
  且都正确捕获 `IntegrityError` 转 409。
- **写接口越权**：扫了所有 `db.get(...)` 后未校验归属的写接口，**0 处**。
  凡按 id 直取对象的，要么校验 `org_id`/`created_by`，要么有角色守卫。

## 四、建议的修复顺序

1. **D-1、D-2**——直接损坏数据，且修法明确、影响面小，应立即修。
   D-2 需要一次迁移（部分唯一索引），并补一个并发建池的回归用例。
2. **D-3**——影响面 22 处但改动机械（`str` + 正则 → `date`），一次做完。
   补一个"假日期被 422 挡下"的用例。
3. **P0-1 N+1、P0-2 统一时钟**——性能与隐患，随后。
4. **P1-1 补越权用例到 100%**——权限重构（阶段十一）的入场券，量最大，
   可以与上面并行推进。

前三项合起来约等于原计划里的"阶段九 代码健康度收口"，建议把 D-1/D-2/D-3
并入该阶段并提到最前。
