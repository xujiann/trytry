依据招标文件《三、服务内容及要求》十一个端共 **163 条**技术服务要求逐条建设，
本表是需求条目 → 实现落点的对照清单，供投标响应与验收核对使用。

- 后端接口统一前缀 `/api/spd`（居民端为 `/api/portal/spd`，走居民令牌 `scope=portal`）；
- 管理端页面见 `server/app/static/pages-spd.js`（左侧导航「全域慢专病」分组，11 个页面与 11 个端一一对应）；
- 移动端：居民端 `server/app/static/m/`（「慢专病」页签）、医生端 `server/app/static/m/doctor.html`（「慢专病」页签）；
- 领域模型 50 张表见 `server/app/models_spd.py`，迁移见 `alembic/versions/d1a2b3c4e5f6_*.py`；
- 用例见 `server/tests/test_spd_flow.py`（55 条）与 `server/tests/test_spd_portal.py`（15 条）。

## 贯穿全系统的三条口径

这三条决定了很多条目的实现方式，先说明，后面不再重复：

1. **慢病与专病并行运行、共用底座**（平台管理端 #21）。患者、机构、任务、随访、
   消息、考核是同一套；病种规则、路径、工作台、统计口径按 `program.category`
   （`chronic` / `specialty`）分别配置与统计，互不覆盖。
2. **筛出来 ≠ 管起来**。筛查（`spd_screenings`）→ 目标池（`spd_candidates`）→
   纳管档案（`spd_enrollments`）是三张表三个阶段，中间可停可退，
   所以"筛查人数"与"纳管人数"永远是两个数。
3. **任务只有一张表**（`spd_tasks`）。路径节点、随访、干预、评估、复诊、转诊、
   上报共用统一任务模型，"接收/分配/转派/催办/超时升级/批量处理/导出"因此只实现一次。

## 与既有模块的关系

| 既有模块 | 关系 |
|---|---|
| `/api/chronic` 慢病管理 | 保留。单病种随访分级台账（公卫口径），与 `spd_*` 并行运行，互不覆盖 |
| `/api/disease-programs` 专病管理 | 保留。院内单机构专病入组—路径—出组，`spd_*` 是其全域（跨县乡村、跨机构、跨端）升级形态 |
| `/api/followups` 随访中心 | 保留。慢病/出院/术后/妇幼四类随访任务；智能随访端（`spd_followup_*`）提供方案规则、问卷、呼叫与抽查质控等通用能力 |
| `/api/referrals` 双向转诊 | 保留。两点之间的一次转诊；慢专病逐级转诊（`spd_referral_cases`）是四环节链路，闭环口径不同，不合表 |
| `/api/performance`、`/api/metrics` | 保留。院级绩效与医共体监测指标；慢专病考核（`spd_indicators`/`spd_scores`）是病种维度的分级考核 |
