## 一、发现（按严重度）

### P0-1 `program_stats` 的 N+1，随入组数线性增长

`app/routers/disease_programs.py:275` 在循环里逐条调 `_completion(r, db)`，
每条入组各查一次 `DiseasePathRecord`。

**实测**：造 50 条入组，请求 `/api/disease-programs/{id}/stats`
→ **103 次 SQL**（2N+3），48.8ms。一个专病中心管到 500 例就是 1000+ 次查询。

这是阶段八我自己写的，当时只顾着口径正确，没看查询数。修法与 `analytics.py`
里已经用过的一样：一次取回全部路径记录，在内存里按 `enrollment_id` 分组。

### P0-2 时间函数四套并存，已经真炸过一次

| 位置 | 实现 | 时区 |
|---|---|---|
| `models.utcnow()` | `datetime.now(timezone.utc)` | aware |
| `scheduler._naive_utcnow()` | 同上 `.replace(tzinfo=None)` | naive |
| `portal._naive_utcnow()` | 与 scheduler 重复的第二份 | naive |
| 5 处路由内联 `datetime.utcnow()` / `datetime.now()` | 直接调用 | naive |

阶段二写 `/api/monitor/overview` 时就因为拿 aware 的 `utcnow()` 去比调度器写入的
naive `next_run_at`，直接 `TypeError`，靠全量测试才逮住。现在这个坑仍然张着口——
**同一张表的两列可能一列 aware 一列 naive**（`improvement_tasks.created_at` 走模型
默认是 aware，`completed_at` 在 `gapfill.py:861` 写的是 `datetime.utcnow()`）。

**验证边界（重要）**：我在 SQLite 上实测过，`DateTime`（未加 `timezone=True`）
读回来 tzinfo 一律为 `None`，所以**当前测试环境不会暴露这个问题**。
PostgreSQL 下 psycopg2 对 aware 值的处理与 SQLite 不同，我没有 PG 环境无法实测，
因此这条列为**隐患而非已确认故障**。但"四套时钟"本身已经害过一次，
不该等到生产上再发现第二次。

### P0-3 40 列用 `Float` 存金额

`amount`/`price`/`cost`/`balance`/`total` 类的列共 **40 个**用 `Float`。
浮点累加误差在阶段七已经露头——`test_fund.py` 里我不得不写
`abs(distributed_amount - 200000) < 1.0` 的容差断言才能通过。

这是**唯一一条我建议慎重评估、不要急着动**的：改 `Numeric` 要动 40 列 + 迁移 +
全部金额计算路径，而县域单县的金额量级下，误差目前落在"分"以下。
真要动，应当在接入真实医保结算之前一次做完，而不是零敲碎打。

### P1-1 越权用例只覆盖 64%，这是阶段十的硬前提

- 写接口路径 **259** 个，其中有对应 403 用例的 **168** 个 → **64%**（粗口径：
  同一测试块里出现该路径且出现 403 断言即算覆盖，会高估而非低估）；
- 装饰器上无角色守卫的写接口 **26** 个（其中相当一部分是居民端与 router 级
  统一守卫，需逐个甄别，不是全都有问题）。

阶段十要把 `require_roles` 换成查权限点，触及全部 550 个端点的鉴权路径。
**现有 643 项测试是这次重构唯一的安全网，而它现在有 36% 的写接口没有越权用例。**
先补网再动手，否则收不了口——这一条上一轮计划里就写了，至今没做。

### P1-2 `dispatch_stats` 全表进内存

`app/routers/staffing.py:218-221` 把 `Employee` 与 `Secondment` 全表拉进内存
再在 Python 里筛。实测 4 次查询、14.6ms（数据量小），量级上一个县几百条派驻，
**当前不构成性能问题**，但写法上是全表扫描，随年份累积会慢慢变差。
优先级低于 P0-1，但修法相同、成本很小，建议一并处理。

### P2-1 单文件过大

`app/static/app.js` **5032 行**、`app/models.py` **3264 行**、
`app/routers/portal.py` **1316 行**。功能都正确，测试也全绿，纯粹是可维护性——
新人改一处要在 5000 行里找。不影响交付，排在功能之后。

## 二、下一步开发计划

### 阶段九 代码健康度收口（新增，插在最前）

先修再走，理由：P0-1 是实测确认的性能缺陷，P1-1 是阶段十动不了手的前提。

1. **修 `program_stats` 的 N+1**——一次取回路径记录按 `enrollment_id` 分组；
   同时给 `dispatch_stats` 改成 SQL 侧过滤。加"查询数不随数据量增长"的回归用例
   （`test_analytics.py` 已有同类用例可照抄）。
2. **统一时钟**——全平台只留一个 `app/clock.py`，明确规定"落库一律 naive UTC"，
   删掉 `portal._naive_utcnow` 这份重复实现，5 处内联调用改为统一入口。
   加一个测试：扫描 `app/` 下不得再出现裸 `datetime.utcnow()`/`datetime.now()`。
3. **补越权用例到 100%**——按上面那份 91 个未覆盖路径的清单逐个补
   "非授权角色调用返回 403"。这是机械活，但它是阶段十的入场券。

### 阶段十 统一资源与申请单中心

（原阶段九，顺延）通用资源注册-发布-撤回模型，把号源/检查/手术间/血制品/工勤
收敛到一套资源表；`/api/service-requests` 从聚合视图升级为排程撮合中心；
流程图形化编排（前端画布产出既有 JSON 定义，后端不动）；DRGs 事前提示与事中预警。

### 阶段十一 权限模型重构与安全加固

（原阶段十，顺延）角色表 + 权限点表 + 关联，`require_roles` 改为查权限点；
六个内置角色作为预置数据保留，保证现有部署零感知升级；审计防篡改哈希链与归档；
错误信息脱敏统一出口；CSP 响应头。

**入场条件**：阶段九第 3 项完成（越权用例 100%）。

### 阶段十二 前端拆分与金额精度（低优先）

- `app.js` 按业务域拆成多个文件，用现有的 `PAGES` 注册表做入口，不引入构建工具
  （build-free 是既定约束，拆文件即可，不要借机上打包器）；
- 金额 `Float → Numeric` 一次性迁移，**建议与接入真实医保结算同批做**。
