> 核对时间：2026-08-11｜核对基线：`claude/county-medical-platform-plan-2p7456` @ `096e237`

> 对照文件：国家《紧密型县域医共体信息化功能指引》36 项、《浙江省县域医共体信息化建设指南》82 项、

## 一、核对方法

前两轮对照（见 [功能指引对照表](功能指引对照表.md)、[浙江省指南对照与开发计划](浙江省指南对照与开发计划.md)）
已把国家 36 项逐子功能销号、浙江 82 项排出 M1–M12 路线图，其中 M1–M9 的多数条目在后续开发中
提前交付。本轮**不采信既有对照表的结论**，改从代码侧反向核对：

1. 用 `app.openapi()` 导出全部 302 条接口路径，按模块归组，逐模块比对指引条目；
2. 用 SQLAlchemy metadata 导出 128 张表的列定义，与 Alembic 迁移链建出的库结构逐表逐列比对
   （本轮结果：**无缺表、无多表、无列漂移**，迁移链与模型完全一致）；
3. 对"文档声称已实现"的条目做代码复核，只认真正跑得起来的实现；
4. 对横切能力（定时、限流、缓存、清理）做专项探查——这类缺口不体现在功能条目上，
   却直接决定生产可用性。

## 三、发现的缺口

### A. 平台横切能力（无功能条目，但直接影响生产可用）

| 编号 | 缺口 | 证据 | 影响 |
|---|---|---|---|
| **A1** | **完全没有定时任务基座** | 全仓 `grep cron\|scheduler\|APScheduler` 零命中 | 慢病超期、医废滞留、合同到期、制剂临期、日终对账、验证码清理——所有"到点该发生的事"目前都只能靠人工调接口或外部 crontab 触发 |
| **A2** | 限流器只有进程内存实现 | `state_store.SlidingWindowRateLimiter` 无 Redis 分支（`TokenBlacklist`/`LoginFailureTracker` 都有） | 多实例部署下短信验证码下发限流形同虚设——N 个实例各自计数，短信轰炸成本降到 1/N。这是上一轮居民端登录改造**新引入**的风险面 |
| **A3** | `sms_codes` 表无清理 | 只写不删，无 TTL 无归档 | 一个县 30 万人口的量级下该表将无界增长；且过期验证码散列长期留存无必要 |

### B. 住院临床域（县级医院核心业务，M7/M9 遗留）

| 编号 | 缺口 | 现状 |
|---|---|---|
| **B1** | 住院病程记录 | `/api/inpatient` 只有入出转、医嘱、病案首页。首次病程、日常病程、上级医师查房、抢救记录全缺。`MedicalRecord` 是**门诊**病历（一次就诊一份），不适用于住院连续文书 |
| **B2** | 护理文书 | 护理级别、护理执行单、体温单、交接班记录均无 |
| **B3** | 手术麻醉管理 | 全仓仅在病案首页有一个 `operation` 文本字段、DRG 分组有"主手术关键词"。手术申请→审批→排班→术中记录→术后随访的完整流程不存在。这同时是 DRG 外科组入组质量的短板 |
| **B4** | 出院/术后随访 | 随访只有慢病随访（`/api/chronic/{id}/followups`）与妇幼访视，出院随访、术后随访无载体 |

### C. 运营与决策（M10/M12 遗留）

| 编号 | 缺口 | 现状 |
|---|---|---|
| **C1** | 会计凭证与复式记账 | `FinanceEntry` 是 `period + income/expense + amount` 的流水台账，无会计科目、无凭证、无借贷平衡校验 |
| **C2** | 成本核算 | 仅消毒供应有单件成本（`/api/cssd/cost-stats`）。科室成本、诊次成本、床日成本无归集 |
| **C3** | 物资采购全流程 | 药品有申请→审批→验收（`/api/pharmacy/purchase-orders`）；**物资**只有出入库（`/api/mgmt/assets/{id}/movements`），缺采购申请/合同/到货验收 |
| **C4** | 高值耗材追溯 | 无条码绑定患者的追溯链 |
| **C5** | 监测指标扩展 | 14 项已落地；县域就诊率/外转率缺"县外就诊登记"数据源；医防融合、运行机制两个维度的指标无采集口径 |
| **C6** | 运行效率口径 | `/api/inpatient/stats` 只有床位使用率与在院/出院人次；平均住院日、床位周转次数、医师担负工作量未计算 |
| **C7** | 绩效自定义公式 | `PerformanceIndicator` 只能调权重，公式硬编码在 `performance.py`；无自定义公式与期末综合绩效报告 |

### D. 平台引擎（M11 架构级）

| 编号 | 缺口 | 现状 |
|---|---|---|
| **D1** | 业务流程引擎 | ESB 的 `EsbFlow` 是**消息级**编排（transform/validate/route/persist），不是带待办联动的业务流程引擎。转诊、会诊、审批各自硬编码状态机 |
| **D2** | 统一规则引擎 | 现有四套各自实现的规则：审方规则（`DrugRule`）、绩效指标、互认规则、数据质控（`QcRule`）、病历质控（`RecordQcRule`）。条件 DSL 未统一 |
| **D3** | 统一申请单中心 | 预约、检查申请、会诊申请、用血申请、药品申领各建一套单据，无通用"资源注册-发布-撮合"模型 |
| **D4** | 支付真实通道 | `PaymentGateway` 协议已定义，但只有 `MockGateway`；真实渠道 SDK 适配未实现 |
| **D5** | 辅助诊断 | 中医辅诊与智能分诊都是关键词/规则匹配，未接模型服务 |

### E. 测试覆盖偏低模块

`consultations.py` 76%、`contracts.py` 78%、`cssd.py` 78%、`referrals.py` 79%、`checkups.py` 80%、
`medwaste.py` 80%——均为早期模块，异常分支（状态机拒绝、越权、并发冲突）测试不足。

## 四、下一步开发计划

排序依据：**先补会出事的，再补业务缺的，最后做架构性的**。

### 阶段一：平台横切能力（优先级最高）

> 理由：A2 是上一轮改造新引入的真实攻击面；A1 是后续所有"提醒/对账/预警"的地基，
> 不先做，后面每个新功能都要再写一遍"靠人工调接口"的说明。

- **T1.1 定时任务基座**：轻量调度器（进程内 + 可选 Redis 抢锁保证多实例只跑一次），
  任务注册表、执行留痕、失败重试与手动触发接口。首批接入：慢病超期扫描、医废滞留预警、
  合同到期提醒、中药制剂临期、日终对账、验证码清理。
- **T1.2 限流器 Redis 化**：`SlidingWindowRateLimiter` 补 Redis 后端（与 `TokenBlacklist`
  同一套 `_redis_client()` 约定），多实例共享验证码下发配额。
- **T1.3 敏感数据保留策略**：`sms_codes` 过期即删（挂 T1.1）；审计日志按月归档策略文档化。

### 阶段二：住院临床文书与手术麻醉

> 理由：县级医院核心业务域，同时是 DRG 入组质量、病历质控、成本核算的共同数据底座。

- **T2.1 住院病程记录**：首次病程/日常病程/上级医师查房/抢救记录四类文书，
  按住院号连续编号，限医师，接入现有病历质控规则引擎。
- **T2.2 护理文书**：护理级别医嘱联动、护理执行单、体温单（体征时序）、交接班记录。
- **T2.3 手术麻醉**：手术申请→审批→排班（手术间/时段资源，复用号源的原子占位模式）→
  术中记录（术者/麻醉方式/切口等级）→术后随访；病案首页 `operation` 改为引用手术记录，
  提升 DRG 外科组入组准确性。
- **T2.4 随访中心**：把慢病随访、妇幼访视、出院随访、术后随访收敛到统一随访任务模型。

### 阶段三：运营与成本

- **T3.1 会计科目与凭证**：科目表、凭证（借贷平衡强校验）、期末结账，`FinanceEntry` 作为凭证明细的来源。
- **T3.2 成本核算**：科室/诊次/床日三级成本归集，分摊规则可配置。
- **T3.3 物资采购全流程**：申请→审批→合同→到货验收，与现有资产出入库打通。
- **T3.4 高值耗材追溯**：条码绑定患者与手术记录（依赖 T2.3）。

### 阶段四：决策指标扩展

- **T4.1 县外就诊登记**：补数据源，打通县域就诊率、外转率两项核心监测指标。
- **T4.2 运行效率完整口径**：平均住院日、床位周转次数、医师担负（依赖 T2 住院数据）。
- **T4.3 绩效自定义公式**：公式 DSL + 期末综合绩效报告（可与 D2 统一规则引擎合并设计）。

### 阶段五：平台引擎（架构级专项）

- **T5.1 统一规则引擎**：抽象条件 DSL，把审方/质控/绩效/互认四套规则迁移过来，
  以兼容并行方式推进，回归测试全绿为红线。
- **T5.2 业务流程引擎与待办联动**：流程定义 JSON 化，转诊/会诊/审批迁移接入。
- **T5.3 统一申请单中心**：通用资源注册-发布-撮合模型，既有五类单据逐步接入。

### 贯穿项

- 每阶段补齐对应模块的异常分支测试，目标把 E 类模块拉到 85% 以上；
- 模型改动一律配 Alembic 迁移并做"迁移链 vs 模型"逐列比对（本轮已建立该检查手法）；
- 角色守卫按 `deps.py` 矩阵延伸，申报/审批职责分离。

### 执行中做出的取舍（与原计划的偏差，逐条说明）

1. **T5.1 未做大爆炸式规则迁移**。原计划写"把审方/质控/绩效/互认四套规则迁移
   到统一引擎"。实际评估后改为兼容并行：统一引擎负责新增规则，四套既有规则
   以只读方式并入统一目录，执行路径暂不合并。理由：硬迁要动 450 项回归测试里
   的相当一部分，而收益（少写几个 if）远小于风险。目录里的 `engine` 字段
   如实标出哪些走统一引擎、哪些仍是既有实现，不含糊其辞。
2. **T5.3 未新建通用单据表**。原计划写"通用资源注册-发布-撮合模型"。实际改为
   五类既有单据的聚合视图 + 统一状态映射。理由：五类单据各有必要的领域字段与
   状态机（号源原子占位、危急值闭环、库存拦截），再造一张通用表的结果只会是
   一张没人写入的空表；真正缺的是"一处看全在办事项"，聚合视图正好解决。
3. **T5.2 流程引擎不迁移既有状态机**。转诊、会诊、手术审批的业务规则（床位
   释放、号源回滚、费用校验）嵌在各自流程里，硬迁到通用引擎只会把规则打散。
   引擎面向新增审批类流程，既有流程后续可选迁移。
4. **成本分摊只做一轮**（行政/医技→临床），不做多级迭代分摊。县域机构科室
   层级浅，多级迭代要处理互相分摊的收敛问题，收益不抵复杂度；未配满 100%
   的分摊比例在返回里单独标出，不悄悄留在原科室。

### 仍未覆盖的部分

外部依赖项一如既往不在开发主线内（DICOM、省平台、医保联调、音视频、血站、
药械采购平台等），平台侧接口已预留。支付真实通道与模型辅诊的适配层骨架
可写但无法验证，建议等对接窗口。
