# 全域慢专病子系统 · 下一步开发计划

## 这份计划是怎么来的

不是"还能加什么功能"的头脑风暴，而是**从代码实测出来的缺口**——每一条都附了
现状的核实方式，可以自己跑一遍确认。当前基线：236 个接口、59 张表、11 个管理端页面、
102 条子系统用例，全量 1323 passed。

缺口分四类，按"招标条目是否已经能走通"排优先级：

- **P0 功能闭合**：招标条目已建了模型与接口，但业务链路走不完（数据落了库没人推、
  状态永远不变），验收时会被当场看出来；
- **P1 集成落地**：实施期对接真实院内系统时必须补的；
- **P2 性能与体验**：现在跑得动，上了量或交给基层用就不行；
- **P3 交付与验收支撑**：演示、E2E、培训材料。

## P0 · 功能闭合（建议 1~2 周内做完）

### P0-1 报告推送任务没有调度，只能手工生成

**现状**（`grep -rn "SpdReportTask" app/spd/jobs.py` → 空）：
`spd_report_tasks` 有 `frequency` / `push_time` / `valid_from|to` / `priority` / `status`
全套字段，但**没有任何定时任务按它们生成报告**。目前只有手工
`POST /api/spd/report-instances` 一条路。招标智能辅助端 #2 要的是"创建报告推送任务，
配置频率、目标用户、推送时间、有效期，提供启用/暂停/删除与优先级调度"——
配置项齐了，调度是空的。

**要做**：在 `app/spd/jobs.py` 加 `spd_report_push` 任务（建议 5 分钟粒度唤醒）：
按 `frequency` + `push_time` 判定到期、跳过 `paused` 与超出有效期的、按 `priority` 排序执行、
生成 `SpdReportInstance` 后给 `subscriber_ids` 投站内消息（走 `platform.notify_user`）、
回填 `last_run_at`。**幂等**：同一任务同一周期只生成一次（按 `task_id + period_label` 判重）。

**验收**：新建一个 daily 任务、把 `push_time` 设成当前时间前一分钟，跑一次任务后
`report-instances` 多出一条、订阅人收到站内消息、再跑一次不重复生成。

**量级**：约 1 人日（含用例）。

### P0-2 复诊与随访的"逾期"只在查询里，不在状态里

**现状**：`sweep_overdue()` 只扫 `SpdTask`。`SpdRevisit` 与 `SpdFollowupRecord` 的
`status` 永远停在 `planned`，"逾期"是查询时用 `plan_date < today` 现算的
（`GET /api/spd/revisits?overdue=true`）。后果是同一件事有两套口径：督办清单按现算、
考核取数按 `status`，两边数字对不上；而考核结果是要进绩效的。

**要做**：把 `sweep_overdue` 扩成三类一起扫（任务、复诊、随访），复诊逾期置
`status=overdue` 并写 `log`，随访逾期置 `overdue`。**注意**随访的
`unreachable`（失访）不能被覆盖成 `overdue`——那是两件事，完成率的分母含失访、
分子不含。同时把 `overdue=true` 的查询改为按 `status` 过滤，让两处口径合一。

**验收**：建一条昨天到期的复诊，跑扫描后状态变 `overdue`；已失访的随访再扫不变。
既有 `test_overdue_sweep_marks_tasks` 扩成三类。

**量级**：约 1 人日。

### P0-3 佐证材料没接平台附件服务

**现状**（`grep -rn "attachment" app/spd/` → 空）：任务的 `evidence` 是一个字符串数组，
前端传什么就存什么。平台已有 `/api/attachments`（10MB 限制、图片/PDF 白名单、鉴权下载），
但慢专病没用上。招标成员端 #17/#18、患者端 #15 都明确要求"上传照片或报告等凭证"。
现状能过 `require_evidence` 的校验（数组非空即可），**但存的可能是任意字符串**。

**要做**：`evidence` 改为存附件 id 列表，提交时校验每个 id 存在且 `owner_type=spd_task`；
出参附带鉴权下载链接。居民端同理（`POST /api/portal/spd/tasks/{id}/submit`）——
居民上传要走居民令牌可用的附件通道，这一条要先确认平台附件接口对 portal 令牌的支持情况，
不支持则需要补一个居民端上传入口。

**验收**：传不存在的附件 id 返回 422；传合法 id 后详情能拿到下载链接；
非本机构人员下载被拒。

**量级**：约 2 人日（含居民端通道确认）。

### P0-4 宣教推送与呼叫任务只落库，不外发

**现状**：`POST /api/spd/edu-pushes` 直接把 `status` 置为 `sent`，**没有调用平台的
短信通道**（`app/sms.py` 有 console/http 两种 provider）；`SpdCallTask` 也只是台账，
没有对接呼叫系统。招标智能随访端 #9 要"及时触达"、#10 要"自动保存并关联患者录音"。

**要做**：
1. 宣教推送按 `channel` 走真实通道：`sms` → `sms.get_sms_provider()`，
   `app` → 站内消息（居民收件箱），`wechat` → 先留接口位并明确标注未接入；
   发送失败置 `failed` 并记原因，**不要静默置 sent**。
2. 呼叫任务定义一个 `CallProvider` 协议（与 `PaymentGateway`、`SmsProvider` 同形状），
   内置 `manual`（人工外呼后回填结果，即现状）与 `http`（对接呼叫中心 API）两种实现。

**验收**：console 通道下推送后状态为 `sent` 且日志里能看到内容；通道故障时置 `failed`；
`GET /api/spd/edu-pushes/stats` 的已读率分母只算真正 sent 的。

**量级**：约 2 人日。

## P1 · 集成落地（实施期开始前）

### P1-1 数据源采集器接真实院内系统

**现状**：`collectors.py` 的 `collect_internal` 是**刻意做薄的样板**——只 count 近期就诊，
不写任何 `spd_measurements`。`LIS` / `PACS` / `checkup` / `publichealth` 四类
在 `COLLECTORS` 里没有注册，跑批会记为失败（这是设计如此，失败要看得见）。

**要做**：按各县实际接口补采集器。优先级：LIS（血糖/血脂/糖化/肌酐 → `spd_measurements`）
> 体检（年度体检指标）> 公卫（既有慢病随访归集）。每个采集器只需实现
`(db, source) -> 行数` 并 `register_collector(type, fn)`，调度、日志、监控与告警不用改。

**验收**：`GET /api/spd/data-sources-monitor` 的 `by_status` 里该类型不再是 failed；
采集回来的指标能在患者档案的趋势里看到，且等级按管理目标判定。

**量级**：每个数据源 2~3 人日，取决于对方接口质量。

### P1-2 跨机构迁出确认后没有在目标机构建档

**现状**：`POST /api/spd/lifecycle-events/{id}/confirm` 把原档案置 `migrated` 并终止
未完成工作，但**目标机构那边没有新档案**。招标个案管理师端 #11 要求"跨机构迁出由目标
机构确认后**重新建立责任关系**"——现在只完成了"断"，没完成"建"。

**要做**：确认时在目标机构建一条新的 `SpdEnrollment`（同病种、继承风险等级与建档信息、
`source=migrate`），并在两条档案间留互指关系（新增 `migrated_from_id` 列）。
**不迁移历史任务与随访**：那些属于原机构的工作留痕，迁走会让原机构的考核凭空少一截。

**验收**：确认后目标机构的在管数 +1、原机构 -1；新档案能看到迁入来源；
原机构的历史考核数字不变。

**量级**：约 1.5 人日（含一条迁移）。

### P1-3 报告段落取数只支持五个内置 key

**现状**：`_compose_section` 认 `summary` / `todo` / `alert` / `workload` / `score` /
`quality` / `trend`，自定义 key 返回 `"该段落未配置取数口径"`。模板可以随便建，
但建了新段落等于建了个空壳。

**要做**：把段落取数做成注册表（与采集器同一形状），内置 key 迁进去，
并补上招标点名的几类：筛查转化、纳管结构、路径完成、转诊闭环、随访质量、村医积分。
自定义段落允许配"指标编码 + 分组维度"，走考核指标库的取数口径复用——
**不要再开一套 SQL 口径**，那是报表与考核数字对不上的根源。

**验收**：新建一个引用 `referral_closure_rate` 的段落，生成的报告数字与
`GET /api/spd/referrals-stats/closure` 一致。

**量级**：约 2 人日。

### P1-4 路径进入条件只在显式端点校验

**现状**：`GET /api/spd/path-nodes/{id}/enter-check` 能校验，但
`advance_path()` 生成下一节点任务时**不校验** `enter_condition`。也就是说条件配了，
自动流转时不生效，只有前端主动调用检查才看得见。

**要做**：`advance_path` 派生任务前先判进入条件；不满足时不建任务、把实例置
`paused` 并记原因，同时给责任人发一条站内消息（"路径因未满足进入条件暂停"）。
**不要静默跳过**——静默跳过的表现是"路径停在那里且没人知道为什么"。

**验收**：配一个 `bp_sys >= 140` 的进入条件，血压正常的患者办完上一节点后实例转
`paused` 且有消息；补录一条高血压值后手工 `advance` 能继续。

**量级**：约 1 人日。

## P2 · 性能与体验

### P2-1 三处 N+1 与考核跑分的查询放大

**现状**（实测代码）：

| 位置 | 问题 | 量级 |
|---|---|---|
| `workbench.py::team_workbench` 的 `pending_assess` | 对最多 5000 名患者逐个查评估 | 5000 次查询 |
| 同上 `pending_path` | 对每名患者逐个查路径实例 | 5000 次查询 |
| `assess.py::run_scoring` | 对象数 × 指标数各查一次 `collect_metrics`，每次内部 2~4 条 SQL | 500 机构 × 5 指标 ≈ 2500~5000 次 |

演示环境数据少，看不出来；一个 30 万人口的县，团队工作台首屏会以秒计。

**要做**：前两处改成一次 `IN` 查询取差集；`run_scoring` 改成**按指标批量取数**
（一个指标一次分组查询拿到全部对象的数字），再在内存里组装。
`collect_metrics` 保留单对象版本供下钻使用，批量版本与它共用口径函数——
两套口径算出不同的数字，比慢更糟。

**验收**：加一条用例，构造 200 名患者 + 50 家机构，断言工作台与跑分的 SQL 条数
不随对象数线性增长（可用 SQLAlchemy 的 `before_cursor_execute` 计数）。

**量级**：约 3 人日。

### P2-2 前端 11 处 `prompt()`，规则编辑器实际没做

**现状**：`pages-spd.js` 里 11 处用浏览器 `prompt()` 收输入（加节点、审核意见、
下转机构、办理结果、考核周期…）。`GET /api/spd/meta` 提供了规则字段与比较符的下拉数据，
但前端只引用了 1 次——**纳入/排除规则、转诊触发条件目前只能靠接口配**，
管理端点不开。

**要做**：
1. 一个可复用的规则编辑器组件（字段下拉 + 比较符下拉 + 值输入 + 增删行），
   用在病种纳排规则、转诊触发规则、问卷异常规则、分组自动规则四处；
2. 把 11 处 `prompt()` 换成行内表单或弹层（弹层要自己写，仓库是 build-free 的，
   不引组件库）。

**验收**：不打开 `/docs` 就能在管理端配出一条完整的纳入规则并触发自动识别。

**量级**：约 4 人日（规则编辑器 2 + 表单替换 2）。

### P2-3 量表二维码只有令牌，没有图片

**现状**：`SpdScale.qr_token` 有了，`GET /api/portal/spd/scales/by-token/{token}` 能扫进来，
但**没有生成二维码图片的端点**——现在要自己拿 token 去外部工具生成。
招标成员端 #8 要"生成评估二维码"、医生移动端 #22 要"生成医生登录及纳管二维码"。

**要做**：加一个 `GET /api/spd/scales/{id}/qrcode`（与村医 `bind_token` 同理），
服务端渲染 SVG 二维码（纯 Python 实现，不引二维码库也可以——本仓库有
build-free 与少依赖的既定约束，需要先确认加一个轻量依赖是否可接受）。

**量级**：约 1 人日（取决于依赖决策）。

## P3 · 交付与验收支撑

### P3-1 演示数据零覆盖慢专病

**现状**（`grep -c spd scripts/seed_demo.py` → 0）：演示站点灌完数据后，
慢专病的 11 个页面全是空的。投标演示与培训都要用这套数据。

**要做**：在 `seed_demo.py` 里补一条完整链路的样例——3 家机构 × 2 个团队 ×
20 名患者，覆盖：筛查（含高危）→ 复核 → 目标池分发 → 签约建档 → 启动路径 →
办几个任务 → 录几次监测（含异常）→ 做一次评估（触发高危干预与复诊）→
发起一次转诊并走到闭环 → 跑一次考核 → 生成一份日报。
末尾做终态自检（与既有脚本同一风格：某个业务校验把中间步骤挡下来时当场报错）。

**验收**：灌完数据后 11 个页面都有内容，且各端工作台的数字互相对得上。

**量级**：约 2 人日。

### P3-2 E2E 未覆盖慢专病

**现状**：`tests/e2e/test_flows.py` 没有 spd。管理端 11 个页面、居民端与医生端各一个
页签，目前只有接口级用例保证，**页面能不能打开、按钮点了有没有反应没有自动化验证**。

**要做**：Playwright 覆盖三条最短闭环：管理端（登录 → 筛查 → 建档 → 启动路径 →
办任务）、居民端（登录 → 自查 → 申请 → 录监测）、医生端（登录 → 待办 → 转诊办理）。
与既有 e2e 同样默认跳过、`--e2e` 开启。

**量级**：约 3 人日。

### P3-3 培训与用户手册

招标 7.6 条要求上线后一年内累计不低于 6 次培训、覆盖全体使用人员。需要按**端**
而不是按模块编写操作手册（一个村医不需要知道考核指标库怎么配）：
村医 / 团队成员 / 个案管理师 / 中心调度 / 卫健监管五本，每本 10~15 页，
截图取自演示环境（依赖 P3-1）。

**量级**：约 5 人日（依赖 P3-1 完成）。

### P3-4 PostgreSQL 独立 schema（有 PG 测试环境后）

见 [慢专病子系统架构说明.md](慢专病子系统架构说明.md) 的说明：当前刻意没做，
因为在 SQLite 上验证不了。有 PG 测试环境后按那里写的路径实施，并配一条真实连库的用例。

**量级**：约 3 人日 + 环境准备。

## 建议排期

| 批次 | 内容 | 相对量级 | 说明 |
|---|---|---|---|
| 第一批 | P0-1 ~ P0-4 | 约 6 人日 | 功能闭合，做完才算"招标条目都能走通" |
| 第二批 | P3-1 演示数据 + P2-2 规则编辑器 | 约 6 人日 | 投标演示与现场配置的前提 |
| 第三批 | P1-1 ~ P1-4 | 约 8 人日 + 对接方配合 | 与实施期对接同步推进 |
| 第四批 | P2-1 性能 + P3-2 E2E | 约 6 人日 | 上量前必须做完 |
| 第五批 | P3-3 培训材料、P2-3 二维码、P3-4 schema | 约 9 人日 | 交付期 |

人日为**相对量级**，不含需求确认与对接方等待时间；跨机构对接（P1-1）的实际耗时
通常由对方接口质量决定，不由本侧工作量决定。

## 不建议现在做的事

| 事项 | 理由 |
|---|---|
| 拆成独立微服务 / 独立数据库 | 八成动作要读平台数据，拆库会把考核数字变成同步产物 |
| 引入前端构建工具 | 仓库是 build-free 的既定约束；P2-2 的规则编辑器用原生实现即可 |
| 再造一套消息队列 | 平台已有 ESB 负责跨系统消息，应用内解耦已由 `app/events.py` 解决 |
| 把 `chronic` / `disease_programs` / `followups` 合并进来 | 招标只要求并行运行；它们承载着在用的业务，合并等于在实施期打断正在跑的业务 |
| 给"疑似人群"做自动纳管 | "筛出来 ≠ 管起来"是这套系统的基本口径，自动纳管会让纳管率失真 |
