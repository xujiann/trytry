# ADR-0013：药品可用汇总的口径与"批次同改"约束

- 状态：Accepted
- 日期：2026-08-22
- 决策者：药事域维护方
- 相关：ADR-0001（核心数据不可变定义）、`server/app/models/pharmacy.py`
  （`DrugStock` / `DrugBatch`）、`server/app/routers/pharmacy.py`、
  `server/app/routers/dispense.py`、
  守卫 `server/tests/test_pharmacy_stock_invariant.py`、
  既有守卫 `server/tests/test_pharmacy_batches.py`、
  迁移 `e1b3c5d7f9a2`

## Problem（问题）

批号效期台账（`DrugBatch`）落地时声明了一条对账不变式：同一 (机构, 药品) 的
`DrugStock.quantity` 恒等于其各批次 `quantity - used_quantity` 之和
（`app/models/pharmacy.py` 的 `DrugBatch` docstring）。但这条不变式**从来没有
真正成立过**，因为只有新写的三条路径（批次入库、发药、退药冲销）两边同改，
四个存量端点只改汇总不动批次：

| 端点 | 实测（批次入库 100 后） |
|---|---|
| `POST /api/pharmacy/stocks` 直接入库 50 | 汇总 150 / 批次和 100 |
| `POST /api/pharmacy/purchase-orders/{id}/receive` 验收 30 | 汇总 180 / 批次和 100 |
| `POST /api/pharmacy/transfers` 调拨 40 到乡镇院 | 乡镇院汇总 40 / 批次和 0 |
| `POST /api/pharmacy/stock-takes` 盘点改 5 | 汇总 5 / 批次和 100 |

危害不是"数字不好看"。发药按批次走 FEFO（`dispense._fefo_batches`），
**没有批次就一片也发不出来**；而缺药预警与采购建议看的是汇总。调拨那一行因此
造出了最典型的**幽灵库存**：乡镇院账上有 40 片，一张方发不出来，系统还认为它
不缺药。盘点那一行则相反——盘完账面 5 片、批次仍挂 100 片，下一次发药照发不误，
这次盘点等于白盘。

同一条不变式还有第二个破口：**批次被召回后余量仍算在汇总里**
（`recall_batch` 只翻 `status`），而**退药冲销无条件把量补回汇总**
（`reverse_dispense` 无条件 `add_amount(DrugStock, +qty)`，不看目标批次还能不能发）。
实测：召回一个余 80 片的批次后汇总仍是 160、实际可发只剩 50；再冲销一张 20 片的
发药单，汇总涨到 180 而可发仍是 50。采购建议拿汇总当有货，于是缺药长期少报。

约束：`drug_stocks` / `drug_batches` 已在生产使用；`GET /api/pharmacy/stocks`
与 `/batches` 的既有字段不能改含义（§7 向后兼容）；本仓库**明确拒绝用定时任务
去改批次状态**（"何时过期"不能取决于任务跑没跑，见 `DrugBatch` docstring）。

## Options（可选方案）

- **方案 A：维持现状**，不变式只对新写的三条路径成立，文档不改。
- **方案 B：收窄不变式的适用范围**——把"汇总 == Σ(批次)"降级为"仅批次入库/
  发药/冲销这三条路径成立"，在模型与接口文档里标注四个存量端点是例外，
  另外单独保证调拨必须走批次（不产生幽灵库存）。
- **方案 C：给四个存量端点补批次侧动作**，让不变式对**所有**改动汇总的端点成立；
  没有批号可报的入库（直接入库、采购验收、盘点盘盈）落到兜底批次
  `未标批号`，调拨按 FEFO 搬真实批次，盘亏按 FEFO 核销批次。
- **方案 D：把 `DrugStock` 降为纯派生量**，每次读取时从批次现算，删掉汇总列。

各方案都要同时回答"召回与冲销"那一半，可选：

- **C1**：召回时把批次余量从汇总扣掉；冲销回补时若目标批次已召回/已过期，
  **只回批次不回汇总**（差额不记录）。
- **C2**：同 C1，但把"退回来却发不出去"的量**显式记在批次的
  `blocked_quantity` 列上**，可发余量改为 `quantity - used_quantity - blocked_quantity`。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零改动、零风险。 |
| B | 改动最小；把"文档撒谎"这件事先止住；调拨走批次即可消除最贵的那个症状。 |
| C | 不变式重新变成一条**真话**，可被一条断言钉死；四个端点的账实问题一次性解决；缺药预警与采购建议从此看的是真数。 |
| D | 口径唯一，不可能对不上账。 |
| C1 | 不加列、不写迁移。 |
| C2 | 差额有了确定的去处，不变式仍然**任何时刻可校验**；"这批退回来 20 片死货"在台账上看得见，报废流程有据可依。 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 幽灵库存与缺药少报继续在生产上跑；不变式是假的，后来人会照着它写新代码。 |
| B | 四个端点的账实不符原样保留；盘点仍然白盘；"哪些路径算数"要靠人记，下一个端点大概率再犯。 |
| C | 改动面最大（4 个端点 + 召回 + 冲销）；调拨会新增"汇总够但可发批次不够"的 409；引入 `未标批号` 这个概念。 |
| D | 汇总是热点读（缺药预警、采购建议、大屏），每次现算要扫全部批次；**且无法用原子增量维护**——派生量必须读后写，并发下必然丢更新（正是 `concurrency.add_amount` docstring 里记录的那个坑）。 |
| C1 | 差额谁也算不出来：冲销进过期批次之后，汇总与批次之间出现一个无法复原的缺口，不变式从此不可校验，等于用一个静默的坑换掉一个响的坑。 |
| C2 | 要加一列、写一个迁移；`BatchOut` 多两个字段。 |

## Migration cost（迁移成本）

- 迁移一个：`e1b3c5d7f9a2` 给 `drug_batches` 加 `blocked_quantity`
  （NOT NULL DEFAULT 0，`downgrade` 直接 drop）。存量批次一片"退回后不可发"的量
  都没有，0 是事实而不是占位，**无需回填历史数据**。
- 代码：`routers/pharmacy.py` 四个端点 + `recall_batch`，`routers/dispense.py`
  的 `reverse_dispense` 与批次占用，`models/pharmacy.py` 两处 docstring。
- 接口：`GET /api/pharmacy/batches` 系列**新增**两个字段
  （`blocked_quantity` / `available`），既有字段含义与取值不变，是可加不可减的
  兼容变更；前端无须跟改。`POST /api/pharmacy/transfers` 新增一个 409 分支
  （可发批次不足），`POST /api/pharmacy/stock-takes` 新增一个 409 分支
  （盘点期间库存变动）。
- 一次性完成，不需要分批。量级：半天，2 个路由文件 + 1 个模型文件 + 1 张表 + 1 列。

## Risk（风险）

- **做了的风险**：调拨与盘点新增 409 分支，调用方若把 409 当成 500 处理会误报；
  兜底批次 `未标批号` 会出现在批次列表页，药师可能误以为是漏填。
  缓解：409 的 detail 写清原因与下一步；批号取中文"未标批号"而不是一串代号，
  含义自解释；新增回归用例 `tests/test_pharmacy_stock_invariant.py`
  覆盖六个端点各自的不变式与幽灵库存不可产生。
- **不做的风险**：乡镇院拿到发不出的库存却不被预警缺药；召回的药继续被算成有货；
  盘点白盘。三者都在真实盘库时才会暴露，且暴露时无法回溯是哪一笔造成的。

## Recommendation（建议）

**采纳方案 C + C2。** 理由：

1. 不变式要么是真话、要么就该删掉。方案 B 把它降级成"部分成立"，等于要求每个
   写新端点的人先记住一张例外表——本仓库已经因为"知道这个坑并不足以不掉进去"
   吃过一次亏（`concurrency.py` 模块 docstring）。C 让它重新可被一条断言钉死。
2. 方案 D 在别处已被否过：派生量无法用原子增量维护，并发下丢更新。
3. C2 相对 C1 多一列，换来的是"任何时刻可校验"。C1 那个算不出来的缺口，
   本质上和本 ADR 要修的问题是同一类。

**采纳后的权威口径**（已同步进 `DrugStock` / `DrugBatch` 的 docstring）：

    DrugStock.quantity == Σ(批次 quantity - used_quantity - blocked_quantity)

- `quantity`：批次**累计入库量**，一条收货事实，只增不减；
- `used_quantity`：已出库量（发药、调出、盘亏），退药冲销原路减回；
- `blocked_quantity`：退回本批次、但退回时本批次已召回或已过效期的量。
  药回到库房却一片发不出去，所以只回批次不回汇总。

**这条口径的已知边界（本 ADR 不解决，明写在此）**：因为拒绝用定时任务改状态，
"批次自己跨过效期"这件事**没有事件可挂**，静置过期的量仍留在
`DrugStock.quantity` 里。这不是疏漏而是取舍：任何按事件维护的增量汇总都不可能
观测到时间流逝，硬要观测就得回到方案 D 的现算（并发下不成立）或引入定时任务
（本仓库已否）。因此——

> **汇总回答的是"账上还有多少可用"，不回答"此刻能发多少"。**
> "此刻能发多少"必须按效期现算（`dispense._fefo_batches`）。

若日后要把过期量也从汇总里剔除，正确的下一步是**在批次列表/预警侧提供现算的
可发口径**，而不是让汇总去追时钟。已登记在本节，不另开技术债条目。

同步更新的守卫：新增 `server/tests/test_pharmacy_stock_invariant.py`；
既有 `server/tests/test_pharmacy_batches.py` 的 `_assert_invariant` 保持不变
（其覆盖的场景里 `blocked_quantity` 恒为 0，两条口径重合）。
