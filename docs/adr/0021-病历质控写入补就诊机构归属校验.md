# ADR-0021：结构化病历写入补「就诊所属机构」归属校验

- 状态：**Proposed**（待人工复核 —— CLAUDE.md §8）
- 日期：2026-09-06
- 决策者：待定
- 相关：**ADR-0019**（目标池分发）、**ADR-0020**（药品调拨）、TECH_DEBT **P1-43** 的第二轮判定

## Problem（问题）

`POST /api/quality/records`（`app/routers/quality.py:upsert_medical_record`）
按 body 的 `encounter_id` 取就诊、**用 `encounter.org_id` 落库**，
但从不校验调用者能不能写这家机构。角色守卫是 `require_roles("doctor")`——不在 `GLOBAL_ROLES` 里。

**已实测复现**：建甲、乙两院与一个挂甲院的 `doctor`；乙院建一次就诊；甲院 doctor 提交病历：

```
② 甲院 doctor 写乙院就诊的病历 -> 201 {"created":true,"record":{"org_id":2,"doctor_name":"t3_doc_a",…}}
   病历 org_id=2 doctor=t3_doc_a
```

病历落在**乙院名下**（`org_id=2`），书写人却是甲院的医生。且这条路径会同步跑
`_apply_qc` 算缺陷扣分——**写进去的内容直接进乙院的质控成绩**。

这是三类里最没有争议的一类：`org_id` 根本不由调用方给，是从 `encounter` 推出来的，
所以"调用方以为自己在写本院"这种误用都不成立——能写到别家，只能是没校验。

## Options（可选方案）

- **方案 A：维持现状。**
- **方案 B：`assert_org_writable(db, user, encounter.org_id)`**，放在取到 encounter 之后、任何写之前。
- **方案 C：按可见机构过滤**，别家的就诊一律 404（不泄露存在性）。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零改动 |
| B | 与 ADR-0019/0020 及同仓库既有写守卫同款；403 语义直白 |
| C | 不泄露"这条就诊存不存在" |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 任何 doctor 可写任意机构的病历并影响其质控成绩 |
| B | 若真有"上级医院代基层补录病历"的用法会被挡——但那种用法本身就该显式授权 |
| C | 与同仓库其它写接口的 403 不一致，排查时"404"会被误读成数据没同步 |

## Migration cost（迁移成本）

一行校验 + 回归用例。不动表结构与响应模型。

## Risk（风险）

- **行为变化**：今天 201 的越权写会变成 403。
- 与 ADR-0019/0020 相比，这条**没有需要业务裁定的口径**——病历写入天然属于就诊发生的那家机构。
  真要放开"代录"，应当走显式授权（本仓库已有 `active_authorization_grants` 那一套），
  而不是靠不校验。

## Recommendation（建议）

**取方案 B。** 落地：
1. `assert_org_writable(db, user, encounter.org_id)`，紧跟在 `encounter is None` 判定之后。
2. 回归用例：甲院 doctor 写乙院就诊的病历必须 403 且不留任何 `MedicalRecord` 行；
   本院就诊仍 201；admin 跨机构仍 201。
3. 变异验证：拿掉守卫，越权用例转红、合法用例仍绿。

**需人工复核后再合**（CLAUDE.md §8）。

## 附：同一轮判定里**未修**的一条，及其理由

`POST /api/contracts`（`contracts.py:sign`）**同样已实测越权**：

```
① 甲院 doctor 改乙院签约 -> 201 {"org_id":2,"doctor_name":"甲院李医生","package":"premium","status":"active"}
   改后 org=2 doctor=甲院李医生 status=active
```

甲院的 doctor 把乙院一份已解约的家庭医生签约**重新激活，并把家庭医生改成了自己**；
签约数据还喂着绩效的「家医履约」指标。这个接口连 `user` 参数都没有，无从校验。

**这一条没有随本 ADR 一起修**，理由是它**需要业务裁定而上面那条不需要**：
家庭医生签约是"居民 ↔ 机构"的关系，现实里可能存在"县医院经办代乡镇院登记签约"的合法用法；
一刀切加 `assert_org_writable(body.org_id)` 会把它挡掉。真正要裁定的是两件事：

1. 跨机构代登记签约是否合法？若合法，走哪种授权？
2. 无论是否合法，**"重新激活既有签约时静默覆盖 `doctor_name`/`package`"** 都值得单独看一眼——
   即便同机构，把别人签的约改成自己名下也应当留痕。

裁定之前不动它，是因为**猜错方向的"修复"会直接掐掉一条正在用的业务流程**，
而这条洞的危害（改签约归属与家医姓名）低于病历与药品实物账。已登记在 TECH_DEBT P1-45。
