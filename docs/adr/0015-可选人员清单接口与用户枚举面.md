# ADR-0015：可选人员清单接口与用户枚举面

- 状态：Accepted
- 日期：2026-08-25
- 决策者：项目负责人（本轮口头裁定"给接口"）；实现与守卫由本轮提交落地
- 相关：ADR-0008（配置域拆包）、`docs/接口标准与治理.md`、CLAUDE.md §8 安全红线、
  守卫 `server/tests/test_selectable_users.py`、消费方 `app/static/pages-spd.js:renderSpdTeams`

## Problem（问题）

慢专病配置域的写操作放给 `CONFIG_ROLES = ("director", "doctor")`
（`app/spd/routers/config/_base.py:22`），其中三处要指定"是哪个人"：

- `POST /api/spd/teams/{id}/members` 的 `user_id`
- `POST /api/spd/village-doctors` 的 `user_id`
- `SpdTeam.leader_user_id`

但**平台侧唯一的用户清单 `GET /api/users` 是 `require_admin`**
（`app/routers/users.py:125`）。于是 `doctor` 能建团队、能加成员，却**列不出可选的人**——
2026-08-25 补的管理端配置页只能退化成让人手填 user_id，并在界面上解释为什么。
手填 ID 在演示库里能凑合，在真实县域里不可行：没人记得住同事的用户 ID。

约束：

- `users` 是核心表、已冻结（ADR-0001），且是人物账号的**唯一权威表**——
  不得为了绕开这个问题在 spd 侧另造平行的人员表（`docs/核心数据不可变定义.md`）。
- `GET /api/users` 回的是完整账号档案：`username`（登录句柄）、`status`、`org_id`、`role`。
  实测形状：`{"id":1,"username":"admin","full_name":"平台管理员","role":"admin","org_id":null,"status":"active"}`。
- CLAUDE.md §8：涉及越权的改动要留决策记录并请人复核。本文件即该记录。

## Options（可选方案）

- **方案 A：维持现状**，配置页继续让人手填 user_id。
- **方案 B：放宽 `GET /api/users` 的守卫**，从 `require_admin` 改成登录即可读（或加 `director`/`doctor`）。
- **方案 C：另开一个最小披露、按可见范围收窄的只读接口** `GET /api/users/selectable`，
  `GET /api/users` 保持 `require_admin` 不动。
- **方案 D：在 spd 侧建一份"可选成员"配置表**，由管理员预先维护候选人名单。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零改动、零新增攻击面。 |
| B | 一行改动，前端不用动，所有需要选人的页面一次都解决。 |
| C | 权限面只扩到"看得见同机构同事的显示名"；登录名与账号状态不外泄；可按可见范围收窄；契约独立，将来改口径不牵动管理清单。 |
| D | 完全不碰用户枚举；候选名单由管理员显式控制。 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 配置域在真实县域里不可用——这正是本轮"可用性线"要修的问题，等于没修。 |
| B | 把**完整账号档案**（含登录名、账号状态）开给全体登录用户。登录名是撞库字典的一半；账号状态则暴露"谁被停用了"。而且这是一次性、不可分级的放宽——以后想收回就是破坏性变更。 |
| C | 多一个端点、多一份契约；两个接口的口径要各自维护（缓解：两者字段不重叠，`selectable` 是真子集且刻意少字段）。 |
| D | 与 ADR-0001「一个概念一个权威表」直接冲突——候选名单是 `users` 的影子副本，人事变动后必然与真源漂开。且管理员维护成本高于收益。 |

## Migration cost（迁移成本）

小。无迁移、无表变更、无破坏性改动：

- 新增 1 个端点 `GET /api/users/selectable`（`app/routers/users.py`，含 `response_model`）；
- 前端 1 处消费方改用它（`pages-spd.js:renderSpdTeams`），退化分支保留为兜底；
- 端点快照 `tests/test_refactor_drift_guards.py::SNAPSHOT_ENDPOINTS` 946 → 947；
- 契约棘轮基线不动（新端点自带 `response_model`）。

## Risk（风险）

**做了的风险**：用户枚举面从"仅管理员"扩到"登录用户可见本机构在册账号的显示名"。
按最小披露设计缓解：

| 收窄手段 | 具体做法 |
|---|---|
| 字段最小化 | 只回 `id` / `name` / `role` / `org_id` / `org_name`。**不回 `username`**（登录句柄）、不回 `status`。 |
| 范围收窄 | 走 `visibility.visible_org_ids` 明细数据档：全域角色（admin/director）看全部，其余角色只看**本机构**；未挂机构的账号看不到任何人、也不出现在任何人的清单里。 |
| 只回在册 | `status == "active"`，停用账号不出现——停用的人本就不该还能被加进团队。 |
| 不给探测口 | `keyword` 只匹配**显示名**：`full_name` 非空时只匹配它，为空时才匹配 `username`。不无条件放开按登录名搜——那会变成用户名探测口（输猜测值看有没有人跳出来），与"不外泄登录名"的前提自相矛盾。 |
| 跨机构显式拒绝 | 传 `org_id` 时先过 `assert_org_visible`，越界回 403 而不是静默返回空表。 |

残余风险：同机构同事的**真实姓名**对本机构所有登录账号可见。判断是可接受——
同机构同事本就在同一栋楼里共事，且排班表、随访记录、转诊单上早就署着这些名字。

**不做的风险**：配置域在真实县域里不可用（方案 A），或为了可用而一次性放宽管理清单（方案 B）。

## Recommendation（建议）

**采纳方案 C。** 理由是它把"能选人"与"能看账号档案"这两件事拆开了——
前者是业务需要、可以下放；后者是管理动作、应当留在管理员手里。方案 B 把两者绑在一起放宽，
省下的那点实现成本换来一个收不回去的权限面。

落地第一步（本轮已完成）：端点 + 契约 + 守卫 + 前端切换 + 端点快照更新。

已同步更新的守卫/快照/文档：

- `tests/test_selectable_users.py`：字段最小披露（**断言响应里不含 `username`/`status`**）、
  可见范围收窄、停用不出现、跨机构 403、关键词不作为登录名探测口——五处变异各自转红；
- `tests/test_refactor_drift_guards.py::SNAPSHOT_ENDPOINTS`：946 → 947；
- `ROADMAP.md` 可用性线的「待裁定（authz）」条目已结案，指向本 ADR。

**需要复核的点**（按 CLAUDE.md §8，请人过一眼）：残余风险那一段的判断——
"同机构同事的真实姓名对本机构所有登录账号可见"是否符合本地的隐私口径。
若某县要求更严，收紧方式是现成的：把 `visible_org_ids` 换成"仅本人所在团队"，
或给本接口加一个独立的权限点。
