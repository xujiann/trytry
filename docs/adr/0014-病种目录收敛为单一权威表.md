# ADR-0014：病种目录收敛为单一权威表（ADR-0003 方案 C 第二阶段）

- 状态：**Proposed**（待仓库所有者裁定）
- 日期：2026-08-22
- 决策者：仓库所有者（ADR-0003 约定本阶段"需三方评审"）
- 相关：[ADR-0003](0003-三套并行子域的收敛策略.md)（第一阶段读侧聚合已落地）、
  `docs/TECH_DEBT.md` P0-8 / P1-11、`docs/DATA_MODEL.md §2`、
  `docs/核心数据不可变定义.md`、`docs/特征化测试指引.md`

## Problem（问题）

同一个病种编码今天在**三张表**里各存一份，各带各的口径。以 `hypertension` 为例
（数字取自各自的种子文件，不是推测）：

| 表 | 列数 | 同一个 `hypertension` 存了什么 |
|---|---|---|
| `chronic_disease_types` | 8 | 分级阈值 sbp≥160 为 3 级、≥140 为 2 级；随访周期 **90 天**；健康指导语 |
| `disease_programs` | 8 | 专病路径节点（`path_nodes` JSON）、牵头机构 |
| `spd_programs` | 15 | 纳入/排除规则、四个管理阶段、里程碑、版本与生效日期 |

管理目标另在 `spd_targets`：`hypertension/treat/bp_sys` 上限 140、随访间隔 **30 天**，
`stable` 阶段则是 90 天。也就是说——**同一个高血压患者，按慢病口径 90 天随访一次，
按慢专病治疗期口径 30 天一次**。两个数字都会进各自的完成率分母。

ADR-0003 第一阶段（读侧聚合）已经把**居民能看到的**孤岛消掉了（转诊、入组各有
`/api/portal/me/*/all`）。但病种目录是**管理端配置**，居民端根本看不到，
聚合接口解决不了：真正的重复在"同一个码三处各带各的阈值"，那是写侧的事。

约束：

- 三张表都有存量数据与在跑的业务（`chronic_disease_types` 被 15 处路由引用、
  `disease_programs` 9 处）；`patients` / `organizations` 等核心表已冻结（ADR-0001）；
- 生产是 PG，迁移必须可回滚，且**不能停机**；
- 仓库原则是增量重构、不做大重写（CLAUDE.md §1.4、ADR-0003 已否决方案 D）。

## Options（可选方案）

- **方案 A（维持现状）**：三表并存，靠文档提醒实施期"三处都要改"。
- **方案 B（口径单向同步）**：仍是三张表，但把**阈值与随访周期**这类会打架的字段
  收敛到一处权威（`spd_programs` + `spd_targets`），另两张表的同名字段改为
  **只读投影**，由一个同步器在配置变更时写过去。
- **方案 C（合表，ADR-0003 提的那个）**：以 `spd_programs` 为唯一权威病种目录，
  `chronic_disease_types` / `disease_programs` 降级为视图或直接迁走，
  两侧路由改读 `spd_programs`。
- **方案 D（只加一层门面）**：不动表，加一个 `/api/disease-catalog` 门面接口对外
  统一返回，写仍分三处。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零成本、零风险；三个子域各自演进互不牵制 |
| B | 打架的只有那几个字段，收敛它们就消掉了绝大部分对账问题；表结构不动，路由不动，回滚只是关掉同步器 |
| C | 一个概念一张表，与《核心数据不可变定义》一致；此后新增病种只配一次 |
| D | 前端只对一个接口；改动量最小 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | "同一个病人两个随访周期"会一直存在，考核数字对不上没有终点；每加一个病种要配三遍，漏配一处是必然而不是偶然 |
| B | 同步器是新的活动部件，会有"同步失败但没人发现"的新故障模式；投影字段只读，实施期在旧页面上改了却不生效，需要 UI 明确标注 |
| C | 改动最大：两侧路由、种子、既有报表全要跟着走；`chronic_disease_types.level_rules` 的分级语义在 `spd_programs` 里**没有对应字段**（慢病是"控制得怎么样"三级，慢专病是"并发症风险"四级，ADR-0003 已论证过这两把尺子量的不是同一件事），合表要么新增列、要么丢语义 |
| D | 掩盖而不是消除：读侧看起来统一了，写侧仍然三处各配各的，对账问题一个不少 |

## Migration cost（迁移代价）

| 方案 | 代价 |
|---|---|
| A | 0 |
| B | 约 3~5 人日：权威字段清单 + 同步器 + 变更事件 + 一致性守卫用例（"三处同码的阈值必须相等"）+ 旧页面的只读标注 |
| C | 约 10~15 人日：数据迁移（含 level_rules 语义落点决策）、24 处路由改写、种子合并、既有统计口径回归、特征化测试网先行 |
| D | 约 1~2 人日 |

## Risk（风险）

- **方案 C 的主要风险不是技术，是口径**：合表当天，慢病侧的"随访周期 90 天"与
  慢专病治疗期的"30 天"必须二选一，选谁都会让某一批机构的完成率当场变化。
  这是业务决策，不是工程决策——ADR-0003 记过同类教训（分级词汇刻意不统一）。
- 方案 B 的风险是**新的静默失败**：同步器挂了，两边继续各用各的旧值，
  而所有页面都显示正常。缓解：同步后立即校验并在数据源监控页告警（现成机制）。
- 三个方案都要先有**特征化测试网**（`docs/特征化测试指引.md`）：先把三套现在
  各自算出什么数字钉住，再动——否则"数字变了"和"数字本来就不一样"分不开。

## Recommendation（建议）

**先做方案 B，把方案 C 留到实施期结束后再评估。**

理由：

1. 今天真正在伤人的不是"三张表"，而是**同一个码三处阈值不一致**——B 精确地
   消掉这一点，代价是 C 的三分之一，且随时可回滚（关掉同步器即恢复现状）。
2. 方案 C 需要一个"90 天还是 30 天"的业务裁定；这个裁定在实施期与各县对完口径
   之后做，比现在拍板更靠谱。B 的同步器本身也是 C 的前置——权威字段清单要先有。
3. 否决方案 D：门面只让读侧看起来齐了，写侧一处不少，属于把问题藏起来。
4. 维持现状（A）只在"确认本项目不会做多病种扩展"时才成立——与招标口径相反。

**落地顺序（B）**：

1. 先给三套各写特征化测试（当前各自算出什么，逐条钉住）；
2. 定权威字段清单：随访周期、分级/控制阈值、病种名称与启停（**不含**慢病的
   `level_rules` 分级语义与慢专病的 `risk_level`——两把尺子，ADR-0003 已裁定不统一）；
3. 权威落在 `spd_programs` + `spd_targets`，另两表同名字段改由同步器写入并在
   管理端标注"只读，改动请到病种档案"；
4. 加一致性守卫用例：三处同码的权威字段必须相等，不等即红（棘轮只进不退）；
5. 同步失败进数据源监控告警，不静默。

本 ADR 只定方向。B 的实施、以及将来是否推进到 C，各自另开任务与 ADR。
