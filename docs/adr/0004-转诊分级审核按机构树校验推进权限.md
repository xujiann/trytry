# ADR-0004：转诊分级审核按机构树（parent_id）校验推进权限

- 状态：Accepted
- 日期：2026-08-19
- 决策者：平台负责人（口径确认："规则选择 1 —— 按机构树 parent_id"）
- 相关：`app/spd/routers/referral.py`（`_assert_review_authority` / `review_referral`）、
  `app/models.py:138`（`Organization.parent_id`）、`app/spd/platform.py:90`（`org_level`）、
  回归 `tests/test_spd_flow.py::test_referral_review_requires_parent_org`、
  `docs/TECH_DEBT.md` 审计 P0-3、`ROADMAP.md`

## Problem（问题）

`spd/routers/referral.py` 的分级审核 `review_referral` 只做了角色校验
（`require_roles("doctor","public_health","director")`），**未校验推进者机构与本单的关系**：
任一服务角色账号、来自任一机构，都能把任一转诊单推进任一环节（P0 越权）。

难点在于"该由谁推进"无从判定：状态机 `_NEXT` 要求步骤一由 `station`（服务站）层级处理，
但 `org.level` 词表只有 `city/county/township/village`，**根本没有 station 这一档**
（`platform.py:97`）。因此"按 `level` 字符串严格校验"会把步骤一直接卡死。而可见性守卫
`assert_patient_visible` 是**关系型**判据（就诊/签约/转诊/授权），上级复核机构若未独立
服务过该患者则拿不到 basis，会把合法的上级复核也 403（`visibility.py:218` `patient_basis`）。

关键事实：`organizations` 表**已经带 `parent_id` + `children` 机构树**（`models.py:138`），
只是转诊链路没用它。机构层级本就该由树的父子关系表达，而非 `level` 字符串。

## Options（可选方案）

- **方案 A（选定）**：按机构树 `parent_id` 校验——每一步只允许本单**当前机构的直接上级机构**
  推进（`user.org_id == current_org.parent_id`）；`admin`/`director` 全域角色放行（中心代录）。
- **方案 B**：给 `organizations.level` 增加 `station` 取值，`org_level` 透传，按 `level` 严格校验。
- **方案 C（维持现状+最小止血）**：仅校验 `user.org_id ∈ {initiator/current/target}` 或全域角色。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 复用既有机构树，不动核心表词表、不需 ADR 改冻结快照；层级由树深度决定，天然支持"服务站"这类中间层；与 `create_referral` 允许管理层代录同口径 |
| B | 语义直白（`level` 一眼可读）；与 `_NEXT` 的 `station` 命名对齐 |
| C | 改动最小 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 依赖机构树 `parent_id` 挂全挂对；`_NEXT` 有 3 级而实际树常为 3 层（村→乡→县，无独立服务站），顶层"县级医院接收"步在 3 层树下只能由全域角色完成（见 Risk） |
| B | 触及核心表 `level` 词表（顶层数据决策，本身要 ADR）；需给存量机构定级/数据迁移；与已存在的 `parent_id` 树重复表达层级 |
| C | 不完备：下一级机构在推进前尚未落到 case 的任何 org 字段上，会卡住正常推进；实质没真正解决"谁能推进" |

## Migration cost（迁移成本）

小。仅改 `referral.py`：新增 `_assert_review_authority` 一个纯校验函数，`review_referral`
加一行调用；导入 `GLOBAL_ROLES`。**无迁移、无数据回填、不改响应字节**（仅新增 403 分支）。
新增回归 1 条。前端/对接方无需跟改（合法路径的成功响应不变）。

## Risk（风险）

- **行为收紧**：机构树未配置（`parent_id` 为空，如仅跑运行期种子而未跑 `import_legacy`）时，
  非全域账号将无法推进——这是**刻意方向**：宁可要求先建好机构树，也不放行"任意机构推任意单"。
  全域 `admin`/`director` 仍可推进，保证不至于完全卡死。已上线部署若依赖"任意服务账号推进"，
  需先补机构树；此风险由本 ADR 与 `ROADMAP.md` 显式登记。
- **层级数不匹配**（`_NEXT` 3 级 vs 实际 3 层树）：顶层"县级医院接收"在无独立服务站的树下
  落不到非全域机构——属**既有的"服务站层缺失"建模缺口**，与本越权修复正交，另案处理
  （补 4 层树 / 或收敛掉 station 一档）。本修复不引入该缺口，也不负责消除它。
- 缓解：既有 `test_referral_chain_to_closure`（admin 全链路）作特征化网守住合法闭环；
  新增 `test_referral_review_requires_parent_org` 钉住"越级 403 / 直接上级放行"。

## Recommendation（建议）

采纳方案 A。落地第一步（已完成）：`_assert_review_authority` + 回归测试 + 本 ADR。
后续（另案，登记在 `ROADMAP.md`）：
1. 运行期种子/管理端补齐机构树 `parent_id`，或提供"机构树体检"接口；
2. 决策 `_NEXT` 的 station 一档：补服务站层机构，或将链路收敛为村→乡→县三级；
3. 视需要把同类机构校验推广到 `arrive`/`down`/`receive-followup`（当前仅 `review` 收紧）。
