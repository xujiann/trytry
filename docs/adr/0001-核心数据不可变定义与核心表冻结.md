# ADR-0001：核心数据不可变定义与核心表冻结

- 状态：Accepted
- 日期：2026-08-18
- 决策者：架构治理
- 相关：`docs/核心数据不可变定义.md`、`docs/数据模型治理.md`、守卫 `tests/test_core_data_invariants.py`、`tests/test_schema_governance.py`

## Problem

本仓库最严重的技术债是"三套并行子域"：同一业务概念被慢病、专病、慢专病各建一套表
（病种目录 `chronic_disease_types` / `disease_programs` / `spd_programs`；患者入组、随访、转诊同样各三套，见 `docs/DATA_MODEL.md §2`）。重复一旦落库极难收敛：口径分叉、统计对不上、居民端出现两份互不相交的列表。若不设闸，日后极可能再冒出"第四套患者主索引 / 第二套机构层级"。当前身份字段其实很干净（`id_card`/`ehc_no` 只在 `patients`，别处一律外键 `patient_id`），需要把这个好状态**锁住**，而不是等它被破坏。

## Options

- **方案 A：仅写文档约定**——在 CLAUDE.md 写"别另造核心表"，靠人自觉。
- **方案 B：文档 + 机器守卫（棘轮）**——把核心实体、身份字段归属、核心表列集合写成测试断言，越界即红。
- **方案 C：数据库层强约束**——用外键/触发器/视图在 DB 层物理禁止。

## Advantages

| 方案 | 优点 |
|---|---|
| A | 零成本，无维护负担 |
| B | 可强制、可度量、CI 拦回归；与仓库既有"欠账不许变长"棘轮同风格；改动需被看见（ADR） |
| C | 最强，DB 层无法绕过 |

## Disadvantages

| 方案 | 缺点 |
|---|---|
| A | 形同虚设——审计已证明"约定没工具兜底=没约定" |
| B | 需维护白名单/快照；合法变更要同步更新（有轻微摩擦，但这正是"逼着走 ADR"的目的） |
| C | SQLite/PG/国产库触发器方言差异大；与"状态用裸字符串、不用 DB 级枚举"的既有取舍冲突；过重 |

## Migration cost

小。**不改任何表结构**，纯新增测试与文档：
- `tests/test_core_data_invariants.py`（身份字段归属白名单 + 人物身份唯一）；
- `tests/test_schema_governance.py`（核心表列集合快照 `FROZEN_CORE_COLUMNS`）；
- 文档 `docs/核心数据不可变定义.md`、CLAUDE.md §4 补两条。
无迁移、无回填、前端/对接方无感。

## Risk

- 低。守卫锁的是**当前已成立**的不变量（探测确认 `id_card`/`ehc_no` 仅 `patients` 持有），落地即绿，不会误伤存量。
- 唯一摩擦：将来合法地要在别处冗余身份字段时守卫会红——这是**特性不是缺陷**，它把这类改动逼进 ADR。缓解：白名单可扩，扩时写 ADR 说明理由。
- 不做的风险：三套子域式的重复继续蔓延到核心主数据，届时收敛成本是数量级更高。

## Recommendation

采纳**方案 B**。已落地：6 个核心实体锁定唯一权威表；身份字段（`id_card`/`ehc_no`/`org_type`/`password_hash`/`token_valid_from`）归属白名单；核心表列集合冻结。变更核心定义须先写 ADR，再更新对应白名单/快照并重跑 `scripts/dump_schema.py`。方案 C 留待若出现真实的跨库触发器需求再单独评估。
