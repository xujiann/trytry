# ADR-0022：会写库的 GET —— 是平台模式还是待改的欠账

- 状态：Proposed
- 日期：2026-09-11
- 决策者：待定（需产品 + 前端 + 运维共同裁定）
- 相关：P2-37（技术债登记）、ADR-0021（病历质控写入补机构归属校验）、
  `tests/test_stage15_horizontal.py::_is_write_endpoint`

## Problem（问题）

全仓有 **6 个 `GET` 端点会写库**（AST 实扫，判据：端点或其本模块调用链里出现
`db.commit()` / `db.add(`）：

| 端点 | 位置 | 写什么 |
|---|---|---|
| `spd/tasks.py:task_summary` | `tasks.py:626` | 进接口顺手跑 `sweep_overdue`，把到期未办置 `overdue` |
| `spd/workbench.py:admin_workbench` | `workbench.py:647` | 同上 |
| `spd/workbench.py:center_workbench` | `workbench.py:998` | 同上 |
| `spd/care.py:list_revisits` | `care.py:1155` | 同上（`overdue=true` 时） |
| `spd/followup.py:list_followup_records` | `followup.py:668` | 同上（`overdue=true` 时） |
| `quality.py:rescore_medical_record` | `quality.py:913` | 按当前规则库重算评分并**回写快照** |

前五个是**有意为之且写下了理由**的（`spd/service.py:472` 的 `sweep_overdue`）：

> 只靠定时任务，演示环境没开调度就永远看不到超期；
> 只靠进页面刷新，没人进页面的机构就永远不超期。

两头都说到了，是个认真的判断，不是随手写的。

**要现在决策的原因**：2026-09-11 发现 `quality:rescore_medical_record` 可被别家
机构触发并改写质控等级（乙院 doctor/operator 实测把甲院病历的 `qc_score` 从 100
改成 43、`qc_grade` 从甲改成丙）。越权本身已修（补 `assert_org_writable`），
但**它为什么躲过了此前所有闸门**才是这份 ADR 的起因：

- 写侧几道静态闸门**只扫 post/put/patch/delete**，这 6 个整族在判据之外；
- 读侧闸门当时只跟进一层本模块 helper，而它取到患者数据在第三跳。

两道判据各自的盲区正好在这里重叠。换句话说：**"会写库的 GET"不只是 HTTP 语义
洁癖问题，它是一类闸门盲区**，而这类盲区已经真的漏过一个跨机构越权。

约束：这 6 个端点都已上线并被前端调用；改方法属破坏性变更（CLAUDE.md §7）。

## Options（可选方案）

- **方案 A（维持现状）**：接受"进页面顺手刷新"是平台模式，只补文档，不动接口。
- **方案 B（只补闸门，不动接口）**：把写侧闸门的扫描面从"HTTP 方法是写"扩到
  "**会写库**"（含 GET）。不改任何接口行为。
- **方案 C（把写移出 GET）**：`sweep_overdue` 只留定时任务，另开显式的
  `POST /api/spd/tasks/sweep-overdue` 供无调度环境手动刷新；复评改
  `POST /records/{id}/qc`。
- **方案 D（全部改 POST）**：6 个端点一律改成 POST，前端跟改。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零成本；`sweep_overdue` 的理由确实成立，演示/未开调度环境依赖它 |
| B | **零破坏、当天可落地**；补住的是真出过事的那类盲区；与既有棘轮纪律一致 |
| C | 语义干净：GET 恢复"安全方法"；写入集中在一个显式入口，便于限流与留痕 |
| D | 最彻底；HTTP 语义与闸门口径都不再有例外 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 盲区继续存在：下一个把写藏进 GET 的人，写侧闸门仍看不见 |
| B | **不解决语义问题**：浏览器预取、代理缓存、客户端重试仍会触发写入 |
| C | 无调度环境要多一次显式刷新；前端要加调用，运维要写进部署说明 |
| D | 破坏已发布契约，6 个端点 + 前端调用点同改，需过渡期（双方法并存一段） |

## Migration cost（迁移成本）

- **B**：仅测试文件一处判据（`_is_write_endpoint`），**已实现**，零接口改动。
- **C**：新增 1 个端点 + 5 处调用点改造 + 前端工作台/看板 3 个页面；
  另需在 `docs/运维手册.md` 写明"未开调度时怎么刷新"。量级：1–2 天。
- **D**：C 的全部 + 复评端点改方法 + 过渡期双方法并存与弃用公告。量级：2–3 天。

## Risk（风险）

- **做 C/D 的风险**：漏改一个前端调用点，用户看到的超期数就停在旧值——
  而这类"数字不动"的故障很难被发现（没有报错）。缓解：改造前先给这 5 个端点
  补特征化测试，钉住"调用后超期数确实变了"。
- **不做（停在 A/B）的风险**：预取/重试触发的重复写入。`sweep_overdue` 是幂等的
  （按日期把 pending 置 overdue），重复执行无害；而 `rescore_medical_record`
  **不幂等于时间**——规则库一改，同一个 GET 会得到不同的分数并回写。
  这是 6 个里风险最高的一个，建议**即使选 A，也单独把它改成 POST**。

## Recommendation（建议）

**先落 B（已实现），把 C 交人裁定。**

理由：B 补的是那类真出过事的盲区，零破坏、当天可落地；而 A/C/D 之间的取舍
取决于"未开调度的现场有多少"——这是运维事实，我这里没有依据，不该替人决定。

已随本 ADR 落地的部分：
- `_is_write_endpoint` 判据放宽，写侧两道闸门（按 id、归属隔一跳）同步纳入会写库的 GET。
- **放宽当天找到 0 条新的**。两臂实测：造一个会写库、无守卫的 GET 探针，
  新判据抓得到、旧判据漏得掉——补的不是今天的洞，是明天的。

需要谁批准：C/D 涉及已发布接口契约与前端改造，需产品与前端同意；
`rescore_medical_record` 单独改 POST 的建议可先行裁定（它是 6 个里唯一不幂等的）。
