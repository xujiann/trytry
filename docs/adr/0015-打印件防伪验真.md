# ADR-0015：打印件防伪验真——签名令牌二维码 + 公开最小披露核验

- 状态：**Accepted**（实现随本 ADR 同批落地；涉及加密与"公开端点"设计，按 CLAUDE.md §8/§9 留档待人工复核）
- 日期：2026-08-28
- 决策者：仓库所有者
- 相关：`app/printverify.py`（实现与算法说明）、`app/qrsvg.py`、
  `app/routers/printing.py`（`_render` 与 `public_router`）、
  `tests/test_print_verify.py`（守卫）、ADR-0012（同一套密钥派生/轮换纪律）、
  CLAUDE.md §8（"按 id 直取、不校验归属、无留痕"红线）

## Problem（问题）

12 种打印单据（报告/处方/证明/结算/出院小结…）的版式里一直有一块
`二维码（验真占位）` 占位框（原 `printing.py` `_render`）——单据打出来就是
一张任何人都能用 Word 仿造的纸。外院窗口、用人单位、保险公司拿到纸面单据时，
**没有任何手段确认它是否真由本平台签发、内容有没有被改**。

约束条件把方案空间压得很窄：

1. **核验者在平台外**，没有账号——核验入口必须公开、免登录；
2. CLAUDE.md §8 红线：不得新增"按 id 直取、不校验归属、无留痕"的接口——
   公开入口 + 按单据号可查 = 任何人可枚举全院单据的存在性，正撞红线;
3. **纸会活很多年**：密钥轮换后，旧打印件必须仍然验得过（ADR-0012 已为登录
   令牌/审计链建立 current+previous 轮换纪律，本功能必须搭同一套）；
4. 核验展示的信息**不得超出纸面已印内容**——验真不能变成隐私泄露口。

## Options（可选方案）

- **方案 A（维持现状）**：占位框不动，验真靠打电话问医院。
- **方案 B（按号公开查询）**：公开端点按 `doc_type + 单据编号` 查询返回真伪。
- **方案 C（签名令牌，选定）**：打印时把 `{doc_type, doc_id, doc_no, org_name,
  issued_date}` 紧凑 JSON 用 HMAC（`gmcrypto.mac`，sm 套件下即 HMAC-SM3；密钥
  `security.signing_key("print-verify")` 域分隔派生）签成不透明令牌
  `v1.<b64url(payload)>.<b64url(mac)>`，编成二维码印在单据上；公开核验端点验签后
  仅回显签内字段 + 现查记录的存在性/现势状态。
- **方案 D（落表打印流水）**：每次打印落一条打印流水（短核验码 + 快照），核验按
  短码查表。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零成本；无新攻击面 |
| B | 实现最简单；核验码短、可手输 |
| C | 无新表无迁移；令牌不可枚举（猜不出合法 HMAC）、不可伪造；展示字段签在令牌里，篡改任何一个字都验不过；核验端零按需取数逻辑（12 种单据一套代码）；密钥轮换沿用既有 `verification_keys` 纪律 |
| D | 可审计"谁在何时打印过什么"；短码可手输；可精确吊销单张打印件 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 假单据无从识别，等保/行业检查过不去 |
| B | 公开可枚举：遍历编号即可探明"某医院有没有第 12345 号处方"，直接违反 §8；单据号本身无完整性保护，改内容验不出来 |
| C | 令牌长（~200 字符），扫码失败时无法手输兜底；无打印留痕（谁打印的不可查）；吊销粒度只到"记录还在不在/同意撤回没撤回"，做不到吊销单张纸 |
| D | 新表 + 迁移 + 打印链路写库（打印从只读变成写操作，报表只读副本场景破坏）；打印流水本身成为需治理的新数据资产 |

## Migration cost（迁移成本）

方案 C 实际成本（已落地）：新模块 `app/printverify.py`（令牌签发/验签/核验）与
`app/qrsvg.py`（二维码 SVG，从 spd 上移平台侧，spd 经 `platform.py` 委托回来，
单向依赖方向修正）；`printing.py` 的 `_render` 换占位框为真码（12 个端点补
`doc_id`/`request` 两个实参）；新公开端点 `GET /api/print/verify`（限速
30 次/分/IP）与静态页 `/verify`；**零迁移、零新表、零依赖**（`qrcode` 本就是
运行时依赖）。响应字节变化仅限占位框→真码那一块，且该块本就标着"验真占位"。

## Risk（风险）

- **做的风险**：公开端点是新攻击面——已用滑动窗口限速（复用
  `SlidingWindowRateLimiter`，Redis 后端多实例共享配额）+ 令牌不可枚举 +
  无效令牌统一返回、不区分失败原因，防探测；令牌泄露无隐私风险（内容=纸面
  已印字段）；密钥若泄露可伪造验真码——密钥派生与主密钥同级保管，轮换走
  既有 previous 宽限机制。
- **不做的风险**：占位框继续裸奔，假单据（假出生证明、假诊断证明）无从识别；
  行业监管（电子证照、互认共享）验收过不去。
- **遗留缺口（接受）**：无打印留痕与单张吊销（方案 D 的能力）——若日后监管
  要求"打印行为可审计"，在方案 C 之上加打印流水表即可，两方案不互斥。

## Recommendation（结论）

**方案 C**。B 违反 §8 红线直接排除；D 的打印流水能力在当前验收范围外，且可
在 C 之上增量补齐，不必现在付出"打印变写操作"的架构代价。C 满足全部四条
约束：公开可核验、不可枚举、轮换后旧纸仍有效、零隐私增量。
