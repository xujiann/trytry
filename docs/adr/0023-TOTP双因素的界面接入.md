# ADR-0023：TOTP 双因素的界面接入 —— 三条自助端点的入口，与登录侧那个更大的缺口

- 状态：Proposed
- 日期：2026-09-17
- 决策者：待定（需安全负责人裁定；CLAUDE.md §8「涉及认证的改动，走 §9 的 ADR 并请人复核」）
- 相关：ADR-0011（用户核心表安全四列与登录留痕，等保整改 E1）、
  P1-55（孤儿端点欠账）、`tests/test_orphan_endpoints.py::KNOWN_ORPHANS`、
  `app/totp.py`、`app/routers/auth.py:225-289`

## Problem（问题）

### 直接触发：三条端点没有入口

`auth` 有三条自助端点，后端完整、界面一条都没调，是 `KNOWN_ORPHANS` 仅剩的 4 条之三：

| 端点 | 位置 | 做什么 |
|---|---|---|
| `POST /api/auth/totp/setup` | `auth.py:242` | 生成密钥（`pending:` 态），返回 `secret` + `otpauth_uri` |
| `POST /api/auth/totp/activate` | `auth.py:261` | 验一次当前验证码，通过即启用（去 `pending:` 前缀） |
| `POST /api/auth/totp/disable` | `auth.py:278` | 关闭，**须验当前验证码**（拿到会话令牌 ≠ 拿到手机） |

三条都走 `Depends(get_current_user)`，是**本人自助**，不是管理员替人操作。

### 真正的问题比"三条端点缺入口"大

清孤儿端点时逐条读代码，发现缺口不止这三条——**`totp_code` 这个词在整个前端出现 0 次**
（实扫 `server/app/static/` 全部 js/html，含管理端、居民端 `m/m.js`、医师端 `m/doctor.js`）：

1. **登录表单没有验证码输入框。**
   `index.html:15-16` 只有用户名与密码两个 input；`app.js:118` 提交的 body 也只有
   `{username, password}`。
2. **登录响应里的 `totp_setup_required` 被前端丢掉。**
   `auth.py:157` 在"角色要求双因素但本人尚未开通"时置 `true`，`app.js:119-124` 只读了
   `data.role`，这个字段无人读取。

把这两条与三条孤儿端点放在一起看，结论是：

> **双因素在前端是完全缺席的，不是"少了三个按钮"。**

于是今天的实际状态是（`config.py:188` `totp_required_roles` 默认 `""`，双因素整体旁路）：

- **运维一旦配上 `MEDPLAT_TOTP_REQUIRED_ROLES`**：该角色里**已开通**的账号会在
  `auth.py:153` 被 401 `totp_required` 拦下，而三个前端**都没有地方填那个验证码**
  ——直接锁死，且无法自助解困。
- 该角色里**未开通**的账号能登录，但收到的 `totp_setup_required` 提示被前端丢掉，
  而且即使看到了也没有入口去开通。

也就是说，**ADR-0011 选定的"按角色渐进启用"这条路，在产品上目前无法启用**：
打开开关的后果不是"多一步验证"，而是"一批人进不来"。

### 为什么现在决策

1. 这三条是孤儿端点欠账的最后一批里、唯一按规则**必须由人裁定**的（CLAUDE.md §8）。
   其余 198 条已全部接通，欠账停在 4 条（3 条本 ADR + 1 条 P1-56）。
2. **接一半比不接更危险**：只把这三条自助端点接上，人们就能开通双因素，
   而登录表单仍然没有验证码框——**开通的那一刻就是把自己锁在门外的那一刻**。
   这正是这件事不能由一次自动接线批次顺手做掉的原因。

### 约束

- **不引新依赖**（CLAUDE.md §12，运行时依赖 11 项）。二维码能力已有：
  `app/qrsvg.py` 的 `qr_svg()`（ADR-0015 打印件防伪验真用的，`qrcode` 已在依赖里，
  延迟导入）——但它是**服务端出 SVG**，前端要用就得再过一个端点。
- **不破坏登录契约**（CLAUDE.md §1.7）：`LoginOut` 现有字段与默认配置下的响应字节
  必须不变——`tests/test_esec_account.py:300` 正是钉这一条的：
  默认配置下 `"totp_setup_required" not in` 登录响应。
- **解困通道已经有了**：`POST /api/users/{id}/totp/reset`（`users.py:648`，`require_admin`
  + `assert_obj_org_writable`）已接在账号页的「重置动态口令」按钮上。
  换手机、令牌丢失有人管——这一条显著降低了开放自助开通的风险。

## Options（可选方案）

- **方案 A｜维持现状**：不接界面，双因素继续整体旁路（`totp_required_roles` 永远留空），
  等保双因素这一项以"技术具备、未启用"报备。
- **方案 B｜只接三条自助端点**：账号页加「开通/关闭动态口令」，登录侧不动。
- **方案 C｜按依赖顺序补齐三件事**（登录侧先行）：
  ① 登录表单加验证码输入（平时隐藏，收到 `totp_required` 后展开重试）；
  ② 登录响应的 `totp_setup_required` 落到界面上（提示去账号页开通）；
  ③ 账号页接三条自助端点（密钥 + otpauth 链接，本人操作）。
  三个前端（管理端 / 居民端 / 医师端）里，**管理端与医师端**走同一条
  `/api/auth/login`，两处都要改；居民端 `m/m.js` 走 portal 令牌，不受影响。
- **方案 D｜C + 服务端二维码**：在 C 之上再加一条 `GET /api/auth/totp/qrcode`
  （返回 `qr_svg(otpauth_uri)`），页面直接显示二维码而不是让人手抄密钥。
- **方案 E｜带外流程**：不做界面，由管理员用脚本生成密钥、线下交付给本人。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零改动、零风险；今天本来就是这个状态 |
| B | 改动最小（纯前端一页），孤儿欠账当场清零 |
| C | **唯一一个让双因素真正可启用的最小集合**；纯前端，不动后端、不动契约、无迁移；登录锁死的风险从根上消失 |
| D | 扫码即用，不用手抄 32 位 base32 密钥；密钥不以文本形式停留在剪贴板 |
| E | 密钥不经过浏览器；开通节奏完全由管理员控制 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 等保三级双因素这一项**始终无法落地**；`auth.py` 那套完整实现与 ADR-0011 的决策永远是死代码；孤儿欠账停在 4 条不动 |
| B | **危险**：开通即锁死——登录表单没有验证码框，开通成功的人下次登录必被 401 拦下，只能找管理员重置。**接一半比不接更坏** |
| C | 密钥与 otpauth URI 要显示在浏览器里（截图、肩窥、DOM 驻留）；要改三处前端文件；e2e 要覆盖"带验证码登录"这条新分支 |
| D | 多一条端点（孤儿闸门分母 +1，需同批带界面）；密钥经由第二条请求再出一次；`qrcode` 从"打印模块用"变成"登录链路用"，依赖面变重 |
| E | 不可规模化（几百个账号靠人工发密钥）；密钥经由聊天/邮件线下传递，**比显示在本人屏幕上更不安全**；`totp_setup_required` 提示仍然没人看得到 |

## Migration cost（迁移成本）

以**方案 C**计：

- **后端**：0。三条端点与 `app/totp.py` 已完整，`LoginIn.totp_code` 已在
  （`auth.py:110`），无新增端点、无迁移、无回填、无契约变更。
- **前端**：3 个文件。
  - `static/index.html` + `static/app.js`：登录表单加一个默认隐藏的验证码 input；
    提交时按需带上 `totp_code`；捕获 401 `totp_required` 后展开输入框并保留已填内容；
    登录成功后按 `totp_setup_required` 给一句提示。
  - `static/m/doctor.html` + `static/m/doctor.js`：同上（同一条 `/api/auth/login`）。
  - `static/pages-clinical.js` 账号页：接三条自助端点（开通两步 + 关闭）。
- **测试/守卫**：`KNOWN_ORPHANS` 划掉 3 条；`MIGRATED_PAGES` 计数同步；
  夹具补 `totp_setup_required` 两支；**`make test-e2e` 必跑**（改的是登录交互形态，
  而 e2e 的每一条用例都从登录开始，CLAUDE.md §7）。
- **量级**：半天到一天，一个批次一个提交，可与其余接线批次同口径。
- **对接方**：无。登录契约不变，默认配置下响应字节不变。

方案 D 在此之上多 1 条端点 + 1 个前端调用点（约 +2 小时）。

## Risk（风险）

**做了（方案 C）的风险**

| 风险 | 缓解 |
|---|---|
| 密钥显示在屏幕上被截图/肩窥 | 默认折叠，点"显示密钥"才展开；页面明写"只显示这一次"；不写日志、不进 URL、不落 localStorage；离开该面板即清空容器 |
| 用户开通后换手机 → 自己进不来 | **已有解困通道**：管理员「重置动态口令」（`users.py:648`）已接好；账号页在开通处就把这句话写明 |
| 登录多一个字段，改错了影响**所有人**登录 | 验证码框默认隐藏、留空即不送该键（后端 `totp_code: str \| None`，`totp_required_roles` 为空时整段旁路）；e2e 全部用例都过登录，改坏了必红 |
| 时钟漂移导致验证码不过 | 已有 ±1 个时间窗容差（`totp.py:verify` 默认 `window=1`）；界面错误文案照抄后端的"请确认令牌App时间与密钥无误" |

**不做（方案 A）的风险**

- 等保三级的双因素鉴别项**无法验收**——不是"没做"，是"做了但用不了"，
  这在整改复查时比没做更难解释。
- `auth.py:225-289` 与 `app/totp.py`（含 RFC 4226/6238 官方测试向量）成为死代码，
  随时间腐化；ADR-0011 里"按角色渐进启用"的决策事实上被架空。
- **最坏的一种**：有人不知道前端没有验证码框，直接配上
  `MEDPLAT_TOTP_REQUIRED_ROLES` 想"打开双因素"——在生产上把一批账号锁在门外。
  这个风险**今天就存在**，且一个配置项即可触发。
  → 无论本 ADR 选哪个方案，建议**立即**在 `docs/运维手册.md` 与
  `server/scripts/preflight_check.py` 里加一条：前端未接入前，该开关必须留空。

## Recommendation（建议）

**建议采纳方案 C，并把 D 作为 C 落地后的可选增强。**

理由：

1. **C 是让双因素真正可启用的最小集合**，而 B 是本批次唯一"做了比不做更坏"的选项
   ——这也是这三条端点当初被暂缓、而不是顺手接掉的原因。
2. C 是**纯前端**改动：不动后端、不动契约、无迁移、无回填。
   安全评审要审的只有"密钥怎么显示给本人"这一件事，面很窄。
3. 解困通道（管理员重置）**已经就位并已有界面**，开放自助开通的兜底不是新建的。
4. D 的二维码体验更好，但它引入一条新端点，并把 `qrcode` 从打印模块拉进登录链路；
   先把 C 跑通、密钥展示口径被评审认可之后再加，顺序上更稳。

**落地第一步**（需批准后执行）：

1. 先加运维护栏（不依赖本 ADR 结论，建议立即做）：
   `docs/运维手册.md` + `server/scripts/preflight_check.py` 明写
   "`MEDPLAT_TOTP_REQUIRED_ROLES` 在前端接入前必须留空"，并让体检脚本在非空时报警。
2. 再按 ① 登录侧 → ② 提示 → ③ 账号页自助 的顺序做，**一个批次一个提交**；
   每批 `make verify` + `make test-e2e`。
3. 三条端点从 `KNOWN_ORPHANS` 划掉放在 ③ 那一批，**不提前划**
   ——划掉意味着"有入口了"，而在 ① 之前那个入口是个陷阱。

**需要谁批准**：安全负责人（密钥展示口径）+ 运维（开关启用节奏）。
本 ADR 只给建议，不替人做决定；采纳前 `KNOWN_ORPHANS` 里那三条与其旁注保持原样。
