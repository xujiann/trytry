# ADR-0017：运行时依赖锁定（requirements.lock 钉版快照）

- 状态：**Accepted**（实现已随 A7 发布流水线批次落地；本 ADR 补记 TECH_DEBT
  P2-29 登记时要求的决策记录，并补上防腐化守卫）
- 日期：2026-08-28
- 决策者：仓库所有者
- 相关：`docs/TECH_DEBT.md` P2-29（实测事故形态）、`server/requirements.lock`
  （文件头含再生成步骤）、两个 Dockerfile、`.github/workflows/{ci,build}.yml`、
  `tests/test_dependency_lock.py`（防腐化守卫）、CLAUDE.md 第 12 条
  （13 项运行时依赖、无理由不新增）

## Problem（问题）

`requirements.txt` 的 13 项运行时依赖全是下界钉（`>=`）——**装到什么版本是
构建时刻的函数，不是仓库内容的函数**。已实测到一例真实分歧：`redis>=5.0`
区间下，redis-py 5.0.0 的 `socket_timeout` 默认 `None`（出网永久挂起），
8.1.0 默认 5 秒；同一份代码在两次构建里装出两种行为，而这条路挂在每个请求
的主路径上（state_store 热路径）。就地修（显式超时 + AST 棘轮
`test_outbound_timeout_guard.py`）只堵住 redis 这一处；其余 12 项依赖藏着
什么版本敏感默认值，没人知道。

约束：不引入新的包管理工具链（CLAUDE.md 第 12 条的克制口径同样适用于
构建工具）；开发体验不变（本地 `pip install -r requirements.txt` 还得能跑）；
安全扫描（pip-audit）要扫得到实际部署的版本集合。

## Options（可选方案）

- **方案 A（维持现状）**：只下界钉 + 逐处就地写死危险默认值。
- **方案 B（freeze 快照，选定）**：干净 venv 解析 requirements.txt 后
  `pip freeze` 出 `requirements.lock`（含全部传递依赖、全 `==`），镜像与 CI
  一律装 lock；requirements.txt 保持区间声明作为**约束真源**。
- **方案 C（pip-compile / pip-tools）**：requirements.in → pip-compile 生成
  带 hash 的锁。
- **方案 D（迁移 uv / poetry）**：换包管理器，用其原生 lock。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零流程改动 |
| B | 零新工具（pip 自带 freeze）；可复现构建立即生效；传递依赖也钉住；pip-audit 扫 lock 即扫实际部署集合；再生成步骤四行命令写在文件头 |
| C | 锁带 `--hash`（抗仓库投毒）；升级单项依赖有原生命令 |
| D | 解析快、锁格式现代、工具链统一 |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | "不吃库默认值"永远铺不满：每个新版本都可能带新的行为默认值，逐处堵是无底洞 |
| B | 无 hash 校验（信任 PyPI 传输层）；再生成靠纪律（文件头步骤 + 守卫测试兜底）；lock 是"某次解析的结果"而非"约束求解的最优解" |
| C | 引入 pip-tools 依赖与其版本自身的锁定问题；hash 模式下任何平台差异（sdist/wheel）都会装不上，对 3.11 本地 / 3.12 CI 的现状要先统一 |
| D | 迁移面最大（Dockerfile/CI/文档/开发者习惯全动），与"13 项依赖的单体"体量不成比例 |

## Migration cost（迁移成本）

方案 B 实际成本（A7 批次已付）：生成 `requirements.lock`（文件头带四行
再生成步骤）；两个 Dockerfile 与 CI 的 4 处安装点改装 lock；`pip-audit`
改扫 lock。本批次补充：防腐化守卫 `tests/test_dependency_lock.py` 三条
（直接依赖必须全部入锁 / 锁内必须全钉版 / 安装点必须走锁不得旁路），
三处变异验证转红。

## Risk（风险）

- **做的风险**：锁会腐化——加依赖忘再生成（守卫一挡）、锁里混进区间
  （守卫二挡）、安装点改回装区间（守卫三挡，这条最阴：本地与 CI 照绿，
  只有生产漂移）。再生成时的升级风险由既有门禁承接（`make verify` +
  CI 全阻断）。
- **不做的风险**：redis 超时事故的形态在其余 12 项依赖上重演，且下次未必
  这么好定位（那次是永久挂起，够醒目；默认值悄悄变个排序/编码就没这么幸运）。
- **接受的缺口**：无 `--hash` 供应链校验（方案 C 的能力）——当前威胁模型下
  接受传输层信任；若日后要上，在 lock 已存在的基础上换 pip-compile 生成即可，
  安装点不用再动。

## Recommendation（结论）

**方案 B**。它用零新工具拿到可复现构建的全部主干收益；C 的 hash 与 D 的
工具链现代化都是可以日后在 B 之上增量补的，而 B 不落地，每一天的构建都在
掷骰子。锁的三种腐化方式已各有守卫，纪律不靠自觉。

## 后记（2026-08-31，P2-26④：测试工具移出运行时依赖）

本 ADR 落地时 lock 是对当时 requirements.txt 的全量 freeze，而当时的
requirements.txt 混着 pytest/pytest-cov——于是测试工具连同其传递依赖随 lock
进了生产镜像（TECH_DEBT P2-26④）。本次把两者移入 `requirements-dev.txt`
（钉版平移：`pytest==9.1.1`、`pytest-cov==7.1.0`），运行时依赖 13→**11 项**，
并按文件头四步重新生成 lock：随之从锁里消失的还有只被测试工具拉进来的
coverage/iniconfig/packaging/pluggy/Pygments 五项传递依赖。安装口径相应调整：
两个 Dockerfile 仍只装 lock（不变，镜像从此不含测试工具）；CI 里**跑 pytest 的
job**（ci.yml `test`、build.yml `test`）从"只装 lock"改为"装 lock + dev"，
与 quality/e2e 两个 job 既有口径一致——运行时各包仍按 lock 钉住，dev 只补测试
工具。本 ADR 正文里的"13 项"是决策时点的事实，保留不改。
