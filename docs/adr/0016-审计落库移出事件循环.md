# ADR-0016：审计落库移出事件循环（await run_in_threadpool）

- 状态：**Accepted**（实现随本 ADR 同批落地；动的是审计链写入路径，按 CLAUDE.md §8/§9 留档待人工复核）
- 日期：2026-08-28
- 决策者：仓库所有者
- 相关：`docs/TECH_DEBT.md` P2-30（登记时的实测数据）、`app/main.py`
  `audit_middleware`/`_write_audit`、`tests/test_audit_middleware_hardening.py`
  （链尾串行化 + 故障隔离 + 本决策的 AST 钉）

## Problem（问题）

`audit_middleware` 是 `async def`——跑在 uvicorn 的事件循环上；它直接同步调
`_write_audit`：开会话、查 `users`、读链尾、算哈希、插行、commit，全程不让出。
实测（SQLite、无 advisory lock）单次**中位 2.49ms / p90 2.77ms / 最大 5.11ms**，
挂在**每个写请求**（POST/PATCH/PUT/DELETE）上。事件循环被占住的毫秒里，
**全部在途请求**（包括纯读、包括健康检查）都冻着。

生产 PG 更重：`_write_audit` 还要先拿 `pg_advisory_xact_lock` 把审计链写入
跨实例串行化——锁等待也发生在事件循环上，等于让各实例的事件循环互相排队。

约束：审计是写操作全量留痕（M2 整改），**"响应返回时本条审计已尝试落库"**
与**"审计失败不拖垮业务响应"**两条既有保证都不能变；链尾串行化（advisory
lock / 进程锁）已由 `test_audit_middleware_hardening.py` 钉住，不能破坏。

## Options（可选方案）

- **方案 A（维持现状）**：继续在事件循环上同步写。
- **方案 B（await run_in_threadpool，选定）**：`await run_in_threadpool(
  _write_audit, ...)`——落库挪到 anyio 线程池，事件循环立即让出；**本请求**
  仍等审计完成才返回。
- **方案 C（fire-and-forget）**：`asyncio.create_task`/后台线程扔进去不等。
- **方案 D（进程内队列 + 批量写）**：审计进内存队列，独立消费线程攒批落库。

## Advantages（各方案优点）

| 方案 | 优点 |
|---|---|
| A | 零改动；语义最直白 |
| B | 事件循环彻底解放（其余请求不再陪等）；**两条既有保证一字不变**（本请求仍等落库完成、异常仍在 `_write_audit` 里吞掉）；改动 3 行；串行化/故障隔离机制原样复用 |
| C | 本请求也不等了，写请求延迟再降 ~2.5ms |
| D | 吞吐最高；PG advisory lock 竞争消失（单消费者天然串行） |

## Disadvantages（各方案缺点）

| 方案 | 缺点 |
|---|---|
| A | 每个写请求冻结全实例事件循环 2.5ms+，PG 下加锁等待放大 |
| B | 写请求自身延迟不变（它本来就要等）；审计写占用线程池工位（与 FastAPI 跑同步端点同一个池，默认 40）——极端审计锁竞争下挤占其他同步工作 |
| C | **"响应返回时已尝试落库"消失**：进程崩溃/重启时已返回 2xx 的写操作审计丢失且无日志；create_task 还会在高峰积压无界任务 |
| D | 同 C 的持久化窗口问题，外加：新增常驻消费线程与有界/无界队列的治理、优雅停机时的排空逻辑——为 2.5ms 引入一个新的有状态组件 |

## Migration cost（迁移成本）

方案 B 实际成本（已落地）：`main.py` 两处调用点改 `await run_in_threadpool(...)`
+ 一行 import；`_write_audit` 本体、串行化锁、吞异常路径**零改动**。
测试侧：既有 6 条硬化用例原样通过（并发链完整性、故障注入业务不受累）；
新增 1 条 AST 钉（不得直调 + 两条路径都必须 await），两处变异验证转红。

## Risk（风险）

- **做的风险**：审计与同步端点共用 anyio 线程池（默认 40 工位）——写风暴 +
  advisory lock 竞争时审计占住工位。但同样的等待此前发生在事件循环上，
  是严格更坏的形态（冻全部 vs 占一工位）；池耗尽的表现是排队而非丢审计。
  monkeypatch 类测试不受影响：线程池里按名字解析的仍是 `main_mod` 的模块
  全局。
- **不做的风险**：写并发一上来，事件循环成为全实例的单点瓶颈；PG 生产形态
  下各实例互相拖慢，且这种"整体变钝"很难从单个请求的表象定位回审计中间件。
- **C/D 的诱惑要挡住**：它们省的是**本请求**的 2.5ms，代价是审计完整性从
  "同步保证"降级为"尽力而为"——对一条防篡改链，崩溃窗口里的静默丢失比
  慢更不可接受。AST 钉里专门断言 await 存在，防有人"顺手优化"掉。

## Recommendation（结论）

**方案 B**。它是唯一在不动任何既有保证的前提下解决"陪等"问题的选项；
C/D 换来的请求延迟收益（~2.5ms）买不回审计链的持久化保证。若日后实测
线程池工位成为瓶颈，再评估 D（届时带上停机排空设计），两步不冲突。
