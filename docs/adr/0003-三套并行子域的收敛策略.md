# ADR-0003：三套并行子域（慢病/专病/慢专病）的收敛策略

- 状态：**Accepted**（2026-08-20 批准，采纳推荐的两阶段方案）
- 日期：2026-08-18（提出）/ 2026-08-20（批准）
- 决策者：仓库所有者
- 相关：`docs/DATA_MODEL.md §2`、`docs/TECH_DEBT.md`、`docs/模块分级_KEEP_IMPROVE_REFACTOR_REPLACE.md`（C 类）、`docs/特征化测试指引.md`

## Problem

同一业务概念存在三套并行实现，是本仓库头号结构债：

| 概念 | 慢病 | 专病 | 慢专病 |
|---|---|---|---|
| 病种目录 | `chronic_disease_types` | `disease_programs` | `spd_programs` |
| 患者入组 | `chronic_patients` | `disease_enrollments` | `spd_enrollments` |
| 随访 | `followups` | — | `spd_followup_*` |
| 转诊 | `referrals` | — | `spd_referral_*` |

后果实测：`chronic_seed` 与 `spd/seed` 用**相同病种码**（`hypertension`/`diabetes`）写不同表、各带阈值，统计口径必然对不上；居民端 `/api/portal/me/referrals` 与 `/api/portal/spd/referrals` 返回两份互不相交列表（数据孤岛）。约束：三套都已上线、都有数据、慢专病是独立可卸载子系统（`MEDPLAT_SPD_ENABLED`），且核心表已冻结（ADR-0001）。

## Options

- **方案 A：维持三套并行**（现状，文档标注"口径不同、并行运行"）。
- **方案 B：读侧聚合，写侧不动**——建统一读模型/视图，让居民端与统计跨三套取数并去重，底层表不合并。
- **方案 C：逐步收敛到单一权威**——选一套为权威（如 spd 作为"全域"底座），慢病/专病经适配层写入或迁移过去，旧表进入只读→废弃。
- **方案 D：立即合并重写**——一次性把三套合成一套新模型。

## Advantages

| 方案 | 优点 |
|---|---|
| A | 零风险零成本，不动上线数据 |
| B | 消除"用户看到两份列表"的最痛点，不碰写路径与迁移，风险可控 |
| C | 根治重复，长期维护成本最低，口径统一 |
| D | 一步到位 |

## Disadvantages

| 方案 | 缺点 |
|---|---|
| A | 债继续累积，口径分叉、孤岛长期存在 |
| B | 底层重复仍在；聚合层要处理三套去重与冲突，是新代码 |
| C | 周期长、需跨表数据迁移与口径对齐；触及子系统边界（spd 单向依赖）需重新论证 |
| D | 违反"不重写可运行模块"；丢失三套各自积累的测试与数据；停机与回归风险极高 |

## Migration cost

- A：0。
- B：中。新增聚合读接口/视图 + 去重规则；不写迁移、不动存量数据；估数天到两周，按概念（先转诊、再病种）分批。
- C：大。每个概念一条迁移链 + 数据搬迁 + 口径映射 + 双写过渡期；估数月，需现场配合核对数据。
- D：极大且不可分批，不评估。

## Risk

- B 风险低：只读叠加，错了不污染源数据；主要风险是去重规则与业务口径不一致 → 用特征化网钉住每套现状后再叠加。
- C 风险中高：跨表迁移可能丢关联、口径对齐易出错 → 必须"先特征化网、再双写、再切读、最后废旧表"，每步可回滚。
- 不做（A）的风险：孤岛与口径分叉随数据量放大，且新功能会被迫再"选一套或又加一套"。

## Recommendation

分两阶段：
1. **先采纳方案 B**（读侧聚合），**优先消除居民端两套 `referrals` 的数据孤岛**——这是用户可感知、且不碰写路径的最高性价比一步。落地前先给三套各写特征化网（`docs/特征化测试指引.md`）。
2. **中期评估方案 C**：以慢专病 `spd_*` 为"全域"权威底座、慢病/专病逐步收敛，作为独立 ADR 立项（涉及子系统边界与跨表迁移，需三方评审）。

**否决方案 D**（一次性重写）：违反仓库增量原则、风险与停机代价不可接受。本 ADR 仅定方向，B/C 的实施各自另开任务。

## 决议与落地记录（2026-08-20）

采纳 Recommendation 的两阶段方案：**先 B、中期再评估 C，否决 D**。

### 第一阶段（方案 B · 读侧聚合）——转诊的**接口侧**已落地

- 新增 `GET /api/portal/me/referrals/all`：把平台 `referrals` 与
  `spd_referral_cases` 并成一份列表，消除居民端"看到哪一份取决于点了哪个入口"。
- 两个老接口（`/api/portal/me/referrals`、`/api/portal/spd/referrals`）
  **响应字节原样不动**，由特征化用例钉住（`tests/test_referral_feed_aggregation.py`）。
- **注册制而非直接 import**：平台不能 import 子系统（依赖方向由
  `tests/test_spd_boundary.py` 的 AST 扫描强制）。子系统装载时经
  `spd/platform.register_referral_source` 把自己的读取函数登记进来；
  子系统关掉，聚合接口只剩平台一个源，照常工作。

### 一个实施中确认的事实：**这里不需要去重**

ADR 正文的 Disadvantages 里写了"聚合层要处理三套去重与冲突"。就转诊而言，
实施时核对下来**并不存在重复**：spd 从不写 `referrals`，`SpdReferralCase` 的
docstring 也写明"不复用既有 `referrals`"——那张表是两点之间的一次转诊，
而 spd 要的是村→乡→县的链路。两批单子真正不相交，所以这一步是 **union 而非 merge**，
硬加一条去重规则只会凭空造出误判。

真正要处理的不是重复，而是**口径分叉**：两套状态码**同名不同义**——
平台 `accepted` 是"已接诊"，spd `accepted` 是"县级已接收"。聚合层的做法是
每条都带 `source`、标签分源映射，如实呈现分歧而不假装它们是一回事
（`test_两套accepted同名不同义_靠source分辨` 钉住这一点）。

### 尚未做的（重要：孤岛尚未真正消除）

- **居民端还没切过来**。`static/m/m.js` 目前仍分别调 `/api/portal/me/referrals`
  与 `/api/portal/spd/referrals`，两个页面各渲染各的——**用户可感知的那个数据孤岛
  依然存在**，本次只落了接口侧。切换是居民端可见的 UI 改动，单独一个任务做；
  切过来时前端那两张标签表（`REFERRAL_STATUS` / `SPD_REF_TEXT`）可以删掉，
  直接用后端的 `status_label`。
- 病种目录、患者入组、随访三个概念的读侧聚合（本次只做转诊）。
- `docs/API_MAP.md` 仍把两套 referrals 描述为孤岛，待居民端切换后一并更新。
- 第二阶段（方案 C，收敛到单一权威底座）仍待独立 ADR 立项。
