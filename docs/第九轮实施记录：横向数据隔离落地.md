# 第九轮实施记录：横向数据隔离落地

计划见《第九轮开发计划：横向越权与数据隔离》。口径 A 案（默认本机构，
跨机构需业务关系）。本文记录实施中的关键决策与被测试纠正的判断——
照例，**漏了什么、错了什么比做了什么更值得留档**。

## 一、交付

- `app/visibility.py`：可见范围模型。患者维度按业务关系判定
  （global/self/encounter/service/contract/referral/authorization），
  机构维度分明细（本机构）与统计（医共体）两档；
- `access_logs` 表：敏感读留痕，判定与留痕绑在同一次调用；
- 患者维度 31 个业务接口：29 个纳入可见性（93.5%），2 个写明理由；
- 机构维度 48 个收 org_id 的 GET：44 个纳入作用域，其余 4 个中
  1 个（冷链）按统计口径收、3 个写明"按业务设计不设限"的理由；
- 横向越权矩阵测试：16 条用例，患者与机构两个维度都逐个真发请求验证。

## 二、三个被测试当场纠正的判断

**1. 患者可见性第一版只认"就诊过"——临床视角，漏掉公卫。**
县域里卫生院与村卫生室干的大量是公卫：建档体检、慢病管理、接种。这些居民
常常一条 `Encounter` 都没有，真按"就诊过"判，管了三年高血压的村医反而
看不到自己管的人。改为从模型元数据推导（28 张同时带 patient_id 与机构外键
的表都算服务关系），不手工枚举。

**2. FHIR 出站导出加关系判定——把对接功能关掉了。**
那是出站对接接口，调用方是区域平台一侧的对接账号，按设计就要能导出全县
任意患者。改回只留痕（basis=export）。遗留项：对接账号该有单独一类身份并
声明导出范围，不该复用 operator 这个人的角色。

**3. 拒绝断言用乙院医生——被"下转"用例污染。**
乙院在转诊用例里拿到了关系，后面的拒绝断言跟着变绿。可见性本来就随业务
推进变化，断言"拒绝"必须用一个状态永不变化的机构。

## 三、撞出的数据模型缺口

就诊凭据、妇女保健、老年评估三张表只有 patient_id，没有"这条服务是哪家
机构做的"。后果成环：发卡机构因为发卡动作没记机构，反而看不到自己发的卡。
补 org_id（可空，存量不编造），三张表随即被关系推导自动认作服务关系。
县外就诊登记（OutboundVisit）不补——那本来就发生在县外，没有县内机构。

## 四、几条口径，防止以后被"顺手统一"掉

- **筛选器不是授权器**。`resolve_org_scope` 解析"想看哪个机构"，
  `scope_org_list` 校验"能不能看"。两者长得像，正因如此才要写下来。
- **明细与统计分两档**。明细=本机构，统计=医共体。牵头医院看片区汇总是
  医共体的管理职能；但拿统计范围查明细，就是把隔离拆了。
- **拒绝时 403 明说，不悄悄返回空**。悄悄返回空会让人以为那家机构没数据，
  转头去翻别的入口；例外是"不带参数的清单"，那是缩范围不是拒绝。
- **被拒的调阅不写留痕**。access_logs 是"谁看了什么"，不是"谁试过"；
  试探行为由写审计覆盖。混在一起，这张表就没法直接用于合规举证。
- **按业务设计跨机构的，开放要写理由**：寻医目录、分组拓扑、手术间撮合、
  互认查询、授权办理、FHIR 导出。开放不是默认，是决定。

## 五、覆盖率（实测口径）

```
患者维度：31 个业务接口 = 已纳入 29 + 白名单 2（get_patient 身份检索 / FHIR 导出）
机构维度：48 个收 org_id 的 GET = 已纳入 44 + 统计口径 1 + 不设限 3（各有理由）
矩阵用例：16 条，全部真发请求；守卫验过非空洞（还原旧写法立刻变红）
```

尚未覆盖（登记为下一轮欠账）：

- 21 个 GET 内部用到 org_id 但不收该参数的（多为聚合统计），未逐一核对口径；
- 写接口（POST/PUT/DELETE）的机构归属校验——现在乙院账号仍可能替甲院
  写数据（如给甲院建职工），纵向矩阵只管角色不管机构；
- 详情接口（`/{id}` 型）按 id 直取的横向校验。
