# 第九轮实施记录：横向数据隔离落地

计划见《第九轮开发计划：横向越权与数据隔离》。口径 A 案（默认本机构，
跨机构需业务关系）。本文记录实施中的关键决策与被测试纠正的判断——
照例，**漏了什么、错了什么比做了什么更值得留档**。

## 一、交付

- `app/visibility.py`：可见范围模型。患者维度按业务关系判定
  （global/self/encounter/service/contract/referral/authorization），
  机构维度分明细（本机构）与统计（医共体）两档；
- `access_logs` 表：敏感读留痕，判定与留痕绑在同一次调用；
- 患者维度 31 个业务接口：29 个纳入可见性（93.5%），2 个写明理由；
- 机构维度 48 个收 org_id 的 GET：44 个纳入作用域，其余 4 个中
  1 个（冷链）按统计口径收、3 个写明"按业务设计不设限"的理由；
- 横向越权矩阵测试：16 条用例，患者与机构两个维度都逐个真发请求验证。

## 二、三个被测试当场纠正的判断

**1. 患者可见性第一版只认"就诊过"——临床视角，漏掉公卫。**
县域里卫生院与村卫生室干的大量是公卫：建档体检、慢病管理、接种。这些居民
常常一条 `Encounter` 都没有，真按"就诊过"判，管了三年高血压的村医反而
看不到自己管的人。改为从模型元数据推导（28 张同时带 patient_id 与机构外键
的表都算服务关系），不手工枚举。

**2. FHIR 出站导出加关系判定——把对接功能关掉了。**
那是出站对接接口，调用方是区域平台一侧的对接账号，按设计就要能导出全县
任意患者。改回只留痕（basis=export）。遗留项：对接账号该有单独一类身份并
声明导出范围，不该复用 operator 这个人的角色。

**3. 拒绝断言用乙院医生——被"下转"用例污染。**
乙院在转诊用例里拿到了关系，后面的拒绝断言跟着变绿。可见性本来就随业务
推进变化，断言"拒绝"必须用一个状态永不变化的机构。

## 三、撞出的数据模型缺口

就诊凭据、妇女保健、老年评估三张表只有 patient_id，没有"这条服务是哪家
机构做的"。后果成环：发卡机构因为发卡动作没记机构，反而看不到自己发的卡。
补 org_id（可空，存量不编造），三张表随即被关系推导自动认作服务关系。
县外就诊登记（OutboundVisit）不补——那本来就发生在县外，没有县内机构。

## 四、几条口径，防止以后被"顺手统一"掉

- **筛选器不是授权器**。`resolve_org_scope` 解析"想看哪个机构"，
  `scope_org_list` 校验"能不能看"。两者长得像，正因如此才要写下来。
- **明细与统计分两档**。明细=本机构，统计=医共体。牵头医院看片区汇总是
  医共体的管理职能；但拿统计范围查明细，就是把隔离拆了。
- **拒绝时 403 明说，不悄悄返回空**。悄悄返回空会让人以为那家机构没数据，
  转头去翻别的入口；例外是"不带参数的清单"，那是缩范围不是拒绝。
- **被拒的调阅不写留痕**。access_logs 是"谁看了什么"，不是"谁试过"；
  试探行为由写审计覆盖。混在一起，这张表就没法直接用于合规举证。
- **按业务设计跨机构的，开放要写理由**：寻医目录、分组拓扑、手术间撮合、
  互认查询、授权办理、FHIR 导出。开放不是默认，是决定。

## 五、覆盖率（实测口径）

```
患者维度：31 个业务接口 = 已纳入 29 + 白名单 2（get_patient 身份检索 / FHIR 导出）
机构维度：48 个收 org_id 的 GET = 已纳入 44 + 统计口径 1 + 不设限 3（各有理由）
矩阵用例：16 条，全部真发请求；守卫验过非空洞（还原旧写法立刻变红）
```

## 五之二、写侧（第四批补）

实测：乙院的 director 能给甲县医院**记一笔 88888 的支出**、建假职工——
写侧的洞比读侧重，这是在替别家做账。

新增 `assert_org_writable`：非全域角色只能以本机构名义写。与读侧分成两个
函数（虽然此刻实现几乎一样）：读与写的口径将来多半会分化，合在一起到时
就得在每个调用点回忆当初是读是写。**写永远不用统计那档**——统计是看得宽，
写不能宽。

43 个写接口套上守卫；4 个豁免写明理由（分组成员管理、建用户、建专病目录
——均为 require_admin 的拓扑/账号管理，org_id 指"被管理的机构"而非
"以谁的名义写"）。

两处自己踩的坑，留档：

1. 批量插入守卫时偏移量算错，3 处守卫**掉进了多行 docstring**——语法合法、
   lint 只报出其中 2 处（另 1 处因文件里别处用到同名导入而不报 unused）。
   靠 AST 扫"docstring 里含守卫字样"才找全 3 处。教训与第八轮同型：
   验证改动落没落上，要看 AST 里的真实语句数（43），不能看文本出现次数。
2. 写侧拒绝用例第一版用医生账号——建职工这类接口的**角色守卫本来就拒医生**，
   用例因角色而绿，机构守卫删掉它也不红。改用能过角色关的经办账号，
   且断言只认"机构名义"字样的 403，不认角色 403。

## 五之三、按 id 写（第五批补）——最隐蔽的一条

清单接口做了机构过滤，但 `/{id}` 型接口从 id 直取对象、跳过清单，
过滤形同虚设。实测：乙院经办按 id **领走了甲院 5 台 CT、交接了甲院医废、
停用了甲院暂存间**。

新增 `assert_obj_org_writable`：对已取出的对象校验归属。53 个按 id 直取
带 org 主对象的写接口，逐个在"取对象、判 404"之后插入守卫。

**测试当场纠正了两处过界**——这一批最值得记的不是补了多少，是喷得太宽：

1. **集中审方被误拦**。`review_prescription` 加守卫后，lead 医院药师审
   member 卫生院的处方直接 403——而这正是"集中审方中心"的核心业务。
   `test_rbac` 当场变红把它照出来。集中审方（2 个接口）与远程会诊
   （2 个接口）都是 lead-支援-member 的协同，机构写守卫会把功能关掉，
   撤回并登记为显式豁免。
2. **DRG 多机构统计用例**用单机构医生替多家机构写入院——那正是守卫该拦的。
   改为跨机构测试数据走 admin 播种（全域）。手术、DRG 病案的 fixture 则是
   业务账号没挂机构，补挂即可（院内流程，本就该本机构写）。

方法上再记一次同型教训：自动插守卫时，先用 AST 数"作为真实语句的守卫数"
（55），确认没有一处掉进 docstring；再靠全量测试把"喷宽了"的那几处逼出来。
喷 53 处不可能全对，靠的是测试兜底，不是靠改的时候想周全。

新增两条矩阵用例并验非空洞：按 id 拒绝别家（领资产/交接医废/停点位逐个
403）、集中审方不被机构守卫拦（反向断言，防止把豁免误加回去）；另立一条
扫描用例把按 id 欠账钉死在"只剩 4 个跨机构协同接口"，多一个就红。

至此写侧三条路（创建、更新/推进、按 id）全部收口。

## 五之四、聚合与运营清单（第六批补，收尾）

登记在案的最后一项："内部用 org_id 但不收该参数"的 18 个 GET。逐个过了一遍，
分成三类，只有一类是真漏：

1. **运营明细清单**（真漏，已修）：CSSD 请求、采购单、缺药预警、用血申请——
   不收 org_id、不过滤，任意账号一拉就是全县的。实测 CSSD 当场漏甲院一条。
   这些不是聚合数，是一条条带机构的明细，改用 scope_org_list 按可见机构过滤。
2. **县域监测**（按设计跨机构，不动）：多点触发预警**定义上**就要跨机构
   （涉及机构数≥2 才升级），一线医生也该看得到"辖区有没有暴发"。
   把它限到本机构等于把这个功能删了——这是整轮里最不能过度收紧的一条。
   迟报清单同理。
3. **管理聚合**（聚合数，非明细）：DRG 统计、基金统计、手术统计——
   给的是各机构的例数/均费/结余这类聚合数，不含患者明细也不能写。
   按既定口径"统计走更宽的范围"，不加机构墙；是否再按角色收紧
   （乡镇经办要不要看全县基金结余）是**角色策略**问题，与数据隔离正交，
   本轮不在此处叠加，登记待管理侧定策略。

判据分清楚"明细还是聚合"是这一批的关键：明细漏一条就是泄露，
聚合数是医共体管理本来就要看的。混在一起要么漏、要么把监测功能关掉。

至此横向隔离读、写两个方向闭合，登记的欠账清零（余下 4 个跨机构协同接口
与 3 类管理聚合均写明理由，非欠账）。
