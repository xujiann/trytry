# 特征化测试指引（重构前的安全网）

```
   LEGACY CODE  ───▶  TEST PROTECTION  ───▶  REFACTOR
   （要改的遗留代码）   （特征化测试钉住现状）   （在网内安全重构）
```

本仓库有大量"能跑但没测、且是重构候选"的遗留逻辑（见 `docs/TECH_DEBT.md`）。
直接重构它们风险高：没有测试就无法证明"重构前后行为一致"。**特征化测试
（characterization / golden-master test）** 是标准解法——在动代码之前，先写一层
测试把**当前实际行为钉死**，重构时行为一变就报警。

## 与普通单元测试的区别

- 普通单元测试断言"代码**应该**怎么做"（按需求/规格）。
- 特征化测试断言"代码**现在实际**怎么做"（按现状，含怪癖）。

因此特征化测试**必须对当前代码全绿**——它捕捉的是现实，不是理想。若某条断言
对当前代码是红的，说明你写错了现状，改断言去迁就代码，而不是反过来。

## 三步法

1. **选目标**：纯逻辑、分支多、无测试、且计划要动的模块最理想。
2. **钉现状**：为每条路径写断言并跑绿；反直觉的行为要显式标注「⚠ 现状怪癖」并钉住——
   那正是重构最容易悄悄改掉的地方。
3. **验证网会咬**：临时改一行被测逻辑，确认对应断言变红，再还原——证明保护有效
   （不要把这次临时改动提交）。之后重构就有了安全网。

重构时若特征化断言变红：要么是回归，要么是**有意**修正行为。无论哪种，都必须是
一次被看见的决定——先改被测行为、并**同步更新断言与其注释说明为何变**，而不是
悄悄漂移。
