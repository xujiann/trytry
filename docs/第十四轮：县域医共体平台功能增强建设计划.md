## 方法与基线

对 `server/app` 全量做四路能力盘点（分析/集成/AI、临床决策/知识、居民端、医共体治理/医保/公卫/药械），
只登记有代码证据的现状与缺口。基线结论：

- **广度已满**：36 主项 / 379 子功能对照国家《功能指引》、浙江省 82 条指南均已落地
  （见 `docs/功能指引对照表.md`、`docs/浙江省指南第二次全量对照…md`），`pytest` 全绿。
- **深度不均**：平台在"记录/流程/统计"层完备，但在**医共体之所以"紧密"的四根支柱**上偏薄——
  ①家医签约"按人头"、②医保支付"总额+点数"、③分级诊疗"闭环随转"、④公卫"全人群兜底"。
  这四处正是把"联合体"焊成"共同体"的着力点。
- **智能层缺位**：`analytics/metrics/drgs/cost/performance` 全是描述性聚合与阈值规则；
  全代码库无任何 ML/预测/画像库（grep 确认无 sklearn/numpy/pandas/torch 等），
  唯一的"风险分"（`chronic.py:325`）是固定查表 ±固定调整。

> 判定原则：凡"纯平台侧业务逻辑 + 建表 + 接口"即可完成的，列为**可落地**（本团队十三轮一直在做这件事）；
> 凡需实时音视频、DICOM 影像共享、外部 HIS/LIS/医保/省平台实盘联调、密码机的，列为**外部依赖项**，
> 只登记不排期。

## 一、四梯队增强计划

### 第一梯队 · 让"紧密"落到实处（最高价值，纯后端可落地）

#### E1　家庭医生签约：服务包内容化 + 履约率 + 签约费按人头分配
**现状证据**：`contracts.py` 的 `package` 是 `basic|standard|premium` 的**不透明枚举**；
`ContractService` 是自由文本履约流水，**无"应履约 vs 已履约"对比、无履约率**；
**全代码库无"签约费"字段**（`performance.py` 无签约费/人头绩效）。签约与 `fund.py`/`performance.py` 无联动。

**建设内容**：
1. **服务包目录化**：`ServicePackage`（包码/名称/年费/适用人群）+ `ServicePackageItem`
   （服务项/类型/年度应履约次数/是否计价）。签约挂包码而非枚举。
2. **履约闭环**：由服务包条目派生"应履约清单"，`ContractService` 履约核销到具体条目，
   自动算 `履约率 = 已履约/应履约`；到期未履约进预警。
3. **签约费与按人头付费**：签约费池按有效签约人头计提，年终结合履约率 + 重点人群系数分配——
   **直接复用 `fund.py` 已验证的 Hamilton 余数法 + 绩效快照冻结分配引擎**，不重造轮子。
4. **重点人群 targeting 与续签周期**：签约打"重点人群"标签（慢病/老年/孕产/残疾…），
   年度续签/到期提醒（复用 `staff-contracts/expiring` 同款到期清单模式）。

**价值**：家医签约"按人头付费、履约挂钩"是紧密型医共体两大支付支柱之一，
当前是最薄弱环节，补齐后签约从"签个名"变成"有钱、有事、有考核"。

#### E2　医保支付方式改革落地：DRG/DIP 实际结算 + 医保智能审核
**现状证据**：`drgs.py` **只做分组分析（CMI/组均费/入院预判/在院超期提示），不做结算**——
无基准点数/费率、无病组支付。**全库无 DIP**（grep 点数/病种分值/带量均无）。
`insurance.py fund-stats` 只有比例统计，**无规则化违规/欺诈识别（智能审核）**。

**建设内容**：
1. **DRG 点数法结算**：`DrgRate`（年度费率/基准点数）+ 病组权重 → 每例应支付额；
   与 `billing.Settlement` 打通，出"病组盈亏"（实际成本 vs 病组支付）。
2. **DIP 病种分值**：`DipCatalog`（病种目录/分值）+ 按分值点数结算，与 DRG 并行可切换（县域多为 DIP）。
3. **医保智能审核规则**：把已有的 `rules.py` DSL 引擎接到结算单上——
   超频次/超量/性别年龄禁忌/串换/分解住院等规则，产出疑点单进人工复核。
4. **总额预算编制**：`FundPool` 总额当前是手工录入，补"按上年基数 + 增长系数 + 人头"测算编制。

**价值**：把 DRG 从"看板"升级为"支付"，把基金监管从"看比例"升级为"抓疑点"，
这是医保"总额包干、结余留用、超支分担"能真正驱动行为改变的前提。

#### E3　双向转诊闭环深化：病历随转 + 下转康复计划 + 转诊号源预留
**现状证据**：`referrals.py` 状态机完整但**很薄**——无病历随转、无下转康复计划/回复单、
接诊后**无号源预留**、无退回路径、与医保差别化报销无联动。`appointments.py` 号源**按机构分池**，
无医共体统一号源池、无"转诊号源预留"。

**建设内容**：
1. **病历随转**：转诊单挂接就诊摘要/检查结论/用药（引用既有 `ExamReport`/处方/`encounter`，只做授权引用不复制）。
2. **下转闭环**：上级出"下转康复计划/随访建议单"，基层接诊回填"下转回复单"，形成上下闭环。
3. **转诊号源预留**：接诊时从上级号源池预留一个号（复用 `appointments` 原子占位），
   居民端凭转诊单直接取号，转诊与挂号打通。
4. **接诊后退回**：补 `accepted → returned` 路径（材料不全/需补检），避免"只能拒或收"。

**价值**：分级诊疗"转得动、接得住、管得好"的核心是信息随人走 + 号源有保障，
当前"只转状态不转信息"是最大断点。

### 第二梯队 · 全人群兜底与药械供应深化（纯后端可落地）

#### E4　公共卫生短板补全 + 12 类项目登记看板
**现状证据**：基本公卫 12 类中，**严重精神障碍患者管理、结核病患者健康管理**
无专属模块（仅在 `chronic.py` 以敏感标记出现）；**卫生计生监督协管**仅靠 `publichealth.py`
通用监测域覆盖，非结构化协管；无"公卫 12 类"统一项目登记与完成度看板。

**建设内容**：
1. **严重精神障碍患者管理**：建档/危险性评估分级/随访/服药依从性/关锁与应急处置留痕（高敏隔离沿用现有机制）。
2. **结核病患者健康管理**：督导服药（DOT）记录/疗程管理/密切接触者筛查/转诊定点。
3. **卫生监督协管**：食品/饮用水/学校/职业/放射五类协管巡查结构化（承接 `publichealth.py` 已有监测域）。
4. **公卫 12 类项目登记与完成度看板**：项目注册表 + 按机构/人群的覆盖率/完成率仪表盘（复用 `metrics.py` 单一查询源模式）。

**价值**：紧密型医共体的公卫职责是"全人群、全生命周期兜底"，两类重点疾病缺位是明显短板。

#### E5　药品统一采购、统一配送与追溯
**现状证据**：`pharmacy.py` 有余缺调拨/缺药预警/采购建议/**逐机构**采购单，
但**无医共体统一采购/带量采购/集采**（grep 带量/集采/统一采购均无）、**无中心统一配送单**
（只有机构点对点调拨）、**无药品追溯码**。`purchase-suggestions` 仅分析不执行。

**建设内容**：
1. **统一药品目录 + 中选品种**：医共体级统一目录，标注集采中选/带量品种与约定量。
2. **带量采购量分配**：按各成员机构历史用量分解约定量，量价挂钩、进度跟踪。
3. **中心统一配送**：中心药房→成员机构的配送单/拣货/签收闭环（区别于现有点对点调拨）。
4. **药品追溯码**：入库/出库/发药登记追溯码，支持一物一码回溯（省平台对接为外部依赖项，先做码流转）。

**价值**：统一采购配送是医共体"资源共享、成本可控"的硬指标，当前采购是"各买各的"。

### 第三梯队 · 数据智能与临床决策支持（标准库实现，仍可 build-free）

#### E6　数据智能层（不引重型依赖，纯 stdlib 统计）
**现状证据**：`/trends` 仅返回历史计数，无预测；无异常检测/回归/画像；`chronic` 风险分是固定查表。

**建设内容**（全部用 Python 标准库/纯算法实现，遵守 build-free 与零重依赖约束）：
1. **趋势预测**：对就诊量/费用/基金支出做简单时序外推（移动平均 + 线性回归 + 同比季节因子），
   给医保基金"月度预结"提前预警超支风险。
2. **慢病风险分层升级**：由"固定查表"升级为多因子加权评分（血压/血糖控制率 + 年龄 + 并发症 + 依从性），
   仍是可解释的规则模型，可配置权重（复用 `formula.py` 白名单 AST 引擎）。
3. **医保/DRG 异常检测**：组内费用离群（均值 ±k·标准差）、机构指标突变检测，喂给 E2 智能审核。

**价值**：把已有成熟的"规则/公式/阈值"底座抬升出一个统计层，决策从"看数"到"预判"。
> 说明：真正的 ML/LLM（NLP 病历、自动编码、影像 AI）需引入重型依赖或外部 API，列为外部依赖项。

#### E7　临床决策支持（CDSS）深化
**现状证据**：`prescriptions.py` 相互作用是**同方内 ATC 精确配对**，无分级、无与**历史/在用**药物联查、
无重复用药类识别、无结构化过敏史核查；无临床路径/医嘱套餐；指南在 `knowledge.py` 只是可检索文本，不可执行。

**建设内容**：
1. **相互作用引擎升级**：相互作用分级（禁忌/慎用/关注）+ 机制说明 + **与患者在用/历史处方联查** + 同类重复治疗识别。
2. **结构化过敏史核查**：患者过敏原列表，开方即时比对（区别于现有"禁忌诊断关键词扫描"）。
3. **临床路径 / 医嘱套餐**：按病种配置标准路径与 order set，入径/变异/出径留痕。
4. **可执行诊间提醒**：把 `knowledge` 指南 + `rules` DSL 结合，做点位主动提醒（该随访了/该复筛了/该转诊了）。

**价值**：从"事后点评"走向"事中拦截与提示"，直接影响医疗质量与安全。

### 第四梯队 · 居民端主动健康与互操作标准化

#### E8　居民端从"可查"到"可办"
**现状证据**：`portal.py` 居民可查档案/账单/转诊/签约、可预约/可评价，但**账单只读（无支付端点）**、
**无自报体征/居家监测上传**、**无在线复诊/图文咨询发起**（远程医疗是医方侧）、
**无检查检验报告查看**、无续方申请。

**建设内容**：
1. **居家监测自报**：居民端上传血压/血糖/体重，自动并入慢病随访（区别于现有仅医方录入/FHIR 入站）。
2. **在线复诊/图文咨询发起**：居民端发起，接入既有集中审方复诊续方链路。
3. **报告查看 + 账单在线支付**：portal 增检查检验报告只读视图、账单接 `PaymentOrder` 网关自助支付。
4. **续方申请**：慢病长处方线上申请→医师审核→药房配送（接 E5 配送）。

**价值**：居民端从"信息门户"变"服务入口"，是签约履约率与慢病管理黏性的关键抓手。

#### E9　互操作标准化增量
**现状证据**：`integration.py` 有 FHIR R4 Patient/Observation（窄）+ HL7v2 ADT/PID + ACK；
**无 Encounter/Condition/MedicationRequest/DiagnosticReport 等资源、无 Bundle 事务、无 CDA**；
`esb.py` 的 `route/persist` 仅内部实体，未真投递外部系统。

**建设内容**（平台侧标准封装，实盘联调属外部依赖项）：
1. **FHIR 资源扩展**：Encounter/Condition/MedicationRequest/DiagnosticReport 出入站 + Bundle 事务。
2. **CDA 文档**：出院小结/转诊单以 CDA 结构导出（承接 E3 病历随转）。
3. **省平台上报连接器骨架**：把 `esb.py` 的 route 抽象出"外部适配器"接口，预留省市监管/医保上报通道。

**价值**：为将来接省平台/区域全民健康信息平台留标准接口，避免二次改造。

## 二、明确的外部依赖项（登记，不排期）

以下需外部条件，平台侧业务流程与接口已闭环预留，联通属实施期集成工作：

- 实时音视频（远程会诊/门诊/教学通道）、DICOM 影像/心电波形共享调阅与移动诊断终端；
- 外部 HIS/LIS/PACS/医保结算/省市监管平台**实盘**联调与数据归集；
- 药品集采省平台对接、药品追溯省平台上报；
- 前端构建工具/框架化（build-free 既定约束，超大 JS 文件可后续增量拆分，须团队 buy-in）；
- SM2/SM4 国密纵深（须密码机或认证密码库采购）；
- 真正的 ML/LLM 能力（NLP 病历结构化、自动编码、影像 AI、智能问答），需重型依赖或外部模型 API。
