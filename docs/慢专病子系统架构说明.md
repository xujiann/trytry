# 全域慢专病全流程管理系统 · 子系统架构说明

本文说明慢专病与县域医共体信息化平台的关系：**它是平台的一个子系统，不是独立系统**。
这不是一句定位口号，而是三层可执行的约束——每一条都有对应的守卫用例
（`server/tests/test_spd_boundary.py`、`test_spd_integration.py`），改坏了会在
CI 上失败，而不是等到实施期才发现。

需求逐条对照见 [全域慢专病全流程管理系统_需求对照表.md](全域慢专病全流程管理系统_需求对照表.md)。

## 一、为什么是子系统

### 支持的理由

招标文件里那些要求，本质上要的都是平台的底座：

| 条目 | 要的东西 | 平台既有能力 |
|---|---|---|
| 平台管理端 #13 | 全县居民主索引、多标识匹配、档案去重合并 | EMPI（`patients` + `/api/dataquality`） |
| 平台管理端 #5 | 县乡村三级机构树用于患者归属、任务派发、逐级转诊、团队授权、考核 | `organizations` 三级树 + `org_groups` |
| 平台管理端 #21 | 共用患者、组织机构、任务、随访、消息、考核底座 | 由 **76 个外键**保证，不是靠约定 |
| 平台管理端 #2 | 按机构、科室、人员、业务范围划分功能与数据权限 | 六角色 RBAC + `visibility.py` 横向隔离 |

### 反对拆成独立系统的理由

这套业务约八成动作要读平台数据——转诊的"有效就诊判定"要读就诊记录、随访方案
匹配要读出院与手术记录、考核取数要跨诊疗/转诊/随访三类表。拆库之后这些全变成
接口同步，而同步有延迟、有不一致，**这些数字是要进考核和绩效的**。再加上复制
一份患者与机构主数据，等于额外背一份永久对账工作。

## 二、依赖方向：单向

```
        ┌──────────────────────────────┐
        │  县域医共体信息化平台          │
        │  patients / organizations     │
        │  users / encounters ...       │
        └──────────────┬───────────────┘
                       │  ①经 platform.py 读（白名单）
                       │  ②经 events.py 收事件（平台只 publish，不知道谁在听）
        ┌──────────────┴───────────────┐
        │  app/spd/  慢专病子系统        │
        │  59 张 spd_* 表 / 182 个接口   │
        └──────────────────────────────┘
```

平台侧只有两处触点，都是"装卸"性质：

| 位置 | 内容 |
|---|---|
| `app/models.py` 末尾 | import 子系统模型，让 `Base.metadata` 认识 `spd_*` 表 |
| `app/main.py` | 调 `register_spd(app)` / `seed_spd(db)` |

除此之外，平台任何模块 import 子系统都会让
`test_spd_boundary.py::test_平台不得依赖慢专病子系统` 失败。数据层同理：
平台表外键指向 `spd_*` 也会失败——那会让子系统卸不掉。

## 三、A 层：边界

### 目录结构

```
server/app/spd/
├── __init__.py      装卸入口：register_spd / seed_spd / spd_enabled
├── platform.py      ★ 对平台的唯一依赖入口（白名单）
├── models.py        59 张表
├── rules.py         纳入/排除/转诊触发/问卷异常共用的规则求值器
├── service.py       领域服务：事实汇集、路径推进、任务派生、积分、超期扫描
├── seed.py          病种/量表/指标/积分/随访方案/报告模板种子
├── subscribers.py   平台领域事件的订阅
├── collectors.py    数据源采集器注册表
├── jobs.py          子系统的两个定时任务
└── routers/         九个路由模块（按领域分，不按端分）
```

### 允许依赖的平台能力（白名单）

清单在 `app/spd/platform.py` 与 `tests/test_spd_boundary.py::PLATFORM_ALLOWLIST`
两处**同步维护**，加依赖要同时改两处并写明理由——依赖面必须始终是可数的，
否则"子系统"只是一个目录名。

| 类别 | 内容 |
|---|---|
| 基础设施 | `config` `clock` `database` `datetypes` `deps` `visibility` `concurrency` `formula` `events` `scheduler` `ws` |
| 主数据 | `Patient` `Organization` `User` |
| 诊疗数据 | `Encounter` `Admission` |
| 居民端 | `ResidentAccount` `current_resident` `accessible_patient` |
| 消息 | `Notification` `broadcast` |

**唯一的例外**：`spd/models.py` 直接从平台 `models` 取 `Money` / `utcnow` 两个
列类型。这是为断开一个真实的导入环——`app/models.py` 末尾要 import 它，若它再
经 `platform.py` 去 import 平台路由，就会在平台尚未初始化完时反向拉起路由。
守卫用例把这条例外的范围钉死在这两个名字上。

### 归属约束

- 表一律 `spd_` 前缀（运维按前缀备份、迁移、库内授权）；
- 接口一律长在 `/api/spd` 或 `/api/portal/spd` 下，且这两个前缀下不许有非子系统接口；
- 子系统的路由文件与平台路由**受同一批防复发扫描**（并发读改写、唯一约束冲突、
  横向机构隔离）——`test_stage14/15` 的扫描目录已包含 `app/spd/routers/`。
  换个目录就绕过检查，是这类规则最典型的失效方式。

## 四、B 层：集成契约

### 1. 平台适配层 `platform.py`

子系统的业务模块不直接 `from app.models import ...`。收口的意义在实施期才显出来：
平台调整 `Encounter` 的诊断字段时改一处，而不是去九个路由文件里找。

平台数据的"形状"也归适配层，不归业务：

| 适配层函数 | 承载的口径 |
|---|---|
| `diagnosis_codes` | 取**全部历史就诊**的诊断 + ICD-10 父目（按最近一次判定会让来看感冒的高血压患者掉出目标池） |
| `org_level` | 机构层级 → 转诊链路层级 |
| `notify_user` | 给具体某个人投递站内消息（平台的 `notify_staff` 是按机构+角色群发的） |

### 2. 领域事件 `app/events.py`

平台**发布**，子系统**订阅**。平台不知道谁在听，依赖方向因此保持单向。

| 事件 | 发布点 | 子系统动作 | 默认 |
|---|---|---|---|
| `admission.discharged` | 出院办理 | 按随访方案生成多时间点随访计划 | **开** |
| `encounter.created` | 就诊登记 | 按病种纳入规则识别疑似人群 | **关** |

三条契约（都从平台既有的 `notify.py` 学来）：

1. **同事务、只 add 不 commit**：订阅者随发布方一起提交或一起回滚。业务回滚了、
   随访计划却建出来了，是最难查的那种脏数据。
2. **订阅者不得抛异常**：总线统一兜住并记日志——出院登记不该因为"随访模块的一个
   空指针"而失败。有对应用例。
3. **订阅者必须幂等**：重复投递不该变成同一个病人两份随访计划。有对应用例。

为什么两个默认不同：出院订阅只有配了诊断关键词的方案才会命中，没配关键词的方案
不匹配任何人，所以开着是安全的；而全域自动识别会在生产上产生大量"疑似"记录，
在诊断数据质量参差时会淹没真正要复核的人，因此交给各县用
`MEDPLAT_SPD_AUTO_IDENTIFY_ON_ENCOUNTER` 自行开启。关着的时候，管理端的
`POST /api/spd/screenings/auto-run` 仍可手工触发**同一段代码**。

事件把触发点挪到动作发生的那一刻，回溯扫描（`followup-plans/auto-match`）退化成
兜底而不是主路径。刻意不做异步队列与跨进程投递——平台已有 ESB 负责跨系统消息，
这里只解决同一应用内的模块解耦。

### 3. 数据源采集 `collectors.py`

`spd_data_sources` 原先只有"登记 + 监控"，现在补上采集：按 `source_type` 找采集器，
`run_source` 统一写同步日志并刷新监控冗余列（成功率按最近 100 次算）。

- 未注册类型的数据源**记为失败**而不是静默跳过——监控页上看得见；
- `run_due_sources` 按各源自己的 `freq_minutes` 判定到期，而不是所有源一个周期
  （HIS 可能要 5 分钟一次，体检系统一天一次就够）；
- 实施期接真实 HIS/LIS 时，`register_collector("LIS", fn)` 注册一个函数即可，
  不需要改调度、监控与告警。

内置的 `internal` 采集器刻意做得很薄：它是采集器该长什么样的样板，
不是一个假装能用的模拟实现。

## 五、C 层：运维隔离

| 能力 | 做法 |
|---|---|
| 装卸开关 | `MEDPLAT_SPD_ENABLED=false` → 不注册路由、不订阅事件、不注册定时任务、不种子化 |
| 独立迁移分支 | 迁移带 `branch_labels = ("spd",)`，与主平台并行推进不抢 head；**升级命令用 `alembic upgrade heads`（复数）** |
| 分子系统备份 | `scripts/spd_backup.sh` 只导 `spd_*` 表，用于子系统单独升级的回滚点、数据交付、迁库演练 |
| 库内授权 | 表前缀统一，可按前缀授予只读账号（例如给上级卫健开只读视图） |

两个必须写明的限制：

1. **分子系统备份不自洽**。`spd_*` 有 76 个外键指向 `users` / `organizations` /
   `patients`，单独恢复到空库会失败，必须恢复到同一套平台主数据上。
   "以为备份了其实恢复不了"是备份最常见的坑，所以脚本本身也会打印这句提醒。
2. **同应用同库的代价**。慢专病的大统计接口（区域看板、考核跑分）与主平台共享
   连接池，压力上来时会互相影响。现有接口都做了分页与索引，真上量后建议读写分离，
   统计走只读副本。

### 关于 PostgreSQL 独立 schema

把 `spd_*` 放进独立 schema 能在保住跨表 join 与外键的同时拿到运维隔离，是比表前缀
更强的隔离粒度。**当前没有实现**：SQLite 不支持 schema，而平台要同时跑在
SQLite（开发/演示）与 PostgreSQL/国产库（生产）上，这一步无法在现有测试体系里
验证，实现了也只是"看起来支持"。需要时的改造路径是：给 59 个模型的
`__table_args__` 加 `{"schema": settings.spd_schema}`、迁移里 `CREATE SCHEMA` 并
指定 `version_table_schema`、跨 schema 外键显式限定目标——建议在有 PG 测试环境
之后再做，并配一条真实连 PG 的用例。

## 六、与既有模块的关系

| 既有模块 | 关系 |
|---|---|
| `/api/chronic` 慢病管理 | 保留。单病种随访分级台账（公卫口径），与 `spd_*` 并行运行 |
| `/api/disease-programs` 专病管理 | 保留。院内单机构专病入组—路径—出组，`spd_*` 是其全域形态 |
| `/api/followups` 随访中心 | 保留。四类随访任务；子系统的智能随访端提供方案规则、问卷、呼叫与抽查质控等通用能力 |
| `/api/referrals` 双向转诊 | 保留。两点之间的一次转诊；子系统的逐级转诊是四环节链路，闭环口径不同，不合表 |
| `/api/performance`、`/api/metrics` | 保留。院级绩效与医共体监测指标；子系统考核是病种维度的分级考核 |

**不建议**把这些模块合并或删掉：招标文件只要求并行运行，而它们承载着在用的公卫与
院内业务，合并等于在实施期打断正在跑的业务。
