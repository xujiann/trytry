# 第九轮开发计划：横向越权与数据隔离

第八轮的教训是"一道看起来关着的闸门只关了 15%"。带着这条教训回头看平台的
权限体系，发现了同一个形状、但后果严重得多的问题。

本计划的每一条都附实测证据，不列"建议加强 XX"这类无法验收的条目。

---

## P0：跨机构数据隔离（本轮主线）

### 证据

平台的越权矩阵测试一直是绿的，输出还写着：

```
越权矩阵：写接口 326 个 = 带守卫 289 + 白名单开放 37；覆盖率 100.0%
```

**但它测的只有"纵向越权"**——医生不能干管理员的事。**横向越权一条没测**：
甲机构的医生能不能看乙机构的数据。

实测（乙镇卫生院的医生，去访问甲县医院的数据）：

| 请求 | 结果 |
|---|---|
| 按 ehc_no 调阅甲院患者档案 | **HTTP 200，返回档案** |
| 全部患者清单 | **HTTP 200，返回甲院患者** |
| 甲院职工名册 `?org_id=甲` | **HTTP 200，返回甲院职工** |
| 甲院财务汇总 `?org_id=甲` | 200，但返回空（这里恰好有作用域） |

静态扫描印证：涉及 `org_id` 的函数 **203 个，做了调用者机构校验的 20 个（9%）**；
`user.org_id` 在整个 `app/routers/` 里出现 **0 次**。

现有的 `resolve_org_scope` 有 26 个文件在用，但它是**筛选器**不是**授权器**——
它解析"调用方想看哪个机构"，从不校验"调用方能不能看这个机构"。
两者长得像，这正是它看起来已经防住了的原因。

### 这不是"全部拒绝"就能了事

医共体的存在意义就是跨机构协同：结果互认、双向转诊、牵头医院管理成员单位、
家庭医生签约随访。一刀切禁止跨机构访问等于把平台的主要功能关掉。

所以要建的是**可见范围模型**，不是墙。

### 口径（已定：A 案）

**默认本机构，跨机构需要一条明确的业务理由。**

| 可见范围 | 依据 |
|---|---|
| 本机构数据 | 用户 `org_id` |
| 本医共体内成员机构 | 仅限**汇总统计**，不含患者明细 |
| 他机构患者明细 | 需业务关系：转诊单、签约关系、或既有的档案调阅授权（浙#59 已有模型） |
| 全域 | `admin` / `director`（且留痕） |

曾考虑的 B 案是"医共体内默认全可见，跨医共体拒绝"——实现快得多，但把一个县
所有机构的患者明细对所有临床角色敞开，与《个人信息保护法》最小必要原则相悖，
**已否决**。

按 A 案，"能看"要有据可查：每一次跨机构访问都能指出依据是转诊单、签约关系
还是调阅授权。这也正是 P1 留痕能写出"依据"这一列的前提——
两者是同一个模型的两面。

### 做法

1. `deps.require_org_access(org_id)` —— 与 `require_roles` 并列的守卫，
   校验的是"能不能看这个机构"；
2. 患者维度另起 `deps.assert_patient_visible(patient, user)`，走业务关系判定；
3. 清单接口默认按可见范围过滤，而不是返回全表；
4. **横向越权矩阵测试**：仿照现有纵向矩阵，逐个接口跑"甲机构用户访问乙机构
   数据"，覆盖率必须同样可量化。没有这条，改完照样不知道漏没漏——
   这正是第八轮那道 15% 闸门的教训。

工作量估计：约 200 个接口需要过一遍，其中患者相关 74 个要逐个判定业务关系。
**建议分两批做**：先患者与病历（法定要求最硬），再管理与财务。

## P1：读操作留痕

审计中间件的注释写得很清楚——记录的是"**写操作**请求尝试"。

也就是说，上面那些跨机构调阅患者档案的行为，**既没被拦，也没留下任何记录**。
《医疗卫生机构网络安全管理办法》与《个人信息保护法》对诊疗数据的要求是
"谁在什么时候查了谁的档案"必须答得出来。

做法：患者档案、病历、检查报告等敏感读接口单独记 `AccessLog`（不进现有的
写审计哈希链，避免高频读把链拖慢），字段至少含 调阅人 / 机构 / 患者 /
时间 / 依据（本机构｜转诊｜签约｜授权）。

**P0 与 P1 要一起做**：跨机构访问一旦按 A 案放开一部分，留痕就是它的配套；
先放开后补留痕，中间这段时间是没法追溯的。

## P2：第八轮的收尾项

三条今天明确记录、未做的：

1. **实训名额超额报名**。`_enrolled_count(db) >= plan.capacity` 是 COUNT 式
   check-then-act，两个人同时报名都判定还有名额。需要给 `TrainingPlan` 加
   计数列 + 迁移，然后用 `claim_quota`。后果轻（多几个学员），但它是今天
   刚扫过一遍的那一类，留着不合适。
2. **扫描盲区**：跨函数传对象、从容器里取对象再插，现行规则仍看不见。
   建议做法不是继续加规则复杂度，而是**定期量一次覆盖率**——
   第八轮的教训是规则会绿着骗人。
3. **`tests/` 17 条存量 lint 告警**：未用变量、无占位符 f-string。一次清完。

## P3：清单接口的数据规模

实测：**119 个 GET 清单接口既无 `limit` 也无分页**，直接 `.all()` 返回全表。

现在没事，因为测试库数据量小。但病历、处方、检查报告、审计日志这些表是
按天线性增长的，一个县跑一年之后，这些接口会一个个变成慢查询，
而且**故障表现是整页打不开，不是慢一点**。

建议：按表的增长速率排序，先给增长最快的十几个加分页（平台已有 `paginate`
工具），其余登记在案分批做。不建议一次全改——119 个接口同时改分页，
前端要跟着全改一遍，风险比收益大。

## 不在本轮的

维持原判，理由照旧：

- 金额端到端 `Decimal`（今为 `asdecimal=False`）——留待接入真实医保结算同批做；
- SM2/SM4 —— 不自己实现密码算法；
- DICOM 阅片、波形分析 —— 不做玩具版；
- 国产数据库适配 —— 没有环境实测，不写"已适配"。

```
P0 第一批（患者与病历隔离 + 横向越权矩阵测试）
        ↓  与之同批
P1 敏感读留痕
        ↓
P0 第二批（管理与财务隔离）
        ↓
P2 收尾三项
        ↓
P3 分页（按增长速率分批）
```

P0 第一批与 P1 是本轮的实质内容，其余可以往后排。
