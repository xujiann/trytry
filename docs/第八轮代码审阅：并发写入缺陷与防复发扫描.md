# 第八轮代码审阅：并发写入缺陷与防复发扫描

审阅对象：阶段九·五新增的模块（医废追溯、疫苗接种、多点触发监测、病理标本、
字典导入、RBAC 权限点）。方法沿用前几轮——**每一条怀疑都写脚本去触发，
看它到底会不会坏、怎么坏**，不靠读代码下结论。

结论先说：这一轮找到的 4 个缺陷里，有 3 个是**同一个错误的第三、第四、第五次
复发**。所以这一轮的重点不是那几个补丁，而是让这个形状以后写不出来。

---

## 一、一个已经犯过三次的错误

平台在阶段七踩过一次 check-then-act：全域基金池「先查有没有、没有就建」，
并发下建出两个（记为 D-2）。阶段九修掉了，并把教训写进了注释。

结果阶段九·五新写的三个模块，各犯了一遍：

| 编号 | 位置 | 实测现象 |
|---|---|---|
| D-5 | `medwaste.collect` | 追溯码按 `COUNT+1` 算，8 并发只落库 5 条，3 条抛未捕获 `IntegrityError` 成 500 |
| D-6 | `vaccination.vaccinate` | 先判 `库存-已用>0` 再 `+=1`，**库存 1 支实测打出 4 针**，`used_quantity` 只加到 1 |
| D-7 | `surveillance.report_syndrome` | 先查再插，8 并发出一个 500 |

D-6 最重。疫苗是按批号强监管的品类，台账说还剩 0、实际打了 4 针，这种账实
不符在需要按批号召回时直接失去意义——而召回正是批号管理存在的全部理由。

D-5 次之。《医疗废物管理条例》要的就是全过程可追溯，收集环节丢记录，台账从
第一步就对不上。

**知道这个坑并不足以不掉进去。** D-2 的修复注释就写在仓库里，写这三处的时候
它也在，照样犯。所以这一轮除了补三处，还做了两件事：

1. `app/concurrency.py`：把正确写法固定成函数，让写对比写错省事；
2. `tests/test_stage14_concurrency.py` 里的 AST 扫描用例：往带唯一约束的表里
   直接插入、又没处理约束冲突的，一律红。

扫描用例立起来当场又抓出 5 处存量同类问题（见第三节）——这条规则不是为将来
立的，它立起来就有欠账要还。

> **订正（见第六节）**：第一版扫描只认内联写法，覆盖率仅 11%，底下还压着
> **48 处**同类问题没被发现。上面这句"抓出 5 处"当时读起来像是把存量清干净了，
> 实际差得远。



## 二、五个共用做法（`app/concurrency.py`）

| 函数 | 用在哪 | 要点 |
|---|---|---|
| `insert_or_conflict` | 本来就不该重复的（同机构同编码资源） | 撞了给可读的 409，不是 500 加一段栈 |
| `insert_with_retry` | **服务端生成的顺序编号**（医废追溯码、病理标本号） | 重试放服务端。调用方重试的是整个业务动作，压力下还会撞进下一次冲突；真正该重试的只是「取下一个号」 |
| `upsert_unique` | 有则覆盖、无则新建（症候群日报） | 先试插再取回来更新。反过来写就是 check-then-act |
| `claim_quota` | 占额度（疫苗批次） | 判定与扣减在同一条 SQL 里，中间隔一次 Python 判断这个函数就没意义了 |
| `insert_if_absent` | 批量幂等导入（字典、审方规则、权限点、内置角色） | SAVEPOINT 把冲突圈在单行内，一条撞车不连累整批 |

`claim_quota` 其实是平台早就在用的做法（`appointments.book_slot` 的原子占号），
只是没抽出来，于是疫苗批次那里又用回了「先读再判再加」。**没抽出来的正确做法，
等于没有。**

### 顺带记一个自己踩的坑

`insert_if_absent` 第一版成功路径上忘了 `savepoint.commit()`，每行都往外层事务
再压一层没释放的 SAVEPOINT。5 行的样例跑得好好的，接上真实规模——权限点同步
640 个写接口——`db.commit()` 收束时直接 `RecursionError`，**应用起不来**。

留档是因为教训不在「忘了一句」，在**用 5 行样例验证了一个按行数递归的东西**。
对应的用例按 800 行压，不按 5 行。

## 三、扫描用例抓出的 5 处存量问题

`dictionaries.bulk_import`、`prescriptions.import_rules`、`rbac.sync_permissions`、
`rbac.seed_builtin_roles`、`rbac.grant_permissions` —— 都是「先把已有的查出来、
不在里面的才插」，而这类接口**一次 commit 提交整批**，一条撞车整批回滚。
导入方看到的是 500 加上一条都没进去。

其中两处在启动路径上：多进程部署（`gunicorn -w 4`）时 4 个 worker 同时启动、
同时读到同一份 existing、同时插同一批权限点，后插的抛 `IntegrityError`——
**worker 起不来**。单进程跑测试永远看不到。

五处统一改用 `insert_if_absent`。预读的 existing 保留，但只作为省一次 SAVEPOINT
的快路径，**不再是判据**——落库成不成以插入结果为准。

## 四、D-8：医废清单看不到追溯码

不是并发问题，是顺手发现的。`GET /api/medwaste` 与 `/alerts` 套的是阶段五写的
`WasteOut`，字段停在 org_id/waste_type/weight_kg/collected_date/status/handler_name，
**追溯码不在里面**。

于是这个模块最核心的那一列，清单页一列都看不到。虽然有 `/trace/{code}` 可以反查，
但码是从清单上抄的，抄不到就查不了。滞留预警更直接：预警的下一步动作是去把那
几包找出来，只报「某机构有 3 包超期」而不报是哪几包、在哪间暂存间，等于没报。

两处改回 `_waste_out`（点位、暂存与交接时间一并带出），预警另加 `overdue_days`
（超期几天）与 `limit_date`——预警页要按严重程度排序，不该让前端自己减日期。

**这类缺陷的成因值得记**：阶段九·五给医废加了追溯码、点位、暂存环节，
写了新的 `_waste_out`，POST 用上了，两个 GET 忘了换。功能是加了，**看不见**。

## 五、测并发的用例自己必须先真的并发

字典导入那条用例，第一版起 8 个线程就完事——旧代码照样全绿。原因是线程创建
本身有先后，前一个常常已经提交完了后一个才开始读，**竞态窗口根本没打开**。
加上 `threading.Barrier` 卡住所有线程、放行时才一起进，旧代码立刻现出 500。

本轮 5 条并发用例全部按老规矩验过**非空洞**——把修复逐个改回旧写法，确认变红：

| 用例 | 改回旧写法后的实测 |
|---|---|
| 并发收集医废 | `[201×4, 500×4]` |
| 并发接种 | `库存 1 支却成功接种 3 次` |
| 并发上报症候群 | `[201×7, 500]` |
| 并发字典导入 | `[200×7, 500]` |
| SAVEPOINT 不堆积 | `RecursionError` |

第 6 条（`test_覆盖语义在串行下照常生效`）在旧代码上就是绿的，这是对的——
它守的是语义不被改坏，不是并发。并发改造很容易顺手把「重复上报按覆盖」
变成「重复上报报错」，那是另一种坏。

## 六、订正：第一版扫描只覆盖 11%，底下压着 48 处同类问题

上面第一节说"扫描立起来当场抓出 5 处存量问题"。**这句话给出的印象是错的**，
订正如下。

第一版判据只认内联写法 `db.add(Model(...))`。但平台 147 处插入里，125 处是
先赋值再插：

```python
obj = Model(...)
db.add(obj)          # ← 第一版看不见
```

覆盖率 22/147 ≈ **11%**。把扫描改成跟踪函数内的变量赋值之后，立刻多出
**48 处**同一个 check-then-act，涉及 46 张带唯一约束的表。

**一条只覆盖 11% 的规则比没有规则更糟**：它会让人（包括写它的人）以为这一类
已经守住了。这一轮真正的教训在这里，不在那三个补丁。

48 处按形状分三类修完：

| 形状 | 处数 | 改法 |
|---|---|---|
| 查重则 409 | 32 | `insert_or_conflict`；原预检查保留作快路径与更好的报错，落库以约束为准 |
| 有则更新 | 10 | `upsert_unique`；累加语义（药品库存、血库、成绩取最高分）改用 `insert_if_absent` 保证行存在再累加 |
| 无预检查 | 6 | 幂等建档撞约束时返回既有那条 |

几处后果值得单列：

- **孕产妇建册 / 慢病建档**：并发下建出两份档案，产检与随访记录会分叉，
  两本各记一半，哪本都不全；
- **医学证明签发**：编号也是 `COUNT+1` 算的（与医废追溯码同型），
  死亡证明、出生缺陷登记都是对外出具的法定文书，重号或丢件不是小事；
- **药品库存**：两张采购单同时验收同一药品，原先都去建库存行，撞唯一约束
  500，**两批药都没入成**，而药已经在库里了。

修的过程中又自己踩了两个坑，都写进了注释与用例：

1. `insert_if_absent` 返回 False 后提前 `return`，外层写事务没结束，整个请求
   一路握着 SQLite 写锁，审计中间件落库直接 `database is locked`；
2. `insert_with_retry` 默认 5 次重试在 8 路并发下顶不住（一个请求 503）。
   N 个请求抢号，最后一个最坏要重试 N 次，默认提到 12。

## 七、D-9：读-改-写累加，实测丢掉 60 支药

顺着 `receive_purchase` 往下查出来的第二类，与唯一约束无关：

```python
stock.quantity += body.quantity     # 读进 Python，加完整体写回
```

并发下两个请求读到同一个旧值，后写的盖掉先写的。实测：库存行建好 10 支后
8 路并发各入库 10 支，应为 90，**实际 30，凭空少了 60 支**。这类账实不符
最难查——每一笔入库的日志看上去都成功了。

路由层共 10 处，逐一改为原子 SQL（新增 `add_amount` / `take_amount`）：

- **物资出库**：原先"先判够不够再 `-=`"，实测 **库存 5 件出库成功 8 次**；
- **发血**：同样的形状。血按毫升对账，发出去的比账上扣的多，血库盘点必然对不上；
- **短信验证码错误次数**：这是防爆破的计数器，丢一次更新等于白送一次尝试机会，
  并行猜码时 `MAX_CODE_ATTEMPTS` 形同虚设；
- **ESB 重投次数**：丢更新则次数涨不上去，消息永远进不了死信队列，**一直重投**。

配了一条扫描用例盯住 `obj.col += x` 形状。成因与前面完全一样：正确做法
（原子 UPDATE）平台早就有（`appointments.book_slot`），只是没抽出来，
于是每写一个新模块就再手写一遍读-改-写。

## 八、D-10：一件物资领完，整张物资清单 500

写 D-9 的并发用例时撞出来的，与并发无关，串行照样复现。

`AssetOut` 直接继承了 `AssetCreate`，连 `quantity: int = Field(ge=1)` 一起继承。
建档时不该建 0 件物资——这条约束没错；但出参也带上它之后，物资一旦全部出库
（现存量 0）就序列化不出来，**整张清单连带 500**，别的物资跟着看不见。

出参放宽到 `ge=0`，入参不动（建档 0 件仍然 422）。

与 D-8（医废清单套着阶段五的旧出参、看不到追溯码）同因：**出参与入参形状
相近就顺手继承，而两者的约束本来就不是一回事**。入参约束的是"允许创建什么"，
出参约束的是"数据库里可能有什么"，后者永远更宽。

## 九、扫描用例的判据与豁免

判据（现行版）：函数里 `db.add` 了某个模型——**内联构造与先赋值再插两种写法
都认**——而该模型的表带唯一约束，则该函数必须出现 `IntegrityError` 或
`concurrency` 的助手之一。

仍会有漏网：跨函数传对象、从容器里取对象再插。但**不会误报**——命中的都确实是
「往带唯一约束的表里插入」。宁可漏也不误报：一条经常误报的规则会先被加豁免，
再被加得没人看，最后被删掉。

漏网不等于可以不管。第一版的漏网率是 89%，而它当时看起来同样"全绿"——
所以这条规则的覆盖率本身值得定期回头量一次，别只看它是不是绿的。

豁免必须写理由。一旦可以不写，这份清单很快会变成绕过检查的后门。另配
`test_豁免清单不得腐烂`：豁免条目对应的函数改名或删掉后，豁免会一直挂着，
这条用例把它揪出来。

当前豁免只剩一条：`org_groups.py:add_member`——已捕获 `IntegrityError`。

原先豁免的 `users.py:create_user`（理由写的是"并发重名只是 500 一次，
不产生错账，暂按已知接受"）已经改用 `insert_or_conflict` 直接修掉。
那条理由本身站不住：注册撞车返回 500 而不是"用户名已存在"，
对着屏幕的人不知道该换个名字还是该重试。**能顺手修的，不该写进豁免清单。**
